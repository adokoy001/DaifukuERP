## 目的
公開後の最初の品質改善として、本人が安全にアカウントを管理できること、失敗時に内部情報や入力を失わないこと、日をまたぐ勤怠と休暇の整合性を優先する。既存15業界に共通する日常業務を改善し、検証を継続実行できる状態にする。

## 受入基準（EARS）
- AC-1: WHEN 予期しない例外やDBの制約違反が発生する THEN API/MCP SHALL SQL・値・秘密を公開応答へ含めず、安全な一般エラーと追跡可能な識別子で通知する。既知の業務エラーは契約を維持し、ログにも生SQLや秘密を残さない。
- AC-2: WHEN 有効な本人が現在のパスワードを提示して変更する THEN SYSTEM SHALL 既存の強度規則を適用し、本人確認・更新・全セッション失効・秘密を含まない監査記録を原子的に行う。誤ったパスワード、失効済みトークン、並行する古い変更は受け入れない。
- AC-3: WHEN 本人が全端末のログアウトを実行する THEN SYSTEM SHALL REST/MCPの既存セッションを失効する。本人画面は会社未所属でも利用でき、変更・失効の成功後は再ログインを案内する。古いリクエストの遅延401は新しいログインを消去しない。メール再設定・MFA・個別端末管理は含めない。
- AC-4: WHEN 参照候補の検索文字列が変わる THEN Web SHALL 以前の文字列の候補を選択させず、検索待機・検索失敗・再試行を明示し、キーボードで正しい候補を選べる。
- AC-5: WHILE 同じ本人・会社で編集している WHEN 自動再取得が一時的な通信障害/5xxで失敗する THEN Web SHALL 編集ダイアログと未保存入力を保持し再取得を案内する。401/403/404やidentity変更時には以前の機微データを残さない。
- AC-6: WHEN 全日有給と勤務実績/訂正を承認する THEN SYSTEM SHALL JST暦日の実勤務区間が重なる承認を両方向で拒否する。終了が翌日00:00ちょうどなら翌日との重複とせず、記録済み休憩だけが翌日にある場合も実勤務と扱わない。未退勤は現在時刻までの実勤務だけを検査し、失敗時の台帳・承認状態は変わらない。WHEN 従業員の拠点変更により別拠点の有給付与台帳または確定給与明細が参照不能になる THEN SYSTEM SHALL 理由を示して変更を拒否し、従業員・所属権限・履歴を保全する。該当履歴のない拠点変更は従来どおり認める。
- AC-7: WHEN 公開候補のCIを実行する THEN CI SHALL 統合gateでWebを含む単体とDBを検証し、Web型・build、ブラウザー、導入/移行/復元も検証する。現行文書は公開済み版と認証/エラー/勤務境界を正しく説明する。

- AC-8: WHEN REST/MCP形式のJSON検索条件がtimestamp項目またはcreatedAt/updatedAtへタイムゾーン付きISO日時を指定する THEN SYSTEM SHALL 等値・不等値・範囲・$inを同じ瞬間として比較し、nullと権限条件の意味を維持する。日時は秒まで明示し、小数秒はミリ秒精度まで受け付ける。不正な日付・時刻・オフセット・曖昧なタイムゾーン省略・非日時値・timestampの$likeはdriver例外になる前に項目付きVALIDATIONで拒否する。通常の日付項目と文字列項目は変換せず、公開DomainはJSON scalarを維持する。同一項目内で複数の既知演算子を指定した場合はすべてをANDで評価し、一部の条件を無視しない。不明な演算子・空の演算子オブジェクト・値の形が不正な演算子は項目付きVALIDATIONで拒否する。

## 設計境界
スキーマ変更は行わず既存sessionVersionとトランザクションを使う。業務読み書きはContext/Repository経由とし、tenant-levelの本人認証処理は既存のアカウント管理境界に従う。給与の制度値・税/保険算定・日跨ぎ給与の対象範囲は変更しない。勤務/休暇の境界は既存の全日休暇契約の整合性修正である。

2. `pnpm gate`、Web単体/型/build、分離した合成データでE2Eを実行する。
3. スマホ375pxとデスクトップで本人アカウント、参照検索、再取得失敗時の画面を確認する。
