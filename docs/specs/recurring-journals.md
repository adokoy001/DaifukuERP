# Spec: recurring-journals（定期仕訳と前払費用の按分）

- 状態: implemented（2026-10-30、[作業記録](../log/2026-10-30-recurring-journals.md)）
- モジュール: `modules/accounting`（entity `recurring_journal` / `recurring_journal_line` / `recurring_journal_run`、action `accounting.generate_recurring` / `accounting.recurring_schedule` / `accounting.todo`、会社設定 `accounting.recurring_auto_submit`）、`kernel`（DSL: entity の明細）、`apps/web`（`/finance/recurring`） ／ 依存: [ui-kit](ui-kit.md)（D1）、[settings-console](settings-console.md)（B1）、[document-links](document-links.md)（C2: 複製・関連）、[inbox](inbox.md)（C3）、[close-guide](close-guide.md)（C4）、[navigation-assist](navigation-assist.md)（D2: 画面の説明）
- ADR: **ADR-0031（新規）entity の明細（`defineEntity({ lines })`）**。0027〜0029 は使用済み・予約済み、0030 は同じ round の opening-balances（B6）が使うため 0031 とする（統合時に衝突したら統合担当が振り直す）。関連: ADR-0002（DSL）、ADR-0005（追記型の帳簿）、ADR-0006（document の状態）、ADR-0013（port）、ADR-0014（明細の hook）、ADR-0016（module 専用の書込み権）、ADR-0027（設定の表示属性）

## 目的（1段落）

家賃・リース料・顧問料の未払計上、前払費用の費用への振替など、毎月・四半期ごと・毎年同じ形で起こる仕訳を、経理担当者は今は毎回「仕訳」画面で手入力している（[マニュアル 05](../manual/05-daily.md)「仕訳を入力する」）。定期仕訳のテンプレートを登録しておき、期日が来た回の仕訳を下書きで作る（確定は人が行う。会社設定で自動確定も選べるが既定は off）。同じ回を二度作らず、締めた期間には作らず、前払費用の総額を回数で按分する。生成した下書きは普通の仕訳なので、[月次締めガイド](close-guide.md)の「仕訳の下書き」の件数にそのまま現れる。

## 受入基準（EARS）

### kernel: entity の明細（ADR-0031）

- AC-1 WHEN `defineEntity` の設定が `lines: [{ entity, parentField }]` を持つ THE SYSTEM SHALL document の明細と同じ仕組みを使う: 汎用の作成・更新（REST、MCP、`<entity>.create` / `<entity>.update`）が `lines` を受け取って置換保存（`saveLines`）し、取得が `lines` を含み、`/meta` の `EntityMeta.lines` に出す。明細の書込みは親を先にロックして親の版を上げ、親 1 件あたり 500 行（`MAX_LINES`）までとし、`after_lines_saved` hook を保存ごとに 1 回呼ぶ。明細 entity の `parentField` が親への `ref` でなければ定義時の `Error` とする（既存の `lineSpecs` の検査）。関連記録（C2）は明細が持つ参照を親の参照として扱い、明細 entity を CSV 取込（B5）の対象にしない。
- AC-2 THE SYSTEM SHALL 下書きでない親の明細を凍結する規則（`saveLines` の draft 検査、`lockParents` の submitted / cancelled 検査）を document にだけ適用し、entity の明細は親の update 権限（と明細 entity の権限）があればいつでも変更できるようにする。IF 親の update 権限が無い THEN THE SYSTEM SHALL `PERMISSION_DENIED` を返し何も書かない。親が entity のときは、明細 entity への直接の書込み（`<line>.create` / `update` / `delete`、REST・MCP）も親を op `update` でロックする（親の create だけを持つロールが既存の親に明細を足せない）。document の親は従来どおり明細の作成で op `create` を使う。明細を持つ既存の document の振る舞い・API・画面は変えない。
- AC-3 WHEN `EntityMeta.lines` を持つ entity の記録画面を開いた THE SYSTEM SHALL document と同じ明細グリッド（`LineGrid`）を表示し、ヘッダと明細を 1 回の保存で送る。グリッドは要求者が更新できない場合に読取専用にする（docstatus による凍結は document だけ）。加えて定期仕訳では、按分（`kind = allocation`）で生成済みの回がある（`lastOccurrenceDate` が空でない）記録の明細グリッドを、理由「生成を始めた按分の明細は変更できません。複製して作り直してください」/ "Lines of an allocation that has started generating cannot be changed. Duplicate it to start over." つきで読取専用にする（`apps/web/src/lib/recurring.ts` の `recurringLineLock`、AC-8 のサーバー側の拒否はそのまま残す）。C2 の「複製」は明細も初期値に入れる（`lib/duplicate.ts` の既存の規則。entity の明細の場合も `duplicate.test.ts` で確かめる）。

### 定期仕訳のテンプレート

- AC-4 THE SYSTEM SHALL `modules/accounting` に `defineEntity` で `recurring_journal`（定期仕訳）を宣言する。field は `name`（名称、必須、100 字）、`description`（摘要、480 字。生成する仕訳の摘要）、`kind`（`fixed` 定額 / `allocation` 按分、既定 `fixed`）、`frequency`（`monthly` 毎月 / `quarterly` 3 か月ごと / `yearly` 毎年、既定 `monthly`）、`dayOfMonth`（1〜31、既定 31。31 = 月末、月の日数を超える日はその月の末日）、`startDate`（開始日、必須、既定は今日）、`endDate`（終了日、任意。この日より後の回は作らない）、`allocationPeriods`（按分回数 2〜120。按分のときだけ必須）、`isActive`（有効、既定 true）、`nextRunDate`（次回日付、serverOwned）、`lastOccurrenceDate`（最後に生成した回の日付、serverOwned）。明細 `recurring_journal_line`（`templateId` は親への ref で `onDelete: 'cascade'`、`seq`、`accountId` 必須、`debit` / `credit`（money、0 以上）、`partnerId`、`taxCategory`、`taxRate`、`memo`。`journal_line` の入力 field と同じ型・制約）を AC-1 の `lines` で持つ。明細 entity の権限は accounting に read / create / update / delete、viewer に read で、他のロールには与えず、`storeAccess` / `siteAccess` も宣言しない。会社 scope、監査は full（明細も）。権限は accounting に read / create / update / delete、viewer に read とし、sales・purchasing ほかのロールには与えない（admin は kernel の規則どおり全権）。`storeAccess` / `siteAccess` は宣言せず、拠点・店舗に限定された文脈からは使えない（`journal_entry` と同じ本社の業務）。一覧の列は名称・種類・周期・次回日付・有効・最後の生成日、検索は名称と摘要。ラベルと選択肢の文言は日本語と英語で持つ。
- AC-5 WHEN 定期仕訳を作成・更新した THE SYSTEM SHALL `nextRunDate` を、AC-6 の回の日付のうち「`startDate` 以後」「月が `lastOccurrenceDate` の月より後（空なら制限なし。1 か月に 2 回は作らない。生成後に日・開始日・周期を変えても、生成済みの月にもう 1 回できない）」「`endDate` 以前（空なら制限なし）」「按分なら `allocationPeriods` 回目以内」をすべて満たす最初の日付とし、無ければ空（終了）にする。IF 要求者が `nextRunDate` または `lastOccurrenceDate` を入力した THEN THE SYSTEM SHALL serverOwned への書込みとして `PERMISSION_DENIED` を返す（kernel の `assertOwnedInput`）。
- AC-6 THE SYSTEM SHALL 回の日付を次の規則で決める（純粋関数。時刻とタイムゾーンを使わない）。k = 0, 1, 2, … について、`startDate` の年月から k × 間隔（毎月 1、3 か月ごと 3、毎年 12）か月後の月の `dayOfMonth` 日（その月の日数を超えるときは末日）。`startDate` より前になる回は数えない（最初の回は `startDate` 以後の最初の該当日）。うるう年はグレゴリオ暦の規則（4 で割り切れる年。ただし 100 で割り切れて 400 で割り切れない年を除く）で 2 月を 29 日とする。按分の回番号（1 始まり）は `startDate` 以後の回を日付順に数えた番号とする。
- AC-7 THE SYSTEM SHALL 定期仕訳の検査を次の 2 種類に分ける。**ヘッダの規則**（明細を見ない）: `endDate` が空か `startDate` 以後（issue `endDate`）、按分なら `allocationPeriods` があり定額なら空（issue `allocationPeriods`）、按分の `endDate` が空か `allocationPeriods` 回目の日付以後（issue `endDate`）。**明細の規則**: 明細 2 行以上、各行は借方か貸方の一方だけが 0 より大きい、借方合計 = 貸方合計、取引先必須の勘定科目（`account.partnerRequired`）の行に取引先がある（`services/balance.ts` の `validateLines` と同じ）。按分では加えて、借方の行と貸方の行がちょうど 1 行ずつで金額が等しい（この金額が按分する総額）、総額が会社通貨の最小単位（JPY は 1 円）の桁で表せる、総額 ≥ 回数 × 最小単位。満たさなければ `VALIDATION` で保存全体を取り消す（明細の誤りは `lines.recurring_journal_line.<行>.<field>` の issue）。いつ何を検査するか: (1) 作成・更新のたびに `before_create` / `before_update` でヘッダの規則を検査する。(2) 明細つきの保存（`saveLines` を通る保存。画面の保存、`lines` つきの作成・更新）では `after_lines_saved` でヘッダと明細の両方の規則を検査する。(3) 明細を送らずにヘッダだけを更新し（`lines` の無い `recurring_journal.update`）、明細の規則に効く種類か按分回数を変えたときは、`before_update` で保存済みの明細に対して明細の規則も検査する（保存済みの明細が 1 行も無い定期仕訳は検査しない。名称・有効・日付だけの変更は明細の規則に効かないので検査しない）。(2) と (3) を区別するため、kernel は汎用の更新が `lines` を持つとき、ヘッダの更新の間も集約を置換中として印を付ける（`isSavingLines(ctx, 'recurring_journal', id)` が `before_update` で true。ADR-0031）。この印を読む既存の hook はすべて明細側の hook で、document のヘッダの hook の振る舞いは変わらない。例: 定額 → 按分への変更と明細を 3 行から借方 1 行・貸方 1 行に減らす変更を 1 回の保存で送ると、`before_update` はヘッダの規則だけを、`after_lines_saved` が新しい明細で全体を検査して保存できる（DB 試験）。明細なしの作成は明細の規則で検査しない（明細の無い定期仕訳は AC-12 の `invalid_template` で生成されない）。
- AC-8 WHILE 定期仕訳に生成済みの回がある（`lastOccurrenceDate` が空でない）THE SYSTEM SHALL 次の変更を `INVALID_STATE` で拒否し、「複製して新しい定期仕訳を作り、この定期仕訳は無効にしてください」というヒントを返す: 種類の変更、按分の定期仕訳の按分回数・周期・日・開始日・明細の変更。明細で凍結するのは行の集合（行の追加・削除）と各行の `accountId`・`debit`・`credit` で、`partnerId`・`taxCategory`・`taxRate`・`memo`・`seq`（並べ替え）と拡張 field は変更できる。`saveLines` と明細 entity への直接の書込みの両方に効き、値が変わらない書込み（金額は Decimal で比較）は拒否しない。定額の定期仕訳の周期・日・開始日・終了日・明細は変更でき、以後の回だけに効く（次回日付は AC-5 のとおり `lastOccurrenceDate` の月より後の月から求め直す。例: 2026-10-15 まで生成済みで日を 15 → 31 に変えると次回は 2026-11-30 で、10 月に 2 回目はできない）。名称・摘要・有効と、按分の終了日（AC-7 の範囲内）はいつでも変更できる。IF 生成済みの回がある定期仕訳を削除しようとした THEN THE SYSTEM SHALL `INVALID_STATE`（「無効にしてください」）で拒否する。

### 生成

- AC-9 WHEN `accounting.generate_recurring { asOf?, templateId? }` が呼ばれた THE SYSTEM SHALL 要求者の会社の有効な定期仕訳のうち次回日付が `asOf`（省略時は日本時間の今日）以前のもの（`templateId` があればその 1 件）を id の昇順に処理し、各定期仕訳の期日が来た回（回の日付 ≤ `asOf`）を日付の古い順に、1 回につき 1 本の下書きの仕訳にする。仕訳は、日付 = 回の日付、摘要 = 定期仕訳の摘要（空なら名称。按分では末尾に ` (k/N)`）、明細 = テンプレートの明細（勘定科目・借方/貸方・取引先・税区分・税率・メモ。按分の金額は AC-13）、拡張 field = ヘッダ・明細とも `postingDimensions` が写す共有の key だけ、起票元（`sourceEntity` / `sourceId`）と逆仕訳元は空とする。作成は要求者の `Context` のまま `Repository` と `saveLines` を通す（権限・監査・hook がそのまま効く）。回ごとに生成記録（AC-17）を書き、処理を終えた定期仕訳の `lastOccurrenceDate` を進めて `nextRunDate` を求め直す。応答は `{ asOf, autoSubmit, created, truncated, templates: [{ templateId, name, status, entries: [{ occurrenceDate, occurrenceNo, entryId, number, docstatus, amount }], nextRunDate, more, stop? }] }` で、`status` は `generated`（1 本以上作った）/ `up_to_date`（`templateId` を指定したが期日の来た回が無い）/ `blocked`（AC-11）/ `failed`（AC-12）/ `inactive`（AC-16）、`amount` は借方合計（下書きの `totalDebit` は確定まで 0 のため明細から求める）。action は REST（`POST /actions/accounting.generate_recurring`）と MCP の tool に既存の派生規則で出る。
- AC-10 WHEN `truncated: false` で終わった実行を同じ `asOf` でもう一度実行した THE SYSTEM SHALL 生成済みの（定期仕訳, 回の日付）の仕訳を 1 本も作らない。`blocked` / `failed` の定期仕訳は同じ止まった回とともに `created: 0` でもう一度報告する（次回日付がその回に留まっているため）。WHEN 2 つの実行が同時に走った THE SYSTEM SHALL （定期仕訳, 回の日付）ごとに仕訳をちょうど 1 本にし、どちらの実行も競合だけを理由に失敗させない（会社ごとの系列ロック `accounting-recurring` を取ってから対象を読み、定期仕訳を id 順に行ロックする。後の実行は先の実行の確定を待ってから対象を読むので、作るものが無ければ `created: 0` で成功する）。THE SYSTEM SHALL 生成記録の一意キー（`templateId`, `occurrenceDate`）により、ロックを通らない経路でも同じ回の 2 行目を DB が拒否するようにする（`CONFLICT`）。
- AC-11 IF 回の日付を含む会計期間が締め済み、その会計年度が締め済み、または回の日付を含む会計期間が無い THEN THE SYSTEM SHALL その回とその定期仕訳の後の回をこの実行では作らず、次回日付をその回に留め、`status: 'blocked'`、`stop: { occurrenceDate, reason: 'closed_period' | 'closed_year' | 'no_period', code: 'INVALID_STATE', message, hint, periodCode?, fiscalYearCode? }` を返す。同じ実行でそれより前の回に作った仕訳は残し、他の定期仕訳の処理は続ける。判定は `assertOpenPeriod`（`hooks/validate-entry.ts`）と同じ規則・同じ advisory lock（`accounting-periods`）で行い、生成の途中で期間が締められる競合を起こさない。
- AC-12 IF 回の作成（または AC-14 の確定）が業務エラー（kernel の `DaifukuError`: 検証・参照先の欠落・権限・状態など）で失敗した THEN THE SYSTEM SHALL その回だけを savepoint（`withSavepoint`）で取り消し、その定期仕訳の処理をそこで止め、`status: 'failed'`、`stop: { occurrenceDate, reason: 'error', code, message, hint?, issues? }` を返し、他の定期仕訳の処理は続ける。IF 処理の開始時にテンプレートが AC-7 の規則を満たさない（明細が無い場合を含む）THEN THE SYSTEM SHALL その定期仕訳では何も作らず、`status: 'failed'`、`stop.reason: 'invalid_template'`（issues つき）とする。業務エラーでない例外（DB 接続の失敗など）は実行全体を失敗させ、何も残さない。
- AC-13 THE SYSTEM SHALL 按分の各回の金額を、kernel の `Decimal` で（JS の number は使わない）、総額 T（≥ 0）・回数 N・会社通貨の小数桁 s（JPY は 0）について、1〜N−1 回目は T ÷ N を s 桁に 0 方向へ切り捨てた額 a（`Decimal.div(N).roundDown(s)`）、N 回目は T − a × (N − 1)（端数は最終回に寄せる）とし、借方の行と貸方の行の両方にその金額を入れる。回番号は AC-6 の番号で決まり、生成の履歴に依らない（同じ回は何度計算しても同じ額になる）。N 回目を生成したら次回日付は空になる。例: 100,000 円を 12 回 → 1〜11 回目 8,333 円、12 回目 8,337 円。
- AC-14 THE SYSTEM SHALL 会社設定 `accounting.recurring_auto_submit`（boolean、既定 false、`category: 'accounting'`、`order: 30`、日英のラベルと説明、`default: false` を宣言。ADR-0027 の表示属性）を登録する。WHEN 値が true THE SYSTEM SHALL 生成した仕訳をその回の savepoint の中で確定し（`submitDocument`。確定時の検査がそのまま効き、失敗は AC-12 のとおりその回を取り消す）、`docstatus: 1` と採番した番号を返す。WHEN false または未設定 THE SYSTEM SHALL 下書き（`docstatus: 0`、番号なし）のまま残す。下書きは回の日付の会計期間について、月次締めガイド（`accounting.close_readiness`）の仕訳の下書き件数（締めを止める項目）に数えられる（close_readiness は変更しない）。action の入力に確定の指定は設けない。
- AC-15 THE SYSTEM SHALL `accounting.generate_recurring` の権限を `{ entity: 'recurring_journal', op: 'update' }` とし、書込みの前に、要求者が `journal_entry` と `journal_line` を create でき、自動確定が on なら `journal_entry` を submit できることを確かめ、できなければ何も書かずに `PERMISSION_DENIED` を返す（出荷時のロールでは `recurring_journal` の update を持つ accounting と admin が仕訳の create / submit も持つため、この確認は多重防御で、純粋関数 `assertCanGenerate(ctx)` の単体試験で確かめる。DB 試験の対象にしない）。sales・purchasing・viewer のロールと、拠点・店舗に限定された文脈には `PERMISSION_DENIED` を返す。
- AC-16 THE SYSTEM SHALL 要求者の会社の定期仕訳だけを読み、仕訳と生成記録を要求者の会社に作る。別会社の定期仕訳・生成記録・生成した仕訳は読めず、変わらない。IF `templateId` が別会社の定期仕訳を指す THEN THE SYSTEM SHALL `NOT_FOUND` を返す。IF `templateId` の定期仕訳が無効 THEN THE SYSTEM SHALL 何も作らず `status: 'inactive'` を返す。
- AC-17 THE SYSTEM SHALL 生成した回ごとに生成記録 `recurring_journal_run`（`templateId`、`occurrenceDate`、`occurrenceNo`（按分の回番号。定額は空）、`entryId`。すべて serverOwned、一意キー（`templateId`, `occurrenceDate`）、`import: false`）を 1 行書く。生成記録は `accounting.generate_recurring` だけが書き、汎用の書込みはどのロール（admin を含む）でも何も書かずに拒否する: create は server-owned の field を送れば kernel の field 所有の検査（`assertOwnedInput`）で `PERMISSION_DENIED`、送らなければ必須の field が無いため `VALIDATION` で、どちらも hook より前に止まる（`before_create` の拒否は多重防御）。update / delete は hook が `INVALID_STATE` で拒否する。権限は accounting に read / create、viewer に read とする（ロールの create は kernel の権限検査のためで、hook が生成処理の中の module 専用の書込み権（create だけを許す。生成の中でも update / delete は通さない）を持つ書込みだけを通す。`contract_billing` と同じ形）。WHEN 生成した下書きの仕訳を削除した THE SYSTEM SHALL 生成記録を残して `entryId` を空にし（`onDelete: 'set null'`）、その回を再び作らない（削除 = その回を飛ばす）。THE SYSTEM SHALL 確定した生成仕訳を手入力の仕訳と同じに扱い、`accounting.reverse_entry` で逆仕訳できるようにする（起票元を持たないため）。
- AC-18 THE SYSTEM SHALL 1 回の呼出しで作る仕訳を 200 本までとし、上限に達したらそこで止めて `truncated: true` を返し、期日の来た回が残る定期仕訳に `more: true` を付ける（まだ処理していない定期仕訳は応答に含めない）。もう一度呼べば続きから作る。
- AC-19 IF `asOf` が実在する `YYYY-MM-DD` の日付でない、または `templateId` が UUID でない THEN THE SYSTEM SHALL `VALIDATION` を返し何も書かない。
- AC-20 WHEN 仕訳を 1 本生成した THE SYSTEM SHALL 業務イベント `recurring_journal.generated`（`templateId`、`occurrenceDate`、`occurrenceNo`、`entryId`、`submitted`）をその回の savepoint の中で出す（回を取り消したらイベントも残らない）。

## データ・業務ルール（出典）

- 締めた期間・年度の日付で仕訳を転記できないこと、会計期間が無い日付の扱い — 既存の [accounting 仕様](accounting.md) AC-10 と `assertOpenPeriod`。生成は下書きでも同じ規則で止める（AC-11）。新しい制度値は無い。
- 回の日付の規則（31 = 月末、月の日数を超える日は末日）— 制度ではなく製品の規則。契約の `contract.billingDay`（[contract 仕様](contract.md)、`modules/contract/src/services/periods.ts` の `END_OF_MONTH`）と同じ表し方にそろえる。
- 按分の端数処理（最小単位への切捨て、端数は最終回）— 制度ではなく製品の規則（AC-13）。会社の会計方針で別の配り方をする場合は定額の定期仕訳を回ごとに分けて登録する。
- 短期前払費用（法人税基本通達 2-2-14）と課税仕入れの時期（消費税法基本通達 11-3-1 の原則と 11-3-8 の例外）— [日本の制度事実](../domain/japan-tax.md#prepaid-expense)。**【未確認】**: この環境から国税庁のサイトに接続できず、通達本文を取得していない（2026-10-30、検索結果の抜粋と解説記事のみ）。システムはこの規則を判定しない（明細の税区分はテンプレートの値をそのまま写す）。マニュアル 05 は「支払の行と毎月の振替の行のどちらか一方だけに課税仕入れの税区分を付ける（両方に付けると消費税集計表で二重に数える）。どちらに付けるかは短期前払費用の取扱いを適用するかによるので税理士に確認する」という中立の注意だけを書き、特例の適用可否は断定しない（原則は消費税法基本通達 11-3-1 の役務の提供を受けた日）。実装セッションで一次資料に接続できたら本文を確認して `docs/domain` の【未確認】を外す。

## 決定事項（計画が選択を残した点。理由つき）

1. **テンプレートは `defineEntity`、明細は DSL の拡張（ADR-0031）で持つ。** 計画と作業指示が entity（`isActive` で止める、いつでも直せるマスタ）を求めている。kernel の明細（`lines`）は document 専用で、entity は明細を持てない。採らなかった案: (a) document にする（`contract` やレシピと同じ）— 金額を直すたびに取消 → 訂正が必要で、訂正版は id が変わるため回の重複防止を版をまたいで引き継ぐ仕組み（系列 id）が別に要る。(b) 明細を別 entity にして汎用フォームで 1 行ずつ作る — ヘッダと明細が別保存になり、汎用フォームで明細を編集できない（計画の「汎用の一覧・フォーム」を満たさない）。(c) json field — 汎用フォームが JSON の入力欄になり、勘定科目の参照整合性も失う。entity の明細は「置換保存・親のロックと版・500 行・`after_lines_saved`」を document と共有し、凍結だけを document に残す小さな拡張で、マスタ（レシピのようなもの）にも使える。ADR 番号は 0031（0027〜0029 は使用済み・予約済み、0030 は同じ round の B6 opening-balances）。
2. **重複防止は生成記録 `recurring_journal_run` の一意キー＋系列ロック＋行ロック。仕訳 entity は変えない。** 仕訳の `sourceEntity` / `sourceId` に定期仕訳を入れる案は採らない: 起票元を持つ仕訳は `accounting.reverse_entry` が単独の逆仕訳を拒否する（「起票元の業務操作で取り消す」）ため、定期仕訳から作った仕訳を普通の仕訳として逆仕訳できなくなる。生成記録は `contract_billing`（契約請求の履歴）と同じ形で、汎用の書込みを hook で拒否する。
3. **次回日付はカーソル（`lastOccurrenceDate` から導出）。下書きを削除してもその回は作り直さない。** 契約は「下書きの請求書を削除すると対象月が再び請求対象になる」が、仕訳の下書きは直接直せるので、削除は「その回は要らない」という意思として扱う。生成記録は `entryId` を空にして残し、なぜ作られないかを後から追える。特定の回の作り直し・巻き戻しは提供しない（未決事項 1）。
4. **日の指定は `dayOfMonth` 1〜31（31 = 月末）で、3 か月ごと・毎年は開始日の月を起点にする。** 契約の `billingDay` と同じ表し方で、月末の扱いを 1 つの field で表せる。週次・営業日の前倒しは範囲外。
5. **締めた期間に当たったら、その定期仕訳はその回で止める（後の回を飛ばして先へ進まない）。** 回を飛ばすと未払計上・按分が黙って欠ける。止まった回と理由・ヒントを定期仕訳ごとに返し、他の定期仕訳は続ける。回ごとの savepoint（kernel の `withSavepoint`。契約の生成を書いた時点では無かった port）で、失敗した回だけを取り消す。
6. **按分は借方 1 行・貸方 1 行に限り、端数は切捨てで最終回に寄せる。回番号は日付の順番で決める。** 複数行を行ごとに按分すると各回の貸借が一致しないことがある（例: 借方 1 円・1 円、貸方 2 円を 2 回に按分すると、1 回目は借方 0 円・0 円、貸方 1 円になる）。回番号を生成の履歴ではなく日付から決めるので、同じ回は常に同じ額になる。按分の定期仕訳は生成を始めたら周期・回数・明細を変えられない（複製して作り直す）。
7. **自動確定は会社設定だけで決め、action の入力では選ばせない。** 契約の生成は呼出しごとに `submit` を指定できるが、定期仕訳の確定は「誰が仕訳を承認するか」という会社の方針で、画面・受信箱・MCP のどこから呼んでも同じに動くべきため。確定は回ごとの savepoint の中で行い、確定できない回は下書きも残さない。
8. **権限は `recurring_journal` の update で絞り、書込み前に仕訳の create（と submit）を確かめる。** 仕訳の create を持つ sales・purchasing（起票元からの転記のため）が定期仕訳を回せないようにする。拠点・店舗限定の文脈は `journal_entry` と同じく使えない。
9. **予定の action `accounting.recurring_schedule` を足し、生成と同じ純粋関数で状態を出す。** 「下書きを作り、人が確認して確定する」流れの前に、何が作られ、どこで止まるかを見せるため（候補一覧の「`contract.schedule` の考え方」）。`TableResult` なのでレポート画面からも開ける。
10. **実行画面は専用画面 `/finance/recurring` にする（汎用の `/a/:action` は使わない）。** 汎用の操作画面は業界テンプレート向けの戻り先と JSON の結果表示で、定期仕訳ごとの結果とリンクを示せない。月次締めガイドと同じく「会計・資金」の専用画面にし、受信箱の行き先にする。
11. **有効フラグの名前は `isActive`。** 同じ module の `account.isActive` / `fiscal_period.isClosed` にそろえる（計画の「active」）。
12. **1 回の呼出しは 200 本まで。** 開始日を過去にした定期仕訳で大量の下書きが一度にできるのを防ぎ、要求の時間を抑える。会計期間が無い日付は AC-11 で止まるので、遠い未来の `asOf` も会計年度を開いた範囲までしか作らない。

13. **spec 査読（critic）の指摘への対応（実装セッション、2026-10-30）。** 採用: (1) ヘッダと明細を 1 回で送る更新の検査 — 案 (a) の kernel の印（`lines` つきの汎用更新はヘッダ更新の間も置換中）を採り、ヘッダの規則と明細の規則を分けて AC-7 に書いた。(2) 生成後に日・開始日・周期を変えた定額で同じ月に 2 回目ができる問題 — 次回日付は「月が `lastOccurrenceDate` の月より後」とした（AC-5、AC-8）。全周期の間隔は 1 か月以上なので月で比べれば十分で、規則を変えない限り従来の「日付が後」と同じになる。(3) AC-10 の言い回し — 打切りなしの再実行と `blocked` / `failed` の再報告に直した。(4) entity の親への直接の明細書込みは親の update でロック（AC-2）。(5) 按分の凍結する明細の field を列挙し、グリッドを理由つきで読取専用にする（AC-3、AC-8）。(6) 止まった理由とヒントは画面が日英に変換し、サーバーの英語の文言は技術情報にだけ出す（AC-21、AC-23）。(7) `endDate` ≥ `startDate` のヘッダの規則（AC-7）。(8) 仕訳の create / submit の事前確認は出荷時のロールでは失敗しないため、多重防御として単体試験で確かめる（AC-15）。(9) 通達 11-3-1（課税仕入れを行った日の原則）を `docs/domain` に足し、マニュアルの注意を中立の文言にした。国税庁への接続は今回も拒否された（proxy 403、2026-10-30）ため【未確認】のまま。11-3-1 は検索結果で第 11 章第 3 節（`11/03.htm`）にあると分かったので、指摘の `11/01.htm` ではなくそちらを出典にした。法人税基本通達 2-2-14 の国税庁の本文 URL は検索で特定できず、二次情報のまま。(10) 按分の計算の Decimal と丸め方向（AC-13）。(11) 検証の抜け（viewer の説明、entity の明細の複製、新しい会社の fixture）。(12) 明細 entity の権限を明記し、AC-21 を削る順番の先頭にした。不採用: なし。ADR 番号は B6 が 0030 を使うため 0031 に変えた。

14. **実装で決めたこと（2026-10-30）。** (1) AC-7 (3) のヘッダだけの更新で明細の規則を検査するのは、明細の規則に効く種類・按分回数を変えたときに限った。明細の無い定期仕訳（CSV 取込でヘッダだけ作ったものなど）の名称を変えるたびに「明細 2 行以上」で拒否されるのを避けるため。周期・日・開始日・終了日は明細の規則に効かず、ヘッダの規則（`endDate` と N 回目の日付など）は毎回検査する。(2) 生成の応答の定期仕訳ごとの結果に `kind` を足した（画面が按分向けの助言を選ぶため）。(3) 予定の列に英語の技術情報 `detail` を足し、理由は `reason` のコードだけにした（画面が日英に変換する）。(4) 移行は `apps/api/drizzle/migrations/0019_recurring_journals.sql`（3 表）。(5) `recurring_journal_run.entryId` の `set null` は単独の外部キーで働き、会社の範囲の複合外部キー（NO ACTION、MATCH SIMPLE）は `entryId` が空になった行を検査しない（DB 試験で下書きの削除を確かめた）。(6) 明細 entity への直接の書込み（`recurring_journal_line.create` / `update` / `delete`。REST と MCP の tool にも出る）では AC-7 の明細の規則を検査しない（AC-8 の凍結だけは効く）。1 行ずつ作る途中は必ず「明細 2 行以上」「貸借一致」を満たさないため、行ごとに検査すると直接の書込みで明細を組み立てられなくなる。不正な明細のままの定期仕訳は生成で `invalid_template`（AC-12）として止まり、予定（AC-21）にも出る。明細はヘッダと一緒に `lines` で送るのが正（画面・`recurring_journal.update`）。(7) AC-17 の汎用 create は hook に届く前に kernel の検査で止まる（文言を実装に合わせて直した。2026-10-30 のレビュー指摘）。生成の書込み権は create だけを許すので、hook の update / delete の拒否は生成の中でも効く。DB 試験は登録された hook を直接呼んで、生成の外では create も拒否し、書込み権の中では create だけを通すことを確かめる。(8) AC-25 の検査で、記録画面の監査ログの表（`components/audit-panel.tsx`、全 entity 共通）の横スクロール枠が、中に焦点を受ける要素が無いのに Tab で止まらず、390px で axe の `scrollable-region-focusable`（serious）になることが分かった。`docs/conventions/ui.md` の規則どおり枠に `tabIndex=0`・`role="region"`・`aria-label` を付けて直した（定期仕訳だけでなく既存の記録画面すべてに効く）。

## 未決事項（利用者の判断待ち）

1. 特定の回の作り直し・飛ばしの操作を設けるか。推奨の既定: 設けない。下書きを削除した回は作り直さず（決定 3）、要るときは仕訳を手入力するか、仕訳の一覧から別の回の仕訳を開いて「複製」（C2）する。
