## 目的（1段落）

従業員経費は今、本人申請 → 拠点の承認 → 給与・精算本部の「精算記録」（精算日と参照番号の手入力）で終わり、支払・仕訳は会計側で別に手入力している（[workforce-platform](workforce-platform.md) AC-5、[マニュアル付録F](../manual/appendix-f-workforce.md)「この操作による銀行送信・会計仕訳の自動作成はありません」）。また、法人カードで払った経費や仮払金で払った経費を区別できない。本項目では、本人が経費ごとに支払方法（立替・法人カード・仮払金）を示し、承認は既存の workforce の確認待ちのまま、経理担当者が承認済みの経費から精算書を作って確定すると、仕訳（費用・仮払消費税と未払金・仮払金）と支払（入出金）を同じトランザクションで作る。仮払金は精算書で消し込み、差額を支払うか返金を受ける。経理担当者と給与・精算本部（多くの中小企業では同じ人）が使う。

## 受入基準（EARS）

### 申請と承認（workforce）

- AC-1 WHEN 従業員が `workforce.save_expense` で経費を保存した THE SYSTEM SHALL 入力 `paymentMethod`（`personal` / `corporate_card` / `advance`、省略時 `personal`）を `workforce_expense.paymentMethod` に保存し、`my_portal` / `management_portal` の経費（`expenseSummary`）に返す。支払方法は他の項目と同じく下書き・差戻し中だけ変更でき、提出後は凍結される。既存の経費は追加 migration で `personal` になる。
- AC-2 THE SYSTEM SHALL 精算書に入れられる経費を `approved` のものに限る（承認は既存の `workforce.review_expense`。本人以外が承認）。WHEN 精算書が確定した THE SYSTEM SHALL 含む経費を `settled` にし、`paidOn` = 精算日、`paymentReference` = 精算書番号、`settledBy` = 確定した利用者を記録する。その経費は `workforce.todo` の `expense_settlement`（精算待ち）から外れ、本人の `/me` に精算済みと精算書番号が出る。`workforce.todo` の項目・件数の規則は変えない。

### 精算書の作成（下書き）

- AC-3 WHEN `expense.draft_settlement { employeeId, kind, expenseIds?, advanceId?, partnerId?, date? }` が呼ばれた THE SYSTEM SHALL 指定の経費（省略時はその従業員の、種類に対応する支払方法の、他の取消されていない精算書に入っていない承認済み経費の全部。最大 200 件）から精算書の下書きを 1 枚作り、`{ id, version }` を返す。明細は経費 1 件につき 1 行で（`expenseIds` に同じ id が 2 回あれば `ValidationError`「duplicate expense id」）、勘定科目は `expense.accounts.defaultExpense` の科目、税区分はその科目の `taxCategoryDefault`（無ければ `standard`）、支払先名・請求書区分は空にする。`date` の省略時は今日（日本時間）、`partnerId` の省略時は種類 `advance` なら仮払の取引先、それ以外はその従業員の同じ種類の直近の確定済み精算書の取引先（無ければ空）。経費の拠点が複数にまたがる指定は拒否する（拠点ごとに 1 枚）。IF 候補の経費が 1 件も無い THEN THE SYSTEM SHALL `ValidationError` を返し、空の下書きを作らない（例外: 種類 `advance` で `advanceId` を指定した場合は明細 0 行の下書きを作る。D24）。作成は workforce の従業員のロックの中で行い（D28）、同じ経費を明示した 2 回目の呼出しは AC-4 の `Conflict` になる。
- AC-4 WHEN 精算書の明細が保存された THE SYSTEM SHALL 従業員のロックの中で（D28） 明細の経費が存在し要求者から読め、精算書と同じ従業員・同じ拠点で、`approved` で、支払方法が種類に対応することを検査し、満たさなければ `ValidationError`（`details.issues` に行と理由）を返す。IF 経費が取消されていない別の精算書に入っている THEN THE SYSTEM SHALL `Conflict`（その精算書の id を `details` に含める）を返す。明細の利用日・内容は経費から写し（server-owned）、要求者は変更できない。
- AC-5 WHEN 精算書の下書きが保存された（明細の保存を含む）THE SYSTEM SHALL D7 の規則で明細ごとの税率・税額・控除対象税額・控除対象外税額・控除率（server-owned）と、ヘッダの税抜合計・税額合計・控除対象税額・控除対象外税額・合計・税率別集計（`taxSummary`）を再計算する。請求書区分 `invoiceKind` は課税の税区分（`standard` / `reduced`）の明細で使い、`qualified`（適格請求書等あり。登録番号 `T`+13 桁が必須、控除率 1）、`not_qualified`（区分記載請求書等あり。控除率は利用日の経過措置の率）、`books_only`（帳簿のみ保存の特例。理由 `booksOnlyReason` = `public_transport` / `business_travel` / `vending_machine` / `collected_ticket` が必須、控除率 1）、`small_amount`（少額特例、控除率 1）、`none`（書類なし、控除率 0）のいずれか（D21）。登録番号は `qualified`、理由は `books_only` のときだけ保存し、他の区分では空にする。丸め: 経費 × 税率ごとに `tax.rounding` の方法で 1 回、控除対象税額は `splitTax`（同じ方法）、行への配分は D7 の切捨て（どの行の税額・控除対象税額・控除対象外税額も負にならない）。税区分が `exempt` / `non_taxable` / `out_of_scope` の明細では請求書区分・理由・登録番号を空として扱い、税額 0 とする。金額は `Decimal`（JPY は 1 円単位、0 より大きい）。
- AC-6 IF 確定時に次のいずれかを満たさない THEN THE SYSTEM SHALL `ValidationError`（項目と理由）を返し、何も書かない: 明細が 1 行以上（種類 `advance` は 0 行を許す。D24）、従業員のロックの中で全明細が AC-4 の条件（同じ従業員・同じ拠点・`approved`・支払方法が種類に対応・取消されていない別の精算書に入っていない）を満たす、経費ごとの明細金額の合計が経費の金額と等しい、課税明細の請求書区分・必要な登録番号・理由・支払先名がそろっている、同じ経費の明細の請求書区分・登録番号が同じ、取引先 `partnerId` がある、精算日が今日（日本時間）以前で含む経費の利用日以降、支払が生じる場合（AC-7）に支払方法 `method` と入出金口座 `paymentAccountId`（省略時は `payment.accounts` の方法別の既定）がある、会社の通貨が JPY。種類 `advance` では `advanceId` が同じ従業員の確定済み・未精算（`open`）の仮払で、仮払の支払日が精算日以前、精算書の取引先が仮払の取引先と同じ。種類 `advance` 以外では `advanceId` が空。

### 確定（submit）

- AC-7 WHEN 精算書を確定した THE SYSTEM SHALL 同じトランザクションで、(1) accounting の `postFromSource`（`sourceEntity = 'expense_settlement'`）で精算書の仕訳を作って確定し、(2) 種類と金額から決まる入出金を payment の `createClearingPayment` で作って確定し（立替精算: 支払・合計額・相手科目 未払金。仮払精算: 合計 > 仮払額なら差額の支払・相手科目 未払金、合計 < 仮払額なら差額の入金・相手科目 仮払金、等しければ作らない。法人カード精算: 作らない）、(3) 含む経費を精算済みにし（AC-2）、(4) 仮払を `settled` にし、(5) `journalEntryId` / `paymentId` と番号（`EXP-<年>-<連番>`、ADR-0006）を記録する。仕訳の摘要と入出金の備考には精算書番号と従業員名を入れる。仕訳と入出金の日付は精算日、税率と控除率は明細の利用日で引く（D20）。明細 0 行の仮払精算は (1) を行わず（`journalEntryId` は空）、仮払額の全額の入金（相手科目 仮払金）を作る（D24）。
- AC-8 THE SYSTEM SHALL 精算書の仕訳を次の形で作る（ゼロの行は作らない。golden で固定）: 借方 費用科目（明細の科目 × 税区分 × 税率ごとに税抜額。税区分・税率を付ける）、借方 仮払消費税（税率ごとに控除対象税額。税区分・税率と摘要「仮払消費税 <税率名>」）、借方 費用科目（科目ごとに控除対象外税額。摘要「控除対象外消費税」）、貸方 未払金（立替精算・法人カード精算は合計、仮払精算は合計が仮払額を超える部分）、貸方 仮払金（仮払精算の min(合計, 仮払額)）。貸方の行には取引先を付ける。借方合計 = 貸方合計 = 合計。入出金の仕訳は payment の規則で作り、相手科目付きの支払は 借方 相手科目 / 貸方 入出金口座、入金は 借方 入出金口座 / 貸方 相手科目（いずれも取引先付き）とする。

  例（golden の 1 件目。JP 勘定科目表、`tax.rounding` 既定の切捨て、標準 10%・軽減 8%）: 立替精算で、経費 A 2026-10-05 3,300 円（旅費交通費 6500、標準、`qualified`）、経費 B 2026-10-06 1,080 円（雑費 6900、軽減、`not_qualified`、経過措置 0.7）、経費 C 2026-10-07 550 円（旅費交通費 6500、標準、`books_only` / `public_transport`）。税額 A 300・B 80・C 50、控除対象 A 300・B 56（80 × 0.7 の切捨て）・C 50、控除対象外 B 24、合計 4,930 円。精算書の仕訳: 借方 6500 3,500（標準 10%）/ 借方 6900 1,000（軽減 8%）/ 借方 1500 350（標準 10%）/ 借方 1500 56（軽減 8%）/ 借方 6900 24（控除対象外消費税）/ 貸方 2150 4,930（従業員の取引先）。入出金（支払 4,930、相手科目 2150）の仕訳: 借方 2150 4,930 / 貸方 1100 4,930。同じ内容の経費（支払方法は種類に対応するもの）で、仮払 10,000 円の仮払精算なら 貸方 1800 4,930 と入金 5,070（借方 1100 / 貸方 1800）、仮払 3,000 円なら 貸方 1800 3,000・貸方 2150 1,930 と支払 1,930（借方 2150 / 貸方 1100）。法人カード精算なら 貸方 2150 4,930（カード会社）で入出金なし。仮払金の科目は 1800（D13）。

  golden の 2 件目以降（D7・D20・D21）: (a) 標準の 1,000 円の領収書 2 件は税額 90 + 90 = 180（精算書全体で丸めた 181 ではない）。(b) 3,300 円の領収書 1 件を 1,000 円と 2,300 円の 2 行に分けると税額 90 / 210。(c) 標準 1,030 円の `not_qualified` は税額 93・控除対象 65・控除対象外 28（利用日 2026-10-05、70%）。(d) 利用日 2026-09-30 の `not_qualified` 1,080 円（軽減）を精算日 2026-10-01 で精算すると控除率 0.8（税額 80・控除対象 64・控除対象外 16）で、仕訳の日付は 2026-10-01。(e) `tax.rounding` が `up` のとき標準 1,000 円は税額 91。(f) `none` の標準 1,100 円は税額 100・控除対象 0・控除対象外 100。(g) 明細 0 行の仮払精算（仮払 10,000 円）は精算書の仕訳なしで入金 10,000（借方 1100 / 貸方 1800）。

- AC-9 IF 確定の途中のどこかが失敗した（入出金の拒否、会計期間が締め済み、勘定科目が存在しない、経費が並行して精算された、仮払が並行して消し込まれた、など）THEN THE SYSTEM SHALL すべてを巻き戻し、精算書の仕訳・入出金・入出金の仕訳を残さず、経費を `approved`、仮払を `open`、精算書を下書きのままにする。
- AC-10 WHEN 同じ経費を含む 2 枚の精算書（下書きの検査を通った後の並行操作を含む）や、手動の `workforce.settle_expense` と精算書の確定が競合した THE SYSTEM SHALL 1 つだけを成功させ、他方を `StateError` または `Conflict` で失敗させる（AC-9 の巻戻しを伴う）。同じ仮払を 2 枚の精算書で消し込むことも同様に 1 つだけ成功させる。

### 確定後の不変・取消・訂正

- AC-11 WHILE 精算書が確定済み THE SYSTEM SHALL ヘッダ（`journalEntryId` / `paymentId` を除く）・明細の変更と削除を拒否し、変更は取消 + 訂正だけとする。WHEN 確定済みの精算書を取り消した（任意の訂正日 `correctionDate` 付き）THE SYSTEM SHALL 同じトランザクションで精算書の仕訳を逆仕訳し（`reverseSourceEntry`、訂正日または元の日付）、入出金を同じ訂正日で取り消し（入出金の仕訳も逆仕訳される。D20）、`paymentReference` がその精算書番号の経費だけを `approved` に戻し（`paidOn` / `paymentReference` / `settledBy` を空にする）、仮払を `open` に戻す。IF 入出金が銀行照合済み（banking の照合が有効）THEN THE SYSTEM SHALL 取消を `StateError`（照合を先に取り消す）で拒否し、逆仕訳・経費・仮払を含めて何も変えない（精算書は確定済みのまま）。WHEN 取消済みの精算書を訂正（amend）した THE SYSTEM SHALL 明細の入力項目を写した新しい下書きを作り、確定すると新しい仕訳・入出金を作る。
- AC-12 IF 確定済みの精算書・仮払が参照している入出金を入出金の画面・API から直接取り消そうとした、または確定済みの精算書が参照している仮払を取り消そうとした THEN THE SYSTEM SHALL kernel の `DependencyError` で拒否する（取消は精算書・仮払の取消から行う）。

### 仮払

- AC-13 WHEN 仮払 `expense_advance`（従業員、取引先、支払日、金額、目的、支払方法、入出金口座）を確定した THE SYSTEM SHALL 同じトランザクションで `createClearingPayment`（支払・相手科目 仮払金）を作って確定し（仕訳は入出金の転記: 借方 仮払金 / 貸方 入出金口座）、`paymentId` と状態 `open` を記録する。番号は `ADV-<年>-<連番>`。WHEN `open` の仮払を取り消した THE SYSTEM SHALL 同じ訂正日で入出金を取り消す（銀行照合済みなら AC-11 と同じく `StateError` で何も変えない）。IF 仮払が `settled` THEN THE SYSTEM SHALL 取消を拒否する（精算書を先に取り消す）。金額は 0 より大きい 1 円単位、支払日は今日以前。

### 入出金の拡張（payment）

- AC-14 THE SYSTEM SHALL `payment.counterAccountId`（相手科目、`account` への参照）を server-owned とし、汎用の作成・更新（REST・MCP・画面）で送られたら `PERMISSION_DENIED` を返す。`createClearingPayment(ctx, { direction, partnerId, date, amount, method, accountId?, counterAccountId, note? })` は要求者の `Context` のまま入出金を作って確定し（direction とロールの既存の検査、`payment` の create / submit 権限が必要）、相手科目が会社の資産または負債の科目で、税の役割（`taxRole`）を持たず、入出金口座（`accountId`）と違うことを検査する（満たさなければ `ValidationError`）。相手科目付きの入出金は `allocatedAmount = 0`・`unallocatedAmount = 0` とし（D22）、`payment.todo` の `unallocated_payments` と締めガイドの `unallocated_payments` に数えられない。IF 相手科目付きの入出金に消込明細がある THEN THE SYSTEM SHALL 保存と確定を `ValidationError` で拒否する。IF 訂正元（`amendedFrom`）が相手科目付きの入出金である下書きを更新または確定した THEN THE SYSTEM SHALL `StateError`（精算書・仮払を取消・訂正する）で拒否する（D23）。相手科目が空の入出金の転記（前払金・前受金）・検査・既存の試験の期待は変えない。

### 権限と境界

- AC-15 IF 精算書・仮払の作成・更新・確定・取消・訂正、または `expense.draft_settlement` / `expense.settlement_candidates` を、`accounting` と `workforce_payroll` の両方（または admin）を持たない利用者が行った THEN THE SYSTEM SHALL 書き込む前（読取 action では読む前）に `PERMISSION_DENIED` を返す。action の `permission` はロールの OR しか表せないため、action と entity の権限は `accounting` に与え、`workforce_payroll` は hook・handler の冒頭で検査する。accounting を持ち workforce_payroll を持たない利用者への拒否は `details.op` = `<op>:requires-workforce_payroll`（`<op>` は `create` / `update` / `delete` / `submit` / `cancel` / `candidates`）、accounting を持たない利用者への拒否は kernel の通常の `details.op`（`create` など）とする（D26）。IF 精算書・仮払の従業員が要求者本人（admin を含む）THEN THE SYSTEM SHALL 作成・更新・削除・確定・取消・訂正（明細の保存・削除と、別の担当者が作った下書きを含む）を `PERMISSION_DENIED`（`details.op` = `<op>:self-settlement`。明細は `update:self-settlement`、削除は `delete:self-settlement`）で拒否する。
- AC-16 THE SYSTEM SHALL `workforce_employee` には自分の精算書・明細・仮払だけを読ませ（行の権限 `userId = $ctx.userId`）、他人の記録は一覧・取得・関連記録のいずれにも現れない（取得は NOT_FOUND。従業員には export 権限を与えないので CSV 出力もできない）。拠点を限定された `workforce_manager` には担当拠点の精算書・仮払だけを読ませる（`siteAccess`）。拠点を限定された文脈から他拠点の従業員の精算書を作ることはできない。`expense.settlement_candidates` と `expense.draft_settlement` は拠点を限定された文脈では実行できず（`siteAccess: false`、`PERMISSION_DENIED`）、`expense.todo` は拠点を限定された文脈の受信箱の呼出しを失敗させない（D25。実装時の決定 I2: 確定できない文脈には提供元が `/meta` に出ず、受信箱は呼ばない）。拠点・店舗を限定された文脈は精算書・仮払を確定・取消・訂正できない（kernel の規則、`PERMISSION_DENIED`）。
- AC-17 THE SYSTEM SHALL 会社をまたいで精算書・仮払・明細を読ませない（id 指定の取得は `NOT_FOUND`、一覧には現れない）。他社の取引先・勘定科目・仮払をヘッダに、他社の経費を明細に指定した保存は `VALIDATION`（取引先・科目・仮払は kernel の参照の整合性、経費は明細の検査）、他社の従業員を指定した `expense.draft_settlement` は `NOT_FOUND` を返す。他社の仕訳・入出金・経費は変化しない。

### 受信箱・設定・導入チェック

- AC-18 THE SYSTEM SHALL 受信箱の提供元 `expense.todo`（[inbox](inbox.md) AC-1 の規約、`mutates: false`、`tx: 'none'`）で、`draft_settlements`（warn: 「確定待ちの経費精算書」。下書きの精算書で従業員が要求者でないもの。href `/e/expense_settlement?status=draft`）と `open_advances`（info: 確定済み・`open` の仮払。href `/finance/expenses`）を、要求者の `Context` の `Repository` で数えて返す。提供元を実行できるのは精算書の `submit` 権限を持つ利用者（`permission: { entity: 'expense_settlement', op: 'submit' }`、つまり accounting と admin）で、`workforce_payroll` を持たない要求者には項目を返さない（`{ items: [] }`。処理できない項目は数えない [inbox](inbox.md) AC-1。提供元の失敗にはしない）。
- AC-19 THE SYSTEM SHALL 会社設定 `expense.accounts`（`advance` 既定 `1800`、`payable` 既定 `2150`、`defaultExpense` 既定 `6900`）を設定画面の「会計」に勘定科目コードの入力欄付きで表示する（[ADR-0027](../adr/0027-setting-presentation.md) の表示属性）。導入チェック `expense.accounts`（id 固定、order 55）は、`expense.accounts` の 3 つのコードと `purchase.accounts.taxReceivable` のコードの科目が会社に無いとき `warn` と href（`expense.accounts` のコードが欠けていれば `/settings?tab=accounting`、仮払消費税だけなら `/settings?tab=purchase`）を返し、そろっていれば `ok` を返す。確定時に科目が欠けていれば `resolveExpenseAccounts` が欠けたコードを列挙した `StateError` を返す。l10n/jp の勘定科目表は新しい会社に `1800 仮払金` を作る。

### 画面

- AC-20 WHEN `expense.settlement_candidates` を実行できる利用者が `/finance/expenses` を開いた THE SYSTEM SHALL 承認済みで精算書に入っていない経費を従業員 × 支払方法 × 拠点でまとめ、件数・合計・最も古い利用日と、下書きの精算書に入っている経費の件数、従業員ごとの未精算の仮払を表示する。各まとまりの「精算書を作成」で `expense.draft_settlement` を呼び（200 件を超えるまとまりは利用日の古い 200 件で、その旨を表示する）、作られた精算書の画面（`/e/expense_settlement/<id>`）へ移動する。作成中はそのボタンを「作成中…」にして live region で知らせる。失敗は ui-kit の失敗表示（メッセージ・技術情報・再試行）で示し、候補を読み直す。再試行は読み直した候補から要求を作り直し、権限の拒否（`<op>:self-settlement` は自己精算の説明、それ以外は必要なロールの説明）とまとまりが無くなった場合は再試行を出さない。要求者本人の経費のまとまり・仮払（出力の `self: true`）と、未精算の仮払が無い従業員の仮払精算のまとまりには作成の操作を出さず、理由を表示する。画面は「会計・資金」分野の専用画面として、meta に `expense.settlement_candidates` がある利用者（accounting と admin）の画面検索・分野一覧に出す。IF サーバーが `PERMISSION_DENIED` で `details.op` が `candidates:requires-workforce_payroll` の拒否を返した、または URL を直接開いた利用者に権限が無い THEN THE SYSTEM SHALL 読込失敗ではなく、必要なロール（accounting と workforce_payroll）を説明する。「この画面の説明」はマニュアルの章を開く。
- AC-21 THE SYSTEM SHALL 精算書・仮払の汎用画面で、ラベル付きの節（基本・支払・金額・転記・備考）、明細の表（経費・利用日・内容・支払先名・勘定科目・税区分・金額・請求書区分・理由・登録番号と、計算された税額・控除対象税額は読取専用）、確定・取消・訂正の操作、関連記録（仕訳・入出金・仮払・経費・訂正の連鎖）と証憑パネル（attachments）を表示する。
- AC-22 WHEN 従業員が `/me` で経費を記録・編集した THE SYSTEM SHALL 支払方法（立替・法人カード・仮払金から支払）を選ばせ、一覧と詳細に支払方法を表示する。精算済みの経費には精算日と精算書番号を表示する。`/workforce` の経費の承認済みの行には、`expense.settlement_candidates` を実行できる利用者に `/finance/expenses` への移動を表示する。
- AC-23 THE SYSTEM SHALL 追加・変更した画面の文言を日本語と英語で持ち、390px 幅で横スクロールなしに操作でき、`/finance/expenses` に axe の serious / critical の違反を出さない。

## データ・業務ルール（出典）

- 端数処理は 1 適格請求書（ここでは 1 経費 = 1 領収書）につき税率ごとに 1 回 — [japan-tax.md#rounding](../domain/japan-tax.md#rounding)（国税庁 Q&A 問57、確認 2026-09-10）。税率は期間付きの `tax_rate`（ADR-0011）。
- 適格請求書・適格簡易請求書と登録番号（`T` + 13 桁）— [japan-tax.md#インボイス制度](../domain/japan-tax.md#インボイス制度)（タックスアンサー No.6625、Q&A 問24-2・問58、確認 2026-09-10）。登録番号の公表サイトでの照合はしない。
- 免税事業者等からの課税仕入れの経過措置（2026-10-01〜2028-09-30 は 70%）— 同上（令和8年度改正、Q&A 問113、再確認 2026-09-10）。率は `l10n/jp/src/services/transitional-credit.ts` の期間付きデータを purchase の上書き点経由で使う。1 億円/年の上限は purchase と同じく範囲外。
- 帳簿のみの保存で控除できる取引（公共交通機関・出張旅費等・自動販売機等・回収される入場券等）と少額特例 — [japan-tax.md#books-only](../domain/japan-tax.md#books-only)、[#small-amount-relief](../domain/japan-tax.md#small-amount-relief) **【未確認】**（2026-10-30、一次資料に接続できず）。経過措置の書類の条件 — [#transitional-documents](../domain/japan-tax.md#transitional-documents) **【未確認】**。仕入税額控除の時期 — [#input-tax-timing](../domain/japan-tax.md#input-tax-timing) **【未確認】**。システムは判定せず、経理担当者が選んだ区分と理由を記録し、控除率 1 とする。理由の名前・説明文は一次資料で確認するまで「未確認」の扱いを manual に明記する。
- 帳簿の記載事項（相手方・年月日・内容・軽減の旨・税率ごとの金額）— [japan-tax.md#input-tax-books](../domain/japan-tax.md#input-tax-books) **【未確認】**。
- 控除対象外の税額を費用科目に含める・仮払消費税の科目 — [purchase](purchase.md) AC-2/AC-3 と同じ。
- 仮払金・未払金の処理は簿記の慣行 **【未確認: 一次出典なし】**（[japan-tax.md#expense-settlement](../domain/japan-tax.md#expense-settlement)）。
- 確定済み伝票の不変・取消 + 訂正 — ADR-0006。仕訳の追記専用 — ADR-0005。module 所有の書込 — ADR-0016。

- 多段の承認経路、承認者の金額別の振り分け。
- 分析データセット（`apps/api/src/analytics/catalog.ts` の従業員経費）への支払方法の追加。
- 費目（`workforce_expense.category` の文字列）から勘定科目への自動対応（未決事項）。

## 実装時に確かめる前提（コードを読んで置いた推定。結果をこの spec に書き戻す）

- 伝票の確定 hook の中で別の伝票を確定・取消できる（入れ子の lifecycle）。前例: payment の `before_submit` が `postFromSource` 経由で `journal_entry` を確定している。精算書の `after_submit` から入出金の `submitDocument`、`after_cancel` から入出金の `cancelDocument` を呼ぶ。
- kernel の `findDependents`（`kernel/src/document.ts`）は確定済み document の `ref` だけを数える。精算書の `paymentId`・`advanceId` と仮払の `paymentId` が AC-12 の拒否を生み、取消済みの精算書は入出金の取消を止めない。仮払から精算書への `ref` は持たない（持つと精算書の取消が止まる）。
- `siteAccess: { kind: 'store' }` の document で、hook が導いた server-owned の `siteId` が作成時に要求者の拠点の範囲で検査される（AC-16 の最後の文）。検査されない場合は hook で明示的に検査する。
- 明細の `before_validate` は全置換保存で行ごとに走り、ヘッダの再計算は `after_lines_saved` で 1 回行う（payment の `hooks/validate.ts` と同じ）。経費ごとの合計の検査は途中の状態を見るため確定時だけにする（AC-6）。
- 入出金の確定時の `assertDirectionRole` と `postFromSource` は、精算書の確定者（accounting）の `Context` のまま通る。
