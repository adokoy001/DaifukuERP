# Spec: print-templates（帳票の共通化と拡充）

- 状態: implemented（2026-10-30。作業記録 [2026-10-30-print-templates](../log/2026-10-30-print-templates.md)）
- モジュール: 新規 `modules/print-layout`（package `@daifuku/mod-print-layout`。`defineModule` を持たない純粋関数のライブラリ。会社設定 `print_layout.date_style` は利用する module の `hooks` が冪等な `ensurePrintLayoutSettings()` で登録する）、`modules/sales`、`modules/trade`、`modules/payment`、`modules/workforce`、`l10n/jp`、`kernel`（action DSL の `print` 宣言と `/meta`）、`apps/web`（印刷ボタン） ／ 依存: [company-admin](company-admin.md)（B2 の `resolveIssuer` と `company.profile`）、[settings-console](settings-console.md)（設定の表示属性）、[ui-kit](ui-kit.md)、[document-links](document-links.md)（記録画面のヘッダ）

## 目的（1段落）

紙や PDF で取引先・従業員へ渡す書類のうち、今は売上請求書（適格請求書）しか印刷できない。見積書・注文書・納品書・領収書・支払通知書・合計請求書・給与明細を、記録の画面から同じ操作で開いて印刷できるようにする。各 module は自分の document を自分の権限で読み、共通の部品（発行者・宛先・明細表・税率別内訳・合計・備考・日付表記・エスケープ）で HTML を組み立てる。画面は `/meta` の宣言を読んでボタンを出すだけにし、帳票ごとの対応表を Web に持たない。

## 受入基準（EARS）

### 規約と発見

- AC-1 THE SYSTEM SHALL 帳票 action を名前 `<module>.render_<document>_html`、`tx: 'none'`、`mutates: false`、出力 `{ html: string }` とし、`defineAction` の任意の宣言 `print: { entity, label, idInput?, when?, fields? }` で「どの entity の記録画面に、どの入力 property へ記録の id を渡して出すか」を宣言する。`idInput` の既定は `'id'`、`when` は記録の field 値（文字列・数値・真偽）との等値条件の AND、`fields` は `idInput` 以外の入力 property の日英のラベルと説明（`{ label: Label; description?: Label }`、入力ダイアログの表示用）。IF `print` を持つ action の名前が規約に合わない、`mutates` が true、`tx` が `'required'`、`internal` が true、入力が `idInput` を property に持つ zod object でない、または `fields` のキーが `idInput` 以外の入力 property でない THEN THE SYSTEM SHALL 定義時に Error を投げる（開発時の誤り）。entity の登録前に走る `defineAction` では確かめられない「`print.entity` が登録済み、`when` のキーがその entity の field、`idInput` の property が uuid の文字列」は、runtime の全 action を走査する単体試験で確かめる。
- AC-2 WHEN `/meta` が要求された THE SYSTEM SHALL 要求者が実行できる action の宣言を `actions[].print`（`{ entity, label, idInput, when, fields }`、`idInput` は既定値を補い、`when`・`fields` は宣言にあるときだけ）として返す。実行できない action は従来どおり `/meta` に出さない。
- AC-3 WHEN 利用者が記録の画面（`/e/:entity/:id`）を開いた THE SYSTEM SHALL `print.entity` がその entity で、`inputSchema.properties` に `idInput` があり、`when` が記録の値とすべて一致し、entity が document なら記録が確定済み（docstatus 1）である action ごとに、宣言の `label` の印刷ボタンを `/meta` の順に出す。module 名と接尾辞 `render_invoice_html` から推測する従来の発見（`PRINT_ACTION_SUFFIX`）はやめ、`sales.render_invoice_html` に `print: { entity: 'sales_invoice', label: 請求書を表示 }` を付けて同じ画面に同じボタン（`data-testid="print-button"`）を出す。各ボタンは `data-print-action=<action 名>` を持つ。2026-10-30 統合時の追記: 期首請求書（[opening-balances](opening-balances.md) AC-20）に出さないため、請求書の宣言は `when: { openingBalance: false }` を持つ（D-16）。
- AC-4 WHEN 印刷ボタンを押した THE SYSTEM SHALL クリックの処理内で新しいタブを同期的に開き、`POST /actions/<name>` に `{ [idInput]: 記録の id, ...追加入力 }` を送り、返った HTML に既存の印刷・閉じるバー（`withPrintBar`、紙には出ない）を付けてそのタブに表示する。WHEN action の入力に `idInput` 以外の property がある THE SYSTEM SHALL 先に入力ダイアログ（`inputSchema` から `SchemaFields` で生成し、`print.fields` を設定画面と同じ表示属性（presentation）として渡して日英のラベルと補助文を出す。必須項目は必須）を開き、ダイアログの「表示」の押下で同じ手順を行う。IF ポップアップが拒否された THEN THE SYSTEM SHALL トースト `popupBlocked` を出す。IF action が失敗した、または `html` が返らない THEN THE SYSTEM SHALL 開いたタブを閉じ、API エラーまたは `printNoHtml` をトーストで出す。IF ダイアログの入力が VALIDATION で拒否された THEN THE SYSTEM SHALL ダイアログを閉じずに該当項目の下へエラーを出す（文言は日英併記。D-15）。WHEN 描画の途中でダイアログが閉じられた、または画面を離れた THE SYSTEM SHALL 開いたタブに結果を表示する（失敗ならタブを閉じてトースト）。

### 共通レイアウト

- AC-5 THE SYSTEM SHALL 共通レイアウトを `@daifuku/mod-print-layout` の公開 index から import できる純粋関数（DB・時刻・registry・fs を読まない）として提供する: `escapeHtml`、`formatMoney`、`formatRate`、`formatDocumentDate`、`issuerBlock`（名称・登録番号・郵便番号・住所・電話・メール）、`addresseeBlock`（宛先と敬称）、`lineTable`（明細表。軽減税率対象の行に ※）、`taxBreakdownTable`（税率ごとの対価の額・消費税額・税込額）、`totalsTable`、`remarksSection`（備考・振込先・但し書きなど見出し付きの文）、`statusBanner`、`printDocument`（`<!DOCTYPE html>`、`lang`、`<title>`、`viewport`、A4 の `@page` を持つ完全な HTML 文書）。部品は inline style を持ち、断片としても文書としても使える。mod-print-layout は kernel 以外に依存せず、税区分の表示名（`TAX_CATEGORY_LABELS` など mod-tax の名称）と税率の表示は呼び出し側の module が行や内訳に入れて渡す。sales の既定請求書レイアウト `defaultInvoiceHtml` はこれらの部品で組み立て、既存の単体・DB テストの期待（断片 `<article class="invoice" lang="…">`、ISO 日付、文言、エスケープ）を変更せずに満たす。`@daifuku/mod-sales` は `escapeHtml`・`formatMoney`・`formatRate` を mod-print-layout から再 export して公開 API を保ち、`modules/sales/src/services/render-html.ts` も `escapeHtml`・`formatMoney`・`formatRate`・`REDUCED_MARK`・`defaultInvoiceHtml`・`InvoiceRenderData` を引き続き export する（既存の `recalculate.test.ts` がこのファイルから import するため。必要なものは再 export）。
- AC-6 THE SYSTEM SHALL 帳票に出す記録・設定・取引先・従業員に由来する文字列をすべて HTML エスケープし（`& < > " '`）、帳票の HTML に `<script>`、外部資源（`src=`、`href=`、`url(`、`<link`）、イベント属性（`on…=`）を含めない。
- AC-7 THE SYSTEM SHALL 金額・数量・税率・税率別内訳を保存済みの値（Decimal 文字列）から桁区切りだけを付けて表示し、税額の計算・端数処理・税率の引き直しを行わない。複数の保存値の合計（合計請求書の合計と税率別合計、納品書の税率区分ごとの税抜合計）は Decimal の加算だけで求める。WHEN 確定後に税率マスタや端数処理の設定が変わった THE SYSTEM SHALL 印刷される金額を変えない。
- AC-8 THE SYSTEM SHALL 会社設定 `print_layout.date_style`（`western` | `japanese_era` | `both`、既定 `both`、設定画面の「会社」タブ、値ごとに日英のラベル）で帳票の日付表記を切り替える。`western` は日本語 `2026年10月30日`・英語 `2026-10-30`、`japanese_era` は `令和8年10月30日`、`both` は `2026年10月30日（令和8年10月30日）`（英語は `2026-10-30（令和8年10月30日）`）。和暦への変換は l10n/jp が登録する差し替え点 `print_layout.era_date`（`toWareki`）で行い、IF 差し替えが登録されていない、または変換できない日付 THEN THE SYSTEM SHALL 西暦で表示する。この設定は新しい帳票（見積書・注文書・納品書・領収書・支払通知書・合計請求書・給与明細）に適用し、売上請求書（sales の既定レイアウトと l10n/jp のレイアウト）の日付表記はこの項目では変えない（D-4。`InvoiceRenderData` に field を足さない）。
- AC-9 THE SYSTEM SHALL 発行者を、取引の帳票（見積書・注文書・納品書・領収書・支払通知書・合計請求書）では B2 の `resolveIssuer`（`sales.issuer` を保存していればその全体、無ければ `company.profile`、無ければ会社名）で決め、登録番号は売り手として出す見積書・納品書・領収書・合計請求書だけに出し、買い手として出す注文書・支払通知書には出さない（D-3）。給与明細では `company.profile`（正式名称、無ければ会社名・郵便番号・住所・電話。登録番号と振込先は出さない）で決める。`company.profile` から発行者を組み立てる処理は mod-print-layout の `issuerFromCompanyProfile` 1 つにまとめ、`resolveIssuer` の代替経路もそれを使う（B2 の `modules/sales/test/issuer.test.ts` は変更なしで通る）。振込先（`bankInfo`）は請求書（従来どおり）と合計請求書だけに出す。新しい帳票の発行者は印刷時点の設定から作る（発行時データは保存しない。請求書の `issuedSnapshot` は従来どおり）。

### 各帳票

- AC-10 WHEN `trade.render_quotation_html { id }` が呼ばれた THE SYSTEM SHALL 見積書として、見積番号・見積日（`date`）・有効期限（`validUntil`）、宛先（取引時名称 `partnerName`、無ければ取引先名。郵便番号・住所は取引先マスタ）、発行者、御見積金額（`total`）、明細（行番号・品名・数量と単位 `uomCode`・税抜単価・税抜金額・税区分と税率）、税率別内訳（`taxSummary`）、税抜合計・消費税額・合計（`subtotal`・`taxTotal`・`total`）、※の凡例、備考（`note`）を出す。
- AC-11 WHEN `trade.render_order_html { id }` が発注（direction `purchase`）に対して呼ばれた THE SYSTEM SHALL 注文書として、注文番号・注文日・希望納期（`requiredDate`）、宛先（仕入先）、発行者、注文金額（`total`）と AC-10 と同じ明細・内訳・合計・備考を出す。IF 受注（direction `sales`）の id THEN THE SYSTEM SHALL INVALID_STATE を返す（ヒント: 注文請書は対象外）。
- AC-12 WHEN `trade.render_delivery_note_html { id }` が出荷（direction `sales`）に対して呼ばれた THE SYSTEM SHALL 納品書として、納品番号・納品日（`date`）・受注番号（`orderId` の受発注書の `number`）、宛先（得意先）、発行者、明細（行番号・品名・数量と単位・税抜単価・税抜金額・税区分の名称と軽減税率対象の ※。税率の % は出さない。受発注書の `taxSummary` は受注日に計算した見込みで、納品日の率と違うことがあるため）、税区分ごとの税抜合計と総合計（明細の保存値の加算）、注記「消費税額は請求書に記載します」、※の凡例、備考を出す。消費税額と倉庫は出さない。IF 入荷（direction `purchase`）の id THEN THE SYSTEM SHALL INVALID_STATE を返す。
- AC-13 WHEN `payment.render_receipt_html { id }` が入金（direction `receive`）に対して呼ばれた THE SYSTEM SHALL 領収書として、番号・領収日（`date`）・金額（`amount`）・受領方法（現金・振込・その他）、宛先（取引先）、発行者（登録番号を保存していれば表示）、内訳として消込明細（売上請求書の番号・請求日・消込額 `payment_allocation.amount`）と未消込額（`unallocatedAmount`、前受金）、備考を出す。税率別内訳、収入印紙欄、印紙税の注記は出さない（未決事項 1）。IF 支払（direction `pay`）の id THEN THE SYSTEM SHALL INVALID_STATE を返す（ヒント: 支払通知書 `payment.render_payment_notice_html`）。IF 下書き（docstatus 0）の入金 THEN THE SYSTEM SHALL INVALID_STATE を返す（記録前のお金の領収書を渡せないようにする。D-7）。
- AC-14 WHEN `payment.render_payment_notice_html { id }` が支払（direction `pay`）に対して呼ばれた THE SYSTEM SHALL 支払通知書として、番号・支払日・支払金額・支払方法、宛先（仕入先）、発行者、内訳（仕入請求書の番号・先方請求書番号 `supplierInvoiceNo`・請求日・支払額）と未消込額（前払金）、備考を出す。IF 入金（direction `receive`）の id THEN THE SYSTEM SHALL INVALID_STATE を返す（ヒント: 領収書）。IF 下書きの支払 THEN THE SYSTEM SHALL INVALID_STATE を返す（D-7）。
- AC-15 WHEN `sales.render_statement_html { partnerId, closingDate? }` が呼ばれた THE SYSTEM SHALL 合計請求書として、取引先の締め日 `closingDay`（31 は月末）で決まる期間 =（前回締め日, `closingDate`]（前回締め日は前月の同じ締め日を月の日数で丸めた日。`closingDateOf(請求日, closingDay) === closingDate` と同じ集合）に請求日がある、その取引先の確定済み（docstatus 1）売上請求書を請求日・番号の順に 1 行ずつ（請求日・請求書番号・支払期日・税抜金額 `subtotal`・消費税額 `taxTotal`・税込金額 `total`）並べ、税率別内訳（各請求書の `taxSummary` を区分と税率ごとに加算。※ は付けない）、合計（各列の加算）、見出しの金額「当期ご請求額合計（税込） / Total of invoices this period」（税込金額の合計。入金済みかどうかを問わない）、固定の注記「入金済みの請求書を含みます / Includes invoices already paid」と「各請求書（適格請求書）の合計です / Summary of the listed qualified invoices」、締め日・対象期間・発行日（今日、日本時間）、すべての請求書の支払期日が同じときだけお支払期限、発行者（登録番号を含む）と振込先を出す。取消（docstatus 2）と下書きは含めない。期首請求書（`openingBalance = true`）も含めない（2026-10-30 統合時に追加、D-16）。対象が 0 件なら「この期間の確定済みの請求書はありません」と合計 0 を出す。WHEN `closingDate` が省略された THE SYSTEM SHALL 今日（日本時間）以前で最も新しい締め日を使う。IF `closingDate` がその取引先の締め日でない THEN THE SYSTEM SHALL VALIDATION（path `closingDate`）を返し、ヒントに直前と直後の締め日を示す。WHEN `closingDate` が今日（日本時間）より後の締め日である THE SYSTEM SHALL 期間途中の請求書を集めて描画し、本文の先頭に「締め前（期間途中） / Period not yet closed」の帯（`role="status"`）を入れる。IF 取引先が得意先でない（`isCustomer` が false） THEN THE SYSTEM SHALL INVALID_STATE を返す（API・MCP からの呼出しも同じ。画面の `when` は表示条件にすぎない）。IF 対象が 500 件を超える THEN THE SYSTEM SHALL INVALID_STATE を返す。
- AC-16 WHEN `workforce.render_payslip_html { id }` が確定済みの給与に対して呼ばれた THE SYSTEM SHALL 給与明細として、番号・対象月（日本語 `2026年10月分`、英語 `2026-10`）・計算期間（`periodStart`〜`periodEnd`）、宛先（従業員名・従業員コード・所属拠点名）、発行者（会社）、支給（通常賃金 `basePay`・割増賃金 `premiumPay`・手当の各行 `allowances`・総支給額 `grossPay`）、控除（`deductions` の 8 区分の名称と金額・控除合計 `deductionTotal`）、差引支給額 `netPay`、勤怠（労働時間 時:分、有給取得日数 `paidLeaveDays`）を出す。計算根拠（`calculation`、各控除・手当の根拠文）は出さない。IF 下書き（docstatus 0）の給与 THEN THE SYSTEM SHALL INVALID_STATE を返す（未確認の控除を含むため）。
- AC-17 WHEN 下書きの見積書・注文書を action で描画した THE SYSTEM SHALL 本文の先頭に「下書き（未確定） / DRAFT」の帯（`role="status"`）を入れる（出荷 `trade_fulfillment` は `trade.fulfill_order` が作成と確定を 1 つの transaction で行い、下書きが存在しないため、納品書の下書きの帯は共通部品の単体試験だけで確かめる。領収書・支払通知書・給与明細の下書きは AC-13・AC-14・AC-16 のとおり拒否する）。WHEN 取消済み（docstatus 2）の見積書・注文書・納品書・領収書・支払通知書・給与明細を描画した THE SYSTEM SHALL 請求書と同じ「取消済み / CANCELLED」の帯を入れる（合計請求書は確定済みの請求書だけを集めるため帯を持たない）。帯は差し替え後のレイアウトにも action が入れる（`<body>` の直後、無ければ先頭）。
- AC-18 THE SYSTEM SHALL 帳票の固定文言を日本語と英語で持ち、要求の `ctx.locale` で切り替える（宛先の敬称 `御中`、給与明細の `様` は日本語だけに付ける）。

### 権限と境界

- AC-19 THE SYSTEM SHALL 帳票 action の権限を `permission: { entity: <対象 entity>, op: 'read' }`（合計請求書は `sales_invoice` の read）とし、対象の記録と付随して読む記録（取引先、受発注書、消込先の請求書、従業員、拠点）をすべて要求者の `Context` のまま `repo()` で読む（`systemContext()` や権限を外す経路を使わない）。行の権限・会社・拠点・本人の境界と field の mask はそのまま適用する。IF 対象を読めない THEN THE SYSTEM SHALL PERMISSION_DENIED（read の無いロール）または NOT_FOUND（行の権限・別会社・存在しない id）を返す。IF 付随する記録を読めない THEN THE SYSTEM SHALL repository のエラー（NOT_FOUND または PERMISSION_DENIED）をそのまま返し、一部だけの HTML を返さない（描画は全ての読取の後に行う）。
- AC-20 IF read 権限の無いロール（例: purchasing が見積書、ロール無しの利用者が入出金）が帳票 action を呼んだ THEN THE SYSTEM SHALL PERMISSION_DENIED を返し、そのロールの `/meta` にその action を出さない（印刷ボタンも出ない）。行の権限により、sales ロールは支払（pay）の入出金と発注の受発注書を、purchasing ロールは入金（receive）の入出金と出荷を印刷できない（NOT_FOUND）。
- AC-21 THE SYSTEM SHALL 取引の帳票（sales・trade・payment の action）に `storeAccess` / `siteAccess` を宣言せず、店舗・拠点に限定された文脈からの呼出しを PERMISSION_DENIED とする（請求書と同じ）。給与明細の action は `siteAccess: true` とし、workforce の行の権限に従う: workforce_employee・manager・hr ロールは自分の確定済みの明細だけ、workforce_payroll ロールは会社内の確定済みの明細を印刷でき、他人の明細と別会社の明細は NOT_FOUND、本人ロールから見た自分の下書きは NOT_FOUND（行の権限で見えない）とする。
- AC-22 THE SYSTEM SHALL 合計請求書に、要求者の有効な会社に属し、指定の取引先を得意先とする確定済み売上請求書だけを含め、別の取引先・別会社・下書き・取消・期間外の請求書を含めない。IF `partnerId` が別会社の取引先または存在しない THEN THE SYSTEM SHALL NOT_FOUND を返す。

### 画面

- AC-23 WHEN 確定済みの見積書・発注の受発注書・出荷・入出金・給与の記録画面を開いた THE SYSTEM SHALL 該当する印刷ボタンを出す（入出金は区分により領収書か支払通知書のどちらか一方、受注と入荷には出さない）。WHEN 得意先（`isCustomer`）の取引先画面を開いた THE SYSTEM SHALL 「合計請求書を表示」を出し、押すと締め日の入力ダイアログ（空欄なら直近の締め日を使う旨の説明付き）を開く。
- AC-24 WHEN `/me` の給与明細タブ、または `/workforce` の給与タブで確定済みの明細を表示した THE SYSTEM SHALL `/meta` に `workforce.render_payslip_html` がある利用者に「給与明細を表示」を出し、AC-4 の手順で新しいタブに開く。下書き・取消の明細には出さない。
- AC-25 THE SYSTEM SHALL 印刷ボタンとダイアログの文言を日本語と英語で持ち、390px 幅で記録画面とダイアログを横スクロールなしに操作でき、ダイアログを開いた画面が axe の serious / critical 違反を出さない（[e2e-a11y](e2e-a11y.md) の `judge()`）。帳票の HTML は `viewport` を持ち、390px 幅では明細表の枠の中だけを横スクロールにする。

## 設計

- 処理の流れ（帳票ごとに同じ）: action の handler が要求者の `Context` で記録を `repo()` から読み、表示用の `<Document>RenderData`（文字列・Decimal 文字列だけの素のデータ。`locale` を含む）を作る → `loadPrintTools(ctx)`（mod-print-layout。`getSetting` で `print_layout.date_style` を、`registry.override` で `print_layout.era_date` を読み、`formatDate(date)` を持つ `PrintTools` を返す。純粋でない唯一の関数）→ `registry.override('<module>.<document>_html', 既定の描画関数)` → `render(data, tools)` → 状態の帯（AC-17）→ `{ html }`。既定の描画関数は module の `services/*-html.ts` に置く純粋関数で、golden の対象。

## データ・業務ルール（出典）

- 適格請求書の記載事項（発行者の名称と登録番号 `T`+13 桁、税率ごとの対価の額と消費税額、軽減税率対象の明示）— [日本の制度事実](../domain/japan-tax.md#インボイス制度)（国税庁 タックスアンサー No.6625、確認 2026-09-10）。請求書のほか、見積書・納品書・領収書・合計請求書の発行者の登録番号の表示と、見積書・注文書の税率別内訳・※印に同じ出典を使う。新しい帳票が適格請求書であるとは表示しない（合計請求書は「各請求書（適格請求書）の合計です」と注記する）。
- 消費税の端数処理は 1 請求書につき税率ごとに 1 回 — [同](../domain/japan-tax.md#rounding)（Q&A 問57）。合計請求書に並ぶ各売上請求書がそれぞれ適格請求書で、端数処理はその請求書ごとに問57 のとおり済んでいる。合計請求書は保存済みの値を表示のために加算するだけで、合計請求書に端数処理の規則は適用しない（AC-7、AC-15）。Q&A 問67（納品書を丸めの単位とし請求書で合算する場合）は背景として参照するにとどめ、根拠にはしない。
- 締め日・支払サイト — [同](../domain/japan-tax.md#商習慣)。期間の決め方は `modules/partner/src/services/due-date.ts` の `closingDateOf` と同じ。
- 和暦: 内部は西暦、表示で変換。令和 = 2019-05-01〜 — [同](../domain/japan-tax.md#商習慣)、元号の開始日と出典（首相官邸、確認 2026-09-10）は `l10n/jp/src/services/wareki.ts`。
- 給与の閲覧範囲（本人は確定済み行だけ、管理者の別拠点制限）— [ADR-0019](../adr/0019-workforce-access.md)。
- 【未検証・印字しない】領収書の記載事項と印紙税（売上代金の受取書の課税・非課税の金額基準、収入印紙欄の要否）。この session から国税庁（www.nta.go.jp）へ接続できず（2026-10-30、ネットワークの許可外）、一次資料で確認できないため docs/domain に追加せず、領収書に該当の文言を出さない。給与等の支払明細書の交付義務と記載事項（所得税法第 231 条）も同じ理由で未確認とし、明細に法令の文言を出さない。

## 設計上の決定（計画が選択を残した点）

- D-1 印刷の対応は action 側の宣言 `print` に置く（entity 側ではない）。理由: 1 つの entity に複数の帳票がある（入出金の領収書と支払通知書）、entity を持たない module・pack・l10n が既存 entity の帳票を足せる、action は既に権限と入力 schema を持つ。Web の対応表は持たない。宣言と命名規約 `<module>.render_<document>_html` を `defineAction` で検査する。kernel DSL の後方互換な拡張なので ADR-0009 に追記し、新しい ADR 番号（ADR-0033）は使わない。
- D-2 共通レイアウトは新しい package `modules/print-layout`（kernel だけに依存）に置く。sales に置くと workforce（今は kernel だけに依存）が sales・accounting・tax・partner・product に依存してしまうため。`defineModule` は持たない（import で module が登録されると runtime と l10n/jp の module 一覧が変わり、一覧を完全一致で確かめる既存試験を書き換えることになるため。entity・action を持たないので module である必要もない）。設定の key の接頭辞は店舗機器の印刷ジョブ（edge の `print.text`）と区別するため `print_layout` とし、設定は kernel の `company.profile` と同じく冪等な `ensurePrintLayoutSettings()` で、利用する module の `hooks` から登録する。mod-tax にも依存しない（mod-tax を import すると税率 entity が登録され、workforce だけの構成に税の entity が入るため。税区分の名称は呼び出し側が渡す）。sales の公開 API（`escapeHtml` など）は再 export で保つ。
- D-3 発行者: 取引の帳票は B2 の `resolveIssuer`（sales が持つ `sales.issuer` を優先）。登録番号は売り手の書類（見積書・納品書・領収書・合計請求書）だけに出し、買い手として出す注文書・支払通知書には出さない（支払通知書の登録番号は通常、仕入明細書として相手方＝仕入先の番号と読まれるため、自社の番号はかえって誤解を招く。仕入明細書としての扱いはスコープ外）。給与明細は `company.profile` から作る（`sales.issuer` は請求書の名義・振込先の設定で、雇用主の表示には合わないため）。`company.profile` からの組み立ては 1 か所（`issuerFromCompanyProfile`）にする。
- D-4 日付表記は会社設定 `print_layout.date_style`（既定 `both`。l10n/jp の請求書の現在の表記と同じ）。元号の表は国の事情なので l10n/jp に残し、差し替え点 `print_layout.era_date` で使う。l10n/jp が無い構成では西暦になる。sales の既定請求書（l10n/jp が無いときだけ使われる）は ISO 日付のまま変えない。売上請求書（l10n/jp の適格請求書レイアウトを含む）の日付表記の切替はこの項目では行わない（発行済みの適格請求書の再印刷の見た目を変えるのは計画の範囲外。既定 `both` は l10n/jp の請求書の現在の表記と同じなので、既定の会社では帳票間の表記もそろう）。
- D-5 計画の entity 名の訂正: 支払通知書は `purchase_settlement` ではなく `payment`（direction `pay`）。`purchase_settlement` は番号・取引先・日付のまとまりを持たない、請求書ごとの append-only の消込事実（消込履歴）で、書類にならないため。注文書は `trade_order` の発注（direction `purchase`）、納品書は `trade_fulfillment` の出荷（direction `sales`）、見積書は `trade_quotation`（作成時に常に direction `sales`）、給与明細は `workforce_payroll`。
- D-6 「保存値から表示し再計算しない」の範囲: 税額の計算・丸め・税率の引き直しをしない。保存値どうしの加算（合計請求書の合計と税率別合計、納品書の税抜合計）は再計算にあたらないとして行う。納品書は出荷に税額が保存されていないため消費税額を出さない。
- D-7 下書き: 画面のボタンは確定済みだけに出す。見積書・注文書の action は下書きも「下書き（未確定）」の帯付きで描画する（請求書の下書きプレビューと揃え、MCP からの確認に使える）。お金の受渡しを示す領収書・支払通知書と、未確認の控除を含む給与明細は下書きを INVALID_STATE で拒否する（帯だけでは、記録前の入金の領収書を手渡す誤りを防げないため）。出荷は常に確定済みで作られる。
- D-8 合計請求書の `closingDate` は任意とし、省略時は今日以前の直近の締め日を使う（画面のダイアログが締め日の計算を Web に複製しないため）。指定された日が締め日でなければ VALIDATION。今日より後の締め日は、期間途中の確認に使えるよう拒否せず「締め前（期間途中）」の帯を付けて描画する。得意先でない取引先は INVALID_STATE。締め日は取引先の現在の `closingDay` を使う（売上請求書は締め日を保存していない。未決事項 6）。
- D-9 店舗・拠点に限定された文脈: 取引の帳票は請求書と同じく `storeAccess` / `siteAccess` を宣言しない（その文脈から売上・入出金の書類を出す業務が無い）。給与明細は workforce の他の action と同じく `siteAccess: true`。
- D-10 差し替え点は帳票ごとに `<module>.<document>_html`（既定の描画関数と同じ引数 `(data, tools)`）。l10n/jp の請求書レイアウトを共通部品へ置き換えることはこの項目では行わない（日付表記の切替だけ対応）。

## 未決事項（利用者の判断待ち）

1. 領収書の記載事項と印紙税の扱い（収入印紙欄・金額基準の注記）— 国税庁の一次資料を確認できなかったため印字しない（推奨の既定）。確認できたら docs/domain に URL と確認日を書き、`payment.receipt_html` の既定レイアウトか l10n/jp の差し替えで追加する。

3. 日付表記の既定値 — `both`（l10n/jp の請求書と同じ）を推奨。`western` にすると既存会社の新しい帳票は西暦だけになる。
4. 合計請求書の前回繰越・入金額 — 初版は期間内の請求書の一覧と合計だけ（推奨）。見出しは「当期ご請求額合計」とし、入金済みを含む旨を注記する（D-12）。入金・繰越の欄は消込履歴（`sales_settlement`）から作れるが、印刷時点で値が変わるため別項目で設計する。
5. 新しい帳票の発行時データ — 印刷時点の発行者・取引先住所を使う（推奨）。発行後に会社名・住所を変えると再印刷の内容が変わる。必要なら document ごとに snapshot の field を足す（移行を伴う）。
6. 締め日を変更した取引先の過去の合計請求書 — 現在の `closingDay` で期間を決める（推奨）。過去の期間を正確に再現するには売上請求書に締め日を保存する変更が要る。
7. 合計請求書の上限 500 件 — 1 取引先・1 締め期間で 500 件を超える場合は印刷できない（推奨のまま。必要ならページ分割を検討）。
8. 納品書の金額を出さない版 — 初版は金額あり（推奨）。取引先ごとの切替は設定の追加が要る。
9. 売上請求書の日付表記を `print_layout.date_style` に従わせるか — この項目では変えない（推奨。D-4）。発行済みの適格請求書の再印刷の見た目が変わるため、利用者の判断で別項目にする。
