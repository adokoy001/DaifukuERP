# 商流の分納・分割請求

状態: バックエンド実装・専用検証済み。画面・移行・統合 gate は親タスクで検証中。

## 範囲

商流を `trade` モジュールへ追加する。見積→受注→出荷→売上請求、発注→入荷→仕入請求を既存 sales / purchase / inventory へ接続する。JPY、税抜単価、固定在庫単位の物品を対象とし、数量は Decimal の小数6桁以内、原単価と明細金額は丸めず保持する。見積・注文の税額は当該日付の見込額で、実請求は請求日の既存税計算で確定する。

## 受入契約

- AC-1: 見積と受発注は通常の文書 API で下書き作成・明細保存・確定できる。確定時に品名・単位・税区分・税抜単価・取引先名を保存し、その後マスタ変更で原資料を変えない。
- AC-2: 確定見積の受注変換は原見積を参照し、二重変換を拒否する。後続受注がある見積は直接取消できない。
- AC-3: 受発注明細を指定した分納は、親注文ロック内で既確定数量を再集計し、超過・重複明細・別注文の明細を拒否する。入出庫は履行文書の確定時だけ発生する。
- AC-4: 履行明細から分割請求できる。既請求数量を親履行ロック内で再集計し超過を拒否する。生成請求は既存会計・消込・発行時スナップショットを使うが在庫を再計上しない。
- AC-5: 元参照・生成資料参照・計算項目は通常 CRUD から偽装できない。履行・商流請求は専用遷移だけが作成し、生成請求と在庫文書の独立取消・単独改訂確定を拒否する。履行・商流請求の取消も理由を伴う専用 action を利用する。
- AC-6: 請求取消は商流請求から実行し、入金残存時は既存請求の取消制約により全体をロールバックする。請求取消で未請求数量が復活し、在庫は保持する。履行取消は有効請求がなく、取消有効日が後続取消日以降の場合に限り在庫も反転する。
- AC-7: 注文の取消は後続履行を先に取り消す。残数打切りは理由必須で履歴を保持し、新規履行を拒否する。打切り後も既履行の未請求は請求でき、有効注文一覧に残す。異なる単位の数量をヘッダ KPI として加算しない。
- AC-8: requestId の再送は同内容なら同じ履行／請求を返し、内容差異は拒否する。会社・方向・明細参照・版番号・並行生成・直接明細編集を検証する。
- AC-9: 請求起点の従来業務は従来設定どおり在庫連携を維持する。商流の検証済み請求だけが別履行在庫を使用する。

## 非対応

サービス、外貨、単位換算、ロット・シリアル、引当、見込在庫、承認階層、返品・値引、運賃配賦、仕入価格差異、入荷時の未請求債務仕訳、三点照合自動判定は対象外。入荷は注文税抜単価で在庫評価する。会計は既存の請求時・三分法のままで、出荷・入荷だけでは総勘定元帳へ仕訳を作らない。実運用の検収や収益認識条件の自動判定は行わない。

## 検証

専用 DB で両方向の分納・分割請求・取消・短納終了・二重実行・並行超過・権限境界・在庫の二重計上防止を検証する。型・lint と既存請求／在庫回帰を統合 gate で照合する。UI は商流ボードと既存明細編集を利用する。

## 公開 API と運用上限

`@daifuku/mod-trade/contract` の `TradeBoard` / `TradeOrderDetail` / `TradeCommand` を公開契約とする。`trade.board` の `open` は有効な確定注文（残数打切りを含む）、`all` は下書き・取消を含む。明細ごとの数量と単位を表示し、注文・履行・請求の番号から原資料へ辿る。

専用操作は `convert_quotation` / `fulfill_order` / `bill_fulfillment` / `cancel_billing` / `cancel_fulfillment` / `close_order`。見積変換は受注下書きを作り、確認後に汎用確定する。生成文書の直接作成・変更・取消はできない。受注の通常改訂でも元見積を確定時に復元し、同じ見積の重複受注を拒否する。

1文書500明細、1操作500明細、一覧100注文／ページ。関連資料の取得は500件ずつページングし、各読込が1万件を超えたときは打切り値を成功扱いせず拒否する。本ボードは現在の運営照会であり、過去日残数を再現する `asOf` 帳票ではない。

同一注文／同一履行を取り消した後の再計上日は、その親に属する先行取消有効日以降とする。日付判定は既存の国内営業日（Asia/Tokyo）を使用し、履行と請求には未来日を許可しない。日次在庫の時系列・期間締め、請求の会計期間締めは既存基盤で再検証する。
