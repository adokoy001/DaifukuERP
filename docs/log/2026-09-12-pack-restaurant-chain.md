# 作業記録: 2026-09-12 飲食店チェーンの導入テンプレート

- 担当: apps_packs_review ／ 対象: `docs/specs/pack-restaurant-chain.md`
- 計測: tokens=null, agent_minutes=null, human_minutes=null, rework_lines=null, gate_failures=null（全体gateは統合担当）

## 決めたこと（と理由）

- 1法人の複数店舗を対象に、店舗厨房・確定レシピ・日次締め・店舗別集計の縦の流れを実装する。
- メニューはサービス、材料は物品とし、販売モジュールの完成品自動出庫との二重計上を防ぐ。
- 現金だけを即時入金にし、カード・QRは既存請求書の売掛残とする。実際の銀行入金を既存入出金で消し込める。
- 原価は在庫補助簿の移動平均原価。日次締めの売上原価仕訳、仕込み製造、POS、決済会社別債権／手数料、フランチャイズ、法人間連結は初版対象外と明記する。
- 店舗の倉庫・現金科目・店頭客を固定し、営業中の伝票を別店舗へ付け替えられないようにする。

## やったこと

- `packs/restaurant-chain` を新設。6エンティティ、日次集計action、submit/cancel/計算フック、必要範囲だけの非公開capabilityを追加。全依存はkernelと共通モジュールで、他packをimportしない。
- 税区分は提供方法＋酒類指定から決め、税込税計算は既存taxに委譲。レシピ単価補完、数量から材料出庫、廃棄の別出庫、期間締め後の訂正日伝播を実装。
- 同時の同店同日確定を会社単位のトランザクションロックで直列化。材料不足・不正内訳・権限不足・追加入金による取消失敗は全体をロールバック。
- 冪等seed/sampleを追加。sampleは二店舗・厨房・米／鶏肉・カレーメニュー・確定レシピのみで取引を作らず、既存設定・既存マスタを上書きしない。
- 手計算台本 `docs/domain/scenario-restaurant-chain.md` に導入手順・金額・在庫・後日入金・取消・役割・税根拠の一次資料URLと確認日を記載。

## 検証

- [実測] PG16の専用 `daifuku_review_restaurant`、公開action経路で11件通過。最終scenario 5件と、テスト入力／例外型修正後のguards 6件を確認。
- [実測] 通常 `pack.apply({sample:true})` / force省略で、会社の既存 `tax.price_includes_tax=false` を保全し、締め自身の税込計算が成立する。
- [実測] 二店舗計: 売上20800円、消費税1800円、現金14400円、カード5000円、QR1400円、材料消費原価3800円、廃棄50円。厨房別在庫残も一致。
- [実測] 後日入金6400円で売掛0円。追加入金の残る締めは取消できず、元の現金入金を含め全状態を保全。
- [実測] 二重締めの並行実行は成功1件のみ。serverOwned書換え・確定明細変更・使用済みレシピ取消・権限不足・別会社参照を拒否。
- [実測] 9月を閉期後、10月1日への取消が売上逆仕訳と逆在庫行まで伝わる。9月報告は元の20800円を維持し、10月に−16400円を計上。
- [実測] package typecheck、対象eslint、差分空白確認が通過。ログはrepo外 `review/restaurant-db-final.log`（scenario最終5件）と `review/restaurant-guards-final.log`（guards最終6件）。

## 見つけた問題と修正

- [テスト実測] fixtureの同名店舗／倉庫コードがID辞書で衝突したため、必要なエンティティだけを辞書に登録。
- [テスト実測] 更新actionの入力を正しい `patch` 契約へ修正し、入力エラーで凍結・所有者保護テストが偽陽性にならないよう、正の更新経路と具体的例外型も確認。
