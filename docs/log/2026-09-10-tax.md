## 決めたこと（と理由）
- **丸めは「税率ごとの合計」から1回**（AC-4、国税庁 Q&A 問57）。`summarizeTax` は明細の `computeLineTax` 結果を足すのではなく、(category, rate) ごとに `amount` を合計してから税額を1回計算・1回丸める。税込のときは `Σ税込 × rate ÷ (1 + rate)` を1回の除算で計算する。理由: 明細ごとに `amount ÷ 1.1` を先に計算して足すと、decimal.js（有効桁 40）の打切りで 1,100 → 99.999… になり、切捨てで 99 になる危険がある（実測で確認）。合計から1回の除算なら 1,100 × 0.1 ÷ 1.1 = 100 が厳密に出る。
- **`computeLineTax` は丸めない**（AC-3）。明細表示用。税込は `taxable = amount ÷ (1+rate)`, `tax = amount − taxable`（`taxable + tax = gross` が常に厳密）。
- **免税/非課税/不課税は常に率 0**（AC-2）。tax_rate 行があればその code/label、無ければ固定の fallback（EXEMPT/NONTAX/OOS）を返す。「行が無いとエラー」は standard/reduced のみ。理由: 課税されない区分に期間データを要求しても意味が無く、過去日付（2019-10 以前）でも解決できる方が sales/purchase に都合がよい。逆に、これらの区分の tax_rate 行に 0 以外の率を入れることはフックで拒否する。
- **重複期間の検出は before_validate フック**（AC-1）。create/update とも「previous + patch のマージ結果」を同 category の他行と比較（両端含む閉区間、validTo null = 無期限）。違反は `ValidationError`（`issues[0].path='validFrom'`, message と hint に相手の code）。`validTo < validFrom` も同フックで拒否。会社ごとに独立（repo の scope で自然にそうなる）。
- **税率行の追加は「既存行を閉じてから追加」**（AC-9）。RED1（軽減1%、2027-04-01〜）を入れるには RED8 の validTo を 2027-03-31 にしてから create する。順序を逆にすると重複エラー。コード変更は不要（DB テストと純粋関数テストの両方で確認）。
- **設定キー `tax.priceIncludesTax` → `tax.price_includes_tax` に変更**（spec AC-5 からの逸脱）。作業中に kernel に追加された `registry.registerSetting` がキーを `<module>.<name>`（snake_case）に制限しており、camelCase では登録できない。汎用設定 UI（/meta/settings）に載せる価値を優先し、格納キーは snake_case、TS 定数 `TAX_PRICE_INCLUDES_TAX_KEY` を export して呼び出し側はリテラルを書かない前提にした。アクションの入出力フィールド名は spec どおり `priceIncludesTax`。→ 判断待ち。
- **丸め桁は通貨から**: `taxScaleForCurrency(currency)` = JPY → 0、それ以外 → 2。通貨マスタが無いための暫定（ADR-0010「桁は通貨マスタ」）。
- **`tax.summarize` の出力には group ごとに `code`/`label`/`gross`/`lineCount` を付けた**（spec の `{category, rate, taxable, tax}` + α）。適格請求書の印字にそのまま使えるように。
- **権限**: tax_rate は accounting/settings が read/create/update、sales/purchasing/viewer は read（sales/purchase 伝票の検証時に `taxSummaryFor` が tax_rate を読むため）。delete は admin のみ（率の履歴は消さない）。`tax.set_settings` は `{ roles: ['settings'] }`（admin は暗黙に通る。kernel の `setSetting` も同じ条件を再確認する）。
- **シードは pre-2019 の標準 8%（STD8: 2014-04-01〜2019-09-30）を含む 6 行**。5% 以前は入れていない（spec 外。テストでは STD5 を追加して過去日付の解決を確認）。

## golden の手計算（test/golden/invoice-rounding.json、税率は STD10=0.10 / RED8=0.08）
- **invoice 1（税抜）**: 10%: 1,234 + 567 + 89 = 1,890 → 189.0 → 切捨て 189 / 四捨五入 189 / 切上げ 189。8%: 1,000 + 333 = 1,333 → ×0.08 = 106.64 → 106 / 107 / 107。合計 税抜 3,223、税 295 / 296 / 296、税込 3,518 / 3,519 / 3,519。参考: 明細ごとに切捨てると 10% は 123.4→123 + 56.7→56 + 8.9→8 = 187 で、税率ごと1回の 189 と 2 円ずれる（問57 が禁じるやり方）。
- **invoice 2（税抜、四捨五入の境界と率 0 の行）**: 10%: 1,000 + 235 = 1,235 → 123.5 → 123 / 124 / 124。8%: 700 + 550 = 1,250 → 100.00 → 100 / 100 / 100。免税 500 → 0。合計 税抜 2,985、税 223 / 224 / 224、税込 3,208 / 3,209 / 3,209。
- **invoice 3（税込、割戻し）**: 10%: 1,100 + 1,650 + 534 = 3,284 → 3,284 × 10 ÷ 110 = 32,840 ÷ 110 = 298.5454…（110 × 298 = 32,780、余り 60、60 ÷ 110 = 0.5454…）→ 298 / 299 / 299、税抜 = 3,284 − 税 = 2,986 / 2,985 / 2,985。8%: 540 + 1,000 = 1,540 → 1,540 × 8 ÷ 108 = 12,320 ÷ 108 = 114.0740…（108 × 114 = 12,312、余り 8）→ 114 / 114 / 115、税抜 1,426 / 1,426 / 1,425。合計 税込 4,824、税 412 / 413 / 414、税抜 4,412 / 4,411 / 4,410。
- 3 伝票 × 3 モード = 9 ケースが初回実行で一致（実装と手計算が独立に同じ値）。
- 2回目のセッションで手計算を再検算: 上記の「余り」を 1 か所訂正（10% の 32,840 − 32,780 は 60。1回目の記録は 20 と書いていた。商 298.5454… と golden の期待値は正しく、JSON の変更なし）。他の 8 グループ値・9 合計値はすべて一致。
