## 決めたこと（と理由）
- **uom の `code` は UN/ECE Recommendation 20 のコード**（個=`H87`, 式=`SET`, 時間=`HUR`, kg=`KGM`, 箱=`BX`）。spec は code 値を指定していない。JP PINT（デジタル庁）が同じコード表を使い、code は immutable で後から直せないため標準に寄せた。表示は `name`（displayField）と `symbol` で行う。`DEFAULT_UOM_CODE = 'H87'` を index から export し、AC-2 の既定値の検索キーにした。
- **`product.uomId` は DSL 上 `required` を付けず、必須性は `before_validate` フックで担保**した（`hooks/default-uom.ts`）。理由: `required: true` にすると汎用 `product.create` アクションが `entity.schemas.insert` で入力を検証してから handler → Repository → `before_validate` の順に進むため、API 経由の「name だけで作成」（AC-2）がフックに到達する前に 400 で落ちる（実測: ゲート1回目の失敗）。フックは (1) 作成時に uomId 省略/null なら会社の `H87` を補い、無ければ hint 付き ValidationError、(2) 更新で `uomId: null` を拒む。DB 列は nullable になる（spec の「required」から逸脱。下記「判断待ち」）。
- **`product.resolve_price`** は `isSold` / `isPurchased` / `isActive` を見ない（spec に記述なし。素直に格納値を返す）。`tx: 'none', mutates: false`、権限は `{ entity: 'product', op: 'read' }`。
- **シードの冪等性は `code` で判定**（uom も product も）。`seedProducts` は先に `seedUoms` を呼ぶので module manifest の `seed` は `seedProducts` 1つ。サンプル品目の code は `SAMPLE-GOODS` / `SAMPLE-SERVICE` / `SAMPLE-FOOD`（spec に指定なし）。
- 自モジュール内のテストは `../src/index.ts` を相対 import（kernel のテストと同じ流儀）。kernel からは `@daifuku/kernel` と `@daifuku/kernel/testing` のみ。
- `roles` を manifest に書いた（viewer/sales/purchasing）。既存モジュールが同名ロールを宣言しているかは読めなかったので重複の可能性あり（registry は roles を検査しないので動作には影響しない）。

## 見つけた問題と修正（発見経路つき）
- **汎用 create アクションは `before_validate` フックより先に Zod 検証する**ため「required だがフックで既定値を補う ref」を DSL で表現できない — 発見: 実測（ゲート1回目、3 テスト失敗）。修正: `uomId` の `required` を外しフックで必須性を担保（上記）。kernel 側の改善候補: (a) 汎用 create/update の入力検証を Repository に委ねる（runAction では strict オブジェクト検証のみ）、または (b) `f.ref(..., { defaultFrom: (ctx) => … })` のような「実行時既定値」オプションを DSL に追加して insert schema で optional 扱いにする。ADR 対象。
- テスト側の型: `Infer<typeof Product>['uomId']` が `string | null` になったための tsc エラー1件 — 発見: 実測（ゲート2回目）。修正: テストで null ガード。

## ドキュメントの穴（spec / docs だけでは決められず推測したこと）
1. uom の標準単位の `code` 値（spec は名称のみ）。→ UN/ECE Rec 20 を採用。
2. AC-2「会社の 個 uom」の特定方法（code か name か）。→ `DEFAULT_UOM_CODE` で code 検索。
3. サンプル品目の具体値（code・名称・価格・単位）。→ 任意に決めた。
4. `resolve_price` が非販売品（`isSold=false`）や無効品目（`isActive=false`）に対してエラーにすべきか。→ しない。
5. ロール名（viewer/sales/purchasing/admin）の正典が docs に無い（spec 内にしか出てこない）。manifest の `roles` を他モジュールと重複宣言してよいかも不明。
6. `ModuleConfig.seed` を誰がいつ呼ぶか（apps 側の責務らしいが conventions に記述なし）。テストでは system 相当のコンテキストで直接呼んだ。
7. モジュールのテストで自パッケージを `@daifuku/mod-product` と `../src` のどちらで import するか（layers.md は他モジュールからの import のみ規定）。→ kernel と同じく相対。
8. `product.list` の `search` は検索語を正規化しない（kernel 仕様）。`nameKana` は半角カナで保存されるので、全角カナで検索すると当たらない。AC-7 の意図が「読みで検索できる」なら kernel の searchCondition 側で `normalize` を適用すべき。今回は半角で検索するテストにした。
