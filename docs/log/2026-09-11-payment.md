## 決めたこと（と理由）
- **権限（AC-6）は「ロール表 + rowRules + フック」の 3 層**。ロール表: accounting = 全 op、sales / purchasing = read/create/update/submit、viewer = read（spec どおり。cancel / delete / amend は accounting と admin のみ）。rowRules: `sales → direction='receive'`、`purchasing → direction='pay'`（kernel の rowFilter は「付与された全ロールが制限されているときだけ絞る」ので、accounting / viewer / sales+purchasing 兼務は両方向を見る）。これで get / list / update / submit / cancel の対象行が自動的に方向で絞られる（見えない行は NOT_FOUND、存在を漏らさない）。**create には rowRules が効かない**（kernel の create は assertOp のみ）ので、ヘッダの `before_validate`（create/update、パッチで direction を変える場合はマージ後の値）と `before_submit` で `roleAllowsDirection(roles, direction)` を検査し、PERMISSION_DENIED（op = `create:pay` のように `<op>:<direction>`）。明細 `payment_allocation` にも同じ rowRules（`invoiceEntity` で方向を判定）。
- **submit できるロールと、submit フックが呼ぶ他モジュールの権限の対応**（判断待ちだった sales ログの件）: sales_invoice / purchase_invoice は `accounting: ['read','update']`、自ロールに update、journal_entry は sales / purchasing / accounting に create/update/submit、account は sales / purchasing / accounting に read。したがって sales（receive）、purchasing（pay）、accounting（両方）のどれで submit しても `applyPayment` → `postFromSource` が同じ Context で完走する（DB テスト AC-3 / AC-6 で 3 ロールとも実測）。cancel は accounting のみなので、負の applyPayment（両エンティティに update が要る）と reverseEntry も通る。
- **検証は「明細保存時の行単位チェック」と「submit 時の全体チェック」に分ける**（AC-2）。行単位（`payment_allocation.before_validate`、汎用 update の replace-all でも repo 直叩きでも同じ）: amount > 0、invoiceEntity が親の direction に一致、請求書が存在し**呼び出し側から見える**（sales / purchase の repository を通す。見えなければ「does not exist or is not visible」）、submitted かつ status=open、親と同じ取引先、amount ≤ 請求書残高、amount ≤ 支払金額。Σ 系（同一請求書の重複、Σ ≤ amount）は submit 時のみ: 汎用 update はヘッダ→明細の順に保存し、replace-all は「新規作成→不要行削除」の順なので、途中状態で Σ > amount が正当に起こる（DB テスト AC-2 で [A:1000]→[A':1000] の置換が通ることを確認）。ヘッダの `before_update` は Σ を再計算するだけで投げない。金額を Σ 未満に減らした draft は `unallocatedAmount` が負のまま保存され（真実を見せる）、submit が `lines` の issue で拒む。
- **submit 時の順序**: 方向×ロール → amount > 0 → 明細と請求書スナップショット（sales / purchase の list、200 件ずつ）→ `validateAllocations`（純粋関数、全 issue を一括で返す）→ 各行 `applyPayment` → 設定の科目解決 → `postFromSource` → 行に allocated / unallocated / journalEntryId を書く（kernel が docstatus / number と同じ UPDATE で保存）。どこで失敗しても同一トランザクションなので draft・請求書・台帳は無傷（DB テスト AC-3 で科目コード欠落時に実測）。`after_submit` で仕訳の摘要に番号を付ける（sales と同じ）。
- **転記（AC-3）は売掛金／買掛金を「消込行ごと 1 行」にした**（メモ `売掛金 INV-2026-000001` のように請求書番号を持つ。Σ = allocated で spec の金額と一致）。前受金／前払金は未消込額が 0 でなければ 1 行、現金／預金は 1 行（memo `入金`/`支払`）。全行に partnerId（1300 / 2100 は partnerRequired）。0 円行は出さない（accounting の XOR 検証）。摘要は `入金 PAY-2026-000001 得意先A` / `支払 …`。
- **cancel（AC-4）は before_cancel で各行を負の applyPayment（paid → open に戻る）、仕訳は `reverseEntry`（元仕訳と同じ日付）**。取消後も allocatedAmount / unallocatedAmount / journalEntryId はそのまま残す（履歴）。kernel の cancel は `findDependents`（ref を持つ submitted 文書）を先に見るが、payment を ref するのは明細だけなので依存なし。
- **amend は kernel がヘッダと明細を複製する**ため、ヘッダの before_validate（create）がシステム所有列を初期化し、明細の before_validate が請求書の現在状態で検証する。cancel 直後（請求書が open に戻った状態）なら複製が通り、`<元番号>-1` で再 submit できる（DB テスト AC-4）。請求書がその後に別の入金で paid になっていれば amend は VALIDATION で失敗する（明細を持たない下書きを作り直す。制限として記録）。
- **`payment.outstanding { direction, partnerId? }`（AC-5）** は sales / purchase の repository を呼び出し側 Context で list する（docstatus=1 ∧ status=open、date・number 昇順、500 件ずつ 10,000 件まで）。列: number / partnerName / date / dueDate / total / paidAmount / balance / invoiceId（ref = 方向に応じて sales_invoice か purchase_invoice）/ partnerId。totals は total / paidAmount / balance。permission は `payment.read`、請求書側の read は各 repository が見る（sales が pay を引くと PERMISSION_DENIED）。
- **設定 `payment.accounts`**（コード: cash 1000 / bank 1100 / receivable 1300 / payable 2100 / advanceReceived 2400 / advancePaid 1900、l10n/jp のシードに全部ある）。`accountId` 省略時は method=cash なら cash、それ以外は bank のコードの科目（無ければ VALIDATION path accountId、hint に設定キー）。update で `accountId: null` を送ると（パッチ or 既存の method で）既定を入れ直す。転記側の 4 科目が無ければ INVALID_STATE（欠落コードを details.missing に）。
- **`date` の既定は JST の今日**（kernel の `default:'today'` は UTC なのでフックで先に埋める。sales / purchase と同じ）。`amount ≤ 0` は draft 保存時から VALIDATION（spec「> 0」）。
- **`invoiceId` は uuid（ref ではない）**: 2 エンティティを指すため。汎用 UI はリンクにできない（gap）。

## 見つけた問題と修正（発見経路つき）
- 作成時（明細なし）の `unallocatedAmount` が 0 になっていた（before_update が走らない create 経路で amount を写していなかった）— 発見: 実測（DB テスト AC-1）。修正: before_validate（create）で `unallocatedAmount = amount`（src 2 行）。gate_failures 1（db 初回。同じ回に test 側の期待値誤り 2 件: draft / paid 請求書に対する行は「not open」と「残高超過」の 2 issue が出る）。
- テスト側の期待値誤り — 発見: 実測。他取引先・残高超過・不正 method（accountId の既定が入らず 2 issue）の各ケースで issue 数を 1 と決め打ちしていた／科目別 net の基準を請求書転記の前に取っていた。修正: 金額を調整、基準の取り直し。gate_failures 2（db 2・3 回目）。
- tsc: 非 async のコールバック内で await（テスト）— 発見: 実測。修正: 先に変数へ。gate_failures 1。
- unit: `lineIssues` の期待 issue 数（支払金額超過と残高超過が同時に出る）と、請求書スナップショット欠落時は残高チェックまで進まない点 — 発見: 実測。修正: 期待値。gate_failures 1。

## kernel / 他モジュールへの要望（gap。本ランでは編集していない）
- **rowRules が create に効かない**（Repository.create は assertOp のみ）。方向×ロールはフックで補ったが、「作成時にも rowRules を適用する」か「create 用の domain 検査」が kernel にあるとフックが不要になる。
- **`PermissionDenied` に details / hint を足せない**（コンストラクタが entity / op / roles 固定）。方向の拒否は op を `create:pay` のようにして表現し、hint は汎用文言のまま（ログに理由を出している）。
- **多態 ref**（`invoiceEntity` + `invoiceId` の組）を DSL が表せない。uuid にしたので FK・汎用 UI のリンク・`findDependents` の対象外。ADR が要る話。
- 既存と重複: 汎用 `<entity>.create` が明細保存後にヘッダを再読込しない（テストは create → get）、`after_lines_saved` フックが無く明細 1 行ごとにヘッダを再保存、`tableResult` を kernel に。
- sales / purchase の `record_payment` アクションが REST/MCP に露出したまま（転記なしで残高が動く）。payment ができた今、内部関数のみ（アクション登録なし）にするか、permission を admin 限定にするかの判断待ち。

## 次のセッションへ
- API/UI からは `payment.create { direction, partnerId, amount, method?, accountId?, date?, lines: { payment_allocation: [{ invoiceEntity, invoiceId, amount }] } }` → `payment.submit { id }`。消込候補は `payment.outstanding { direction, partnerId? }`（TableResult、行の `invoiceId` と `balance` をそのまま明細に）。取消は `payment.cancel { id }`（accounting）。
- 設定は `payment.accounts`（科目コード）。l10n/jp のシードは既定コードを全部含む。
- イベントは sales / purchase 側の `sales_invoice.payment_applied` / `purchase_invoice.payment_applied`（本モジュールは独自イベントを出していない。kernel の `payment.submitted` / `payment.cancelled` は出る）。
