## 決めたこと（と理由）
- **再計算は「ヘッダの `before_validate` フック 1 か所」に集約し、明細の `after_create/after_update/after_delete` フックがヘッダを空パッチで再保存して同じ計算を走らせる**（AC-2、指示の「汎用 `purchase_invoice.update` はヘッダ→明細の順に保存する」問題への対応）。汎用 update ではヘッダの before_validate が **旧**明細で一度計算し、そのあと saveLines が明細を 1 行ずつ create/update/delete するたびに明細フックが `repo(ctx, PurchaseInvoice).update(id, {})` を呼ぶので、最後の書き込みは必ず最終的な明細集合を反映する。DB テスト AC-2 で「汎用 update（明細差し替え）」「ヘッダのみ変更（税込→税抜）」「repo 直叩きの明細 update/create/delete」の 3 経路すべてで合計が追従することを実測。代償: 明細 N 行の保存でヘッダを N 回再計算・再保存する（各回 partner / 明細 / 税率 / 設定 / 会社 の読み取り、監査行 1 件）。数行の請求書では無視できるが、大量明細では kernel に「明細保存後フック」が欲しい（下記 gap）。
- **submit 前にも同じ再計算を実行してから転記**（hooks/submit.ts）。保存時に計算済みでも、直前の状態に依存せず「submit 時点の明細・仕入先・税率」で転記する方が安全。明細 0 行は VALIDATION（path `lines`）。
- **控除率はオーバーライド点 `purchase.exempt_supplier_credit_ratio` 経由でのみ決まる**（AC-2）。コアの既定は registered→1、exempt→0（経過措置なし）。l10n/jp は文字列名で `registry.registerOverride` する（`l10n/jp/src/services/transitional-credit.ts` が既に同名・同シグネチャで用意されていた — 本モジュールを import せずに済む契約が成立している）。戻り値は `assertCreditRatio` で「Decimal かつ 0〜1」を検証し、逸脱は INVALID_STATE（パックのバグを黙って通さない）。`CreditRatioFn` 型と定数 `PURCHASE_CREDIT_RATIO_POINT` を index から export。
- **控除率は registered/exempt に関係なく常にオーバーライドを呼ぶ**（spec の文言どおり）。パック側が registered→1 を返す責任を持つ。
- **控除対象税額の丸めは税率グループごとに 1 回、会社設定 `tax.rounding.mode`（既定 切捨て）・通貨桁（JPY=0）で行う**（AC-2「丸めは税率ごと、切捨て既定」）。`deductibleTax = round(tax × ratio)`、`nonDeductibleTax = tax − deductibleTax`。ヘッダの `taxSummary` JSON にはグループごとの deductible/nonDeductible と creditRatio を含めた（適格請求書・帳簿の根拠として残す）。
- **転記の借方は (科目, 税区分, 税率) のバケット単位**（AC-3）。品目行は設定 `purchase.accounts.purchases`（既定 5000）、経費行はその `accountId`（両方あれば accountId が勝つ）。**税込入力で同じ税率グループに複数科目があるとき**、明細ごとの `amount ÷ 1.1` を足すとグループの税額（1 回丸め）と一致しないため、丸め済みのグループ税額を科目バケットに按分（各バケットは `sum × r ÷ (1+r)` を同じ丸めで、最後のバケットが残差）し、`科目の借方 = バケット税込合計 − 按分税額` とする。これで Σ借方 = グループの税抜額が厳密に成立し、仕訳は常に貸借一致（unit の property 300 runs で確認）。
- **控除対象外消費税は 1 行、先頭明細の科目へ**（AC-3「one line」）。複数科目にまたがる請求書では按分せず先頭行の科目に寄せる（簡略化。判断待ち）。メモは固定文字列 `控除対象外消費税`。仮払消費税行は税率グループごと 1 行、メモ `仮払消費税 <税率ラベル>`。金額 0 の行は出さない（accounting の XOR 検証に落ちるため）。負の合計（返品・値引きの請求書）は貸借を鏡像にして転記する。
- **転記科目は設定 `purchase.accounts = { purchases:'5000', payable:'2100', taxReceivable:'1500' }` の科目コードで解決**（registry.registerSetting で宣言、汎用設定 UI に載る）。該当科目が無ければ INVALID_STATE（コードと設定キーを hint に）。勘定科目マスタは l10n/jp が持つ前提なので本モジュールはシードしない。
- **draft の間 `status/paidAmount/balance/journalEntryId` はシステム所有**: before_validate が常に `draft / 0 / total / null` に戻す（ユーザーが `status:'paid'` を送っても無視）。submit で `open / 0 / total / entryId`、applyPayment で paidAmount・balance・status、cancel で `cancelled` に動く。amend（kernel がヘッダ全列を複製）でも同じフックが効くので、複製された `cancelled`・journalEntryId は draft 用に戻る。
- **`dueDate` の扱い**: 空なら仕入先の締め日／支払月／支払日から `computeDueDate`（partner モジュール）。update では「パッチに dueDate がある」→ null なら再計算・値ならそのまま、「パッチに無い」→ 既存が null、または date/partnerId が変わったら再計算、それ以外は維持。submit 時に null なら再計算。
- **`date` の既定は JST の今日（`todayLocal(ctx.now())`）**。kernel の `default:'today'` は UTC 日付なので、フックが先に埋めて控除率の判定日と保存日を一致させる。
- **cancel は `paidAmount ≠ 0` なら INVALID_STATE（hint 固定文字列 `PAID_CANCEL_HINT`）**。それ以外は `reverseEntry`（逆仕訳は元仕訳と同じ日付＝請求書日付。締め済みなら accounting が INVALID_STATE で拒み、cancel 全体がロールバック）。`balance` は spec どおり触らない（年齢表は `status='open'` で絞る）。
- **`applyPayment(ctx, { invoiceId, amount, date })` は転記しない**（AC-5）。amount は正＝支払、負＝取消（paidAmount が 0〜total の範囲を出る場合は VALIDATION、負の total では範囲を反転）。`date` は本モジュールに支払履歴が無いので outbox イベント `purchase_invoice.payment_applied` の payload と監査に残るだけ。状態は `balance=0` で `paid`、それ以外 `open`。権限は purchase_invoice の `update`（purchasing / accounting / admin）。
- **`purchase.ap_aging { asOf? }` は仕入先ごと 1 行、列 = 期日前／1〜30／31〜60／61〜90／90日超／残高／件数**（TableResult は accounting の `tableResult`/`column` を再利用）。対象は `docstatus=1 ∧ status='open' ∧ date ≤ asOf`。経過日数 = asOf − dueDate（dueDate が無ければ date）。残高は現在値（支払履歴が無いので「asOf 時点の残高」の遡及はできない — 制限として明記）。
- **権限**（AC-6）: purchasing = read/create/update/submit/cancel/amend、accounting = read/update、viewer = read。spec に delete が無いので draft 削除は admin のみ（テストで確認。判断待ち）。明細は purchasing が read/create/update/delete、accounting/viewer が read。
- **明細の既定値**: `productId` があれば description=品目名、unitPrice=purchasePrice、taxCategory=品目の税区分。経費行は `accountId.taxCategoryDefault`。両方無ければ VALIDATION（path `accountId`）。既定が取れず taxCategory 未指定なら VALIDATION（path `taxCategory`）。`amount = quantity × unitPrice`（丸めない。丸めは税率ごと 1 回の税額のみ）。
- **明細の凍結**: kernel は saveLines 経路しか守らないので、`before_create/update/delete` フックで「親が draft でなければ INVALID_STATE」を repo 直叩きにも適用（accounting の freeze-lines と同じ考え）。

## golden の導出（AC-7、test/golden/exempt-supplier.json）
前提: 税込 11,000 の品目行 1 行、標準税率 10%（tax_rate STD10、2019-10-01〜）、会社設定 `tax.rounding` 既定 = 切捨て・請求書単位、通貨 JPY（桁 0）。
1. 税率グループ（standard, 0.1）の税込合計 G = 11,000。税額 T = round_down(G × 0.1 ÷ 1.1) = round_down(1,000) = **1,000**。税抜 A = G − T = **10,000**（1 請求書につき税率ごとに 1 回丸め、国税庁 Q&A 問57）。
2. 2026-10-15、免税事業者、テスト内で `registry.registerOverride('purchase.exempt_supplier_credit_ratio', fn)`（fn: registered→1、exempt→ 2026-10-01 以降 0.7、それ以前 0.8）→ ratio = **0.7**。控除対象 = round_down(1,000 × 0.7) = **700**、控除対象外 = 1,000 − 700 = **300**。
   仕訳: 借方 5000 仕入高 10,000（バケット税抜 = 11,000 − 按分税額 1,000）／ 借方 1500 仮払消費税 700（メモ「仮払消費税 標準10%」）／ 借方 5000 仕入高 300（メモ「控除対象外消費税」）／ 貸方 2100 買掛金 11,000（取引先 = 仕入先）。借方合計 11,000 = 貸方合計。科目別: 5000 = 10,300、1500 = 700、2100 = −11,000（spec の「Dr 5000 10,300 / Dr 1500 700 / Cr 2100 11,000」と一致）。
3. 同じ請求書を 2026-09-15 に → ratio 0.8 → 控除対象 **800**、控除対象外 **200**。仕訳: 5000 10,000 + 200 = 10,200、1500 800、2100 11,000。
4. オーバーライド無し（コア既定）の免税事業者 → ratio 0 → 控除対象 0、控除対象外 1,000。仮払消費税行は出ず、5000 = 10,000 + 1,000 = 11,000。
5. 課税事業者 → ratio 1 → 1,000 / 0。
unit テストは 1〜5 を `summarizeTax`（mod-tax の純粋関数）＋ `applyCreditRatio` ＋ `buildJournalLines` で再現し、行ごと（科目・借方・貸方・メモ）と科目別合計を golden と照合。DB テストは 2・3 を実際の伝票 create → submit → journal_line の行で照合（`sourceEntity='purchase_invoice'`、description `仕入 免税工房 INV-EX-1`、番号 `BILL-2026-000001` 形式）。
補足（unit のみ）: 税込・同一税率で複数科目のケース 3 × 3,667 = 11,001 → T = round_down(1000.09…) = 1,000、A = 10,001。5000 バケット 3,667 − round_down(333.36) = 3,334、6400 バケット 7,334 − (1,000 − 333) = 6,667、計 10,001 で厳密に一致。

## 見つけた問題と修正（発見経路つき）
- DB テスト初回: 汎用 `purchase_invoice.create` の応答が合計 0 だった — 発見: 実測（4 件失敗）。原因は kernel の crud create が「明細保存前のヘッダ行」をそのまま返すこと（update は再読込するのに create はしない）。DB の行は正しい（明細フックで再計算済み）。修正: テストの `createBill` を「create → get で再読込」にし、gap として下記に記録。gate_failures 1。
- 同回: AC-4 の科目別 net の基準を submit 後に取っていた／AC-5 年齢表を絶対値で比較して先行テストの残高が混入 — 発見: 実測。修正: 基準を submit 前に、年齢表はテスト前後の差分で比較（テストの誤り、実装は正しい）。
- DB テスト 2 回目: purchasing による submitted 伝票の delete を INVALID_STATE と期待していたが PermissionDenied（spec どおり purchasing に delete 無し）／amend 後の番号 `<元番号>-1` を期待したが kernel は新規連番を採る — 発見: 実測（2 件失敗）。修正: 前者は admin コンテキストで INVALID_STATE を確認、後者は「新規番号かつ元と異なる」に変更し gap として記録。gate_failures 1。
- tsc: `snapshot()` にドメイン行を渡す際の型（Record<string, unknown> への変換）— 発見: 実測。修正: `as object as Record<string, unknown>`。gate_failures 1。
- eslint: services/payment.ts の `import { Decimal }` が型のみ使用 — 発見: 実測。修正: `import type`。gate_failures 1。

## kernel への要望（gap。本ランでは kernel を編集していない）
- **汎用 `<entity>.create` が明細保存後にヘッダを再読込しない**（`actions/crud.ts` の create ハンドラは `withLines(ctx, entity, created)` に保存前の行を渡す。update は `lineRows ? await r.get(id) : updated` で再読込している）。明細から導出されるヘッダ列（本モジュールの合計、accounting の totals など）が create 応答に出ない。修正案: update と同様に `lineRows ? await r.get(created.id) : created`。
- **「明細保存完了後」のフック**（例: `after_lines_saved`）。無いので明細 1 行ごとにヘッダを再保存している（明細 N 行 → ヘッダ再計算 N 回、監査行 N 件）。
- **amend の採番**: ADR-0006 と `amendDocument` のコメントは `<元番号>-<n>` だが、`submitDocument` は amendedFrom を見ず新規連番を採る。
- **amend が明細を複製しない**（ヘッダ列のみ）。訂正用の draft は明細を入れ直す必要がある。
- 既存記録と重複: TableResult の zod を kernel が持つ（今は accounting から import）、`cancelDocument` の依存チェックが before_cancel より先、システム導出フィールドの宣言（`status`/`paidAmount` 等を汎用 create/update から書けなくする印）。

## 次のセッションへ
- payment モジュールからは `import { applyPayment } from '@daifuku/mod-purchase'` で同一トランザクション内に `applyPayment(ctx, { invoiceId, amount, date })`。支払取消は負の amount。イベント `purchase_invoice.payment_applied`（payload: invoiceId, number, amount, date, paidAmount, balance, status）。
- l10n/jp は `registry.registerOverride('purchase.exempt_supplier_credit_ratio', fn)`（`fn: ({ supplierTaxStatus, date }) => Decimal`、0〜1）。purchase 側の定数 `PURCHASE_CREDIT_RATIO_POINT` / 型 `CreditRatioFn` は index から export 済み（import してもよいし、文字列名でもよい）。
- 転記科目は会社設定 `purchase.accounts`（科目コード）。l10n/jp の勘定科目シードは 5000/1500/2100 を含めること（無ければ submit が INVALID_STATE）。
- 年齢表は `runAction(ctx, 'purchase.ap_aging', { asOf })`。出力は TableResult。
