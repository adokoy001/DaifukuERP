## 決めたこと（と理由）
- **実機で操作したことだけを「確認」と書き、各章の末尾に 検証 欄**を置いた（CLAUDE.md 規則 11）。画面で操作したもの・API で確認したもの・仕様書やソースから書いたもの（未検証／レビューのみ）を分けた。
- **スクリーンショットは既存のデモ DB（小売＋不動産の両 pack 適用済み）で撮る**。サーバ再起動・`db:reset` が禁止のため `DAIFUKU_PACKS` を変えられず、見出しが「家賃請求書」「入居者/取引先」になる。00 章でそう断り、この現象自体を制限事項（ラベル上書きが全社共通）の実例として書いた。

- **HTML 変換は python3 の `markdown`（tables / fenced_code / toc）を child_process で呼ぶ**（npm 依存を増やさない。自作パーサより表・入れ子リストが確実）。見出し ID は章ごとに接頭辞を付けて衝突を避け、章ファイルへのリンクはページ内アンカーに書き換え、画像は data URI で埋め込む。目次は横スクロールの 1 行（sticky、高さ 77px）にした（最初は折り返しで 145px あり、見出しを隠したため）。

## 見つけた問題と修正（発見経路つき。すべて本セッションでは未修正）
操作手順は画面（:5173、admin）で再現できる形で書く。

1. **新規の売上請求書が画面から保存できない**（重大）— 発見: 実測。手順: 「販売」→「売上請求書」→「+ 新規」→ 得意先・請求日を入れ、明細に品名・単価・税区分を入れて「保存」→「入力内容を確認してください」、「税率別内訳」（json・required・computed）に「必須項目です」。`[]` を入れると保存でき、サーバが計算で上書きする。訂正版の下書き（既に `[]` を持つ）は影響なし。仕入請求書・レジ締めは該当しない。e2e は請求書を API で作っているので検出されなかった。原因の推定: 汎用フォームが required かつ既定値なしの json 項目をクライアント検査している（DSL に computed/readOnly ヒントが無い既知の未実施項目の実害）。
2. **確定済みの売上請求書の「残高」「状態」「入金済額」を手で書き換えて保存できる**（データ整合性）— 発見: 実測。手順: 確定済みで未入金の請求書（例 INV-2026-000003、残高 1,000）を開く →「残高」を 0、「状態」を「入金済」にして「保存」→「保存しました」。API で `status: paid, balance: 0, paidAmount: 0`。未消込一覧・年齢表から消えるが、売掛金 1300 の仕訳は残る。`allowOnSubmit` が payment モジュールの内部更新用に開けてある項目を、汎用 update がそのまま受け付けている（sales の before_update は確定済みで再計算を飛ばす）。確認後に API で元に戻した。
3. **新規作成で bool の既定値が反映されない** — 発見: 実測。手順: 「取引先」→「+ 新規」→ 名称だけ入れて「保存」→ API で `isActive: false`（台帳の既定は true）。仕入請求書の「税込入力」（既定 true）も新規画面でオフ、売上請求書の「税込入力」は会社設定 `tax.price_includes_tax = true` でもオフで表示され false が送られる。`/meta` が既定値の有無（`hasDefault`）しか出さず値を出さないため、画面が既定値を知らない。
4. 既定値のある enum・int が新規画面で空欄／「（未選択）」表示（取引先の課税区分・締め日、入出金の方法、請求書の状態）。保存時にサーバが既定値を入れる — 発見: 実測。
5. 明細で品目を選んでも品名・単価・税区分が入らず、空だとクライアントで必須エラー（spec では省略時にサーバが品目から補う）。レジ締めの「店舗倉庫」「税込単価」も必須入力（spec では既定あり）— 発見: 実測。
6. 確定済みの仕訳に「取消」ボタンが出て、押すと英語の `INVALID_STATE … use accounting.reverse_entry`。逆仕訳の画面操作は無い — 発見: 実測（JE 元入金で確認）。
7. 「訂正」の確認ダイアログの文言が「訂正」の一語（`doc-actions.tsx` が確認文に `S.amend` を渡している）— 発見: 実測。
8. 画面から実行できない mutating アクションが多い（`open_fiscal_year`、`reverse_entry`、`contract.generate_invoices`/`end`、`real_estate.*`、`retail.close_month`、`pack.apply`、`attachment.supersede`）。汎用 UI は `resultKind: table` 以外のアクションを出さない — 発見: 実測＋ソース。テンプレートの業務は API/MCP 前提になっている。
9. エラー表示が英語・技術的（重複アップロードの sha256 と `details.existingId`、在庫不足、同時更新の `CONFLICT … (version 4, expected 3)`、使用中の取引先削除の FK 制約名 `journal_line_partner_id_partner_id_fk`）— 発見: 実測。
10. 英語のままのラベル: レポート条件（From / To / As Of / Account Id / Period）、設定画面の細目（Mode / Revenue / Name …）、bool 設定が JSON テキスト欄、レントロールの用途・状態・税区分がコード値、合計欄のキー（`taxableRent`、`output_tax_total`）、試算表の区分列（asset …）— 発見: 実測。
11. レポート一覧で `contract.schedule` の名前が「対象月」（説明文の最初の句で題名を作る規則）— 発見: 実測。
12. 内部 ID の露出: レジ締めの「売上請求書」「現金入金」参照欄が UUID、消込明細の請求書 ID、監査ログの実行者 `user:01a09088…`、レポートの ID 列、下書き伝票の見出しが短縮 UUID、確定伝票の見出しで番号が 2 回 — 発見: 実測。
13. 計算項目・システム項目が入力欄として表示（下書きの税抜合計・入金済額・状態、仕訳の起票元・借方合計、入出庫の発生元、税率別内訳の JSON）。確定後の契約の「終了日」「状態」「次回請求対象月」も編集可能（試していない）— 発見: 実測（既知の未実施「readOnly ヒント」の再確認）。
14. 1 社に小売と不動産を適用すると `sales.accounts.revenue` が 4200 になり、レジ締めの売上が賃貸料収入に計上される（REG-2026-000004 で確認後に取消）— 発見: 実測。
15. 会計期間の「締め済み」が汎用フォームで切り替えられ、`close_period` アクションと監査ログ上区別できない（`action` 欄が空）。会計期間に「削除」ボタンが出る — 発見: 実測。
16. 必須の文字列項目が空文字を受け付ける（`POST /actions/partner.create {"name": ""}` が 200。作成後に削除）— 発見: 実測。
17. `pnpm --filter @daifuku/mcp start` をそのまま MCP クライアントに渡すと pnpm のバナーが stdout に出て非 JSON 行になる（`-s` で解消。mcp-app spec の検証手順の書き方も同じ）— 発見: 実測。
18. 細かい点: 一覧の日本語名の並び順が文字コード順、請求書一覧に「状態」列が 2 つ、明細の合計行が単価列も合計する（レジ締めで 2,132）、ページ読込ごとに `favicon.ico` の 404、ext 変更の監査ログが生 JSON — 発見: 実測。
