## 変更と保持する契約

2026年の税表・料率・年齢判定・端数処理等のパラメーターをl10n/jpのJSONと期間付きmanifestへ移した。workforceは公開portから国・通貨に合う算定器を選び、会社のRepositoryで取得して配布内容との一致を確認したデータを渡す。支払日・保険月・賃金締日・年調実施日を別々に検査し、未対応期間、資料の改変、方式不明、競合する版を拒否する。

新しいDSL entityと追加migration `0015_payroll_rule_versions.sql` は導入確認の記録だけを持つ。旧制度表の列と行を変更しない。既存データの導入確認は別行を追加し、同版の再導入は不変である。制度訂正は明示的な置換関係を持つ版を追加する設計とした。

旧形式の給与・年調は旧serializerと同じデータで再検査し、新計算には形式版と制度識別情報を保存する。確定時には原資料だけでなく保存済みの計算JSON・金額列も比較する。旧計算の金額・根拠・課税証跡をmigrationや導入操作で書き換えない。

画面は導入済みの対応年度と過去資料の年度を区別する。制度の出典・範囲・方式・hash・導入の確認記録を表示し、一般従業員は導入できない。資料を再取得できないときは入力を保持して操作を止め、会社切替時には前会社の確認画面を持ち越さない。

## 検証

既存の算定試験35件を期待値を変えず国別層へ移した。合成2037年・変更料率・期間境界・方式やschema/hashの不一致を含む追加19件と合わせ54件が成功した。実際の2027年以降の法定値は出荷していない。

既存workforce DB試験6件の期待値は維持した。国別providerの登録を統合試験のcompositionに追加し、新しい保存金額・計算JSONの改変拒否12件と合わせ18件が成功した。moduleからl10nへの逆依存は作っていない。

全体DB試験で、日本moduleの依存一覧を固定していた既存試験が失敗した。新しい公開portへ接続するための `workforce` 依存を完全一致の期待配列へ追加し、給与providerの登録も検査した。依存規約そのものは緩和せず、対応specの一覧も現行構成へ合わせた。

Webの関連ブラウザー4件（従来の給与導線1件と新規3件）が同一実行で成功した。制度の確認・導入、503応答時の入力保持、冪等な再導入、未対応期間の拒否、従業員権限、2会社の分離を確認した。390pxの画面と英語表示は目視し、dialogの横溢れも測定した。Webの入力補助単体12件、API/Web型検査、Web/edge buildも成功した。

最終レビューで、制度catalogの取得エラーが給与本部画面全体を隠す回帰を検出した。制度欄へエラーを局所化し、新算定を停止しながら保存済みの記録を表示するよう修正した。別のブラウザー試験1件で、初回catalog失敗・明細展開・算定停止・再取得後の操作復帰・保存行不変を確認した。

通常ブラウザー全体は新しい専用の空DBから実行し、72件が同一実行で成功した（19.5分）。上記の追加障害ケース1件は別実行で成功した。新しい制度画面の390pxと英語1280pxを親レビューでも目視した。公開対象のstaged差分約1.50MBは秘密スキャンで検出0だった。

最初の全gate実行は私的runnerのumask077が試験用0644ファイルを0600にしたため1件失敗した。テストは変更せず、ログを0600で先に作り、試験プロセスを通常のumask022に戻して対象6件の成功を確認した。

修正後の最終 `pnpm gate` は一回の通し実行でexit 0となった。型・Lint・依存境界、単体120ファイル1,003件、DB111ファイル668件、配備13件、文書105件・参照1,019件、assurance 15条件がすべて成功した。行数超過は既定の警告であり、行数合わせの分割は行っていない。API/Web型検査、Web/edge buildも成功し、Webの既存のbundleサイズ警告は残る。

## 旧実装からの互換・更新

旧実装 `62bf9d16802db7becfdda40dfce7c2db44312176` の全15migrationを使って合成の給与・年調・申告準備資料を作った。そのdumpを新しい専用DBへ復元し、正式setupの計画表示・対象確認・別DB復元確認を経て0015へ更新した。元の合成DBを更新先に使わず、実業務環境にも接続していない。

| 検証 | 実測結果 |
| --- | --- |
| 移行前後 | 旧12表45行が全フィールド一致。ID・version・日時・JSON・金額を含む |
| 正式upgrade | 15→16migration、seed 0、バックアップ1件、独立復元側でも旧12表45行が一致 |
| 旧制度の導入確認 | 旧45行不変、導入記録1件を追加。同版再導入は同じ行を返す |
| 申告準備の再出力 | 旧確認済み資料の出力全体が一致。CSV 6行・3,081バイトも完全一致 |
| 旧給与下書き | 2件をcalculate actionによる再保存なしで確定。計算JSON・元資料・金額を保持 |
| 旧年調下書き | 1件をcalculate actionによる再保存なしで確定。計算JSON・元資料・金額を保持 |
| 既存の確定結果 | 給与7件、年調2件（精算済1件を含む）、税証跡7件が全フィールド一致 |
| 新形式 | 新規給与1件を形式版2・制度識別情報付きで作成し、確定後も根拠と金額を保持 |
| 未対応年度 | 2027年の月次制度選択と年調calculateを拒否 |
| 最終の旧記録 | 意図して確定した旧下書き3行以外の既存42行が全フィールド一致 |

確定時には計算根拠を再生成して比較する。『再保存なし』はcalculate actionで下書きを置き換えなかった意味で、確定検査を省略した意味ではない。旧下書きの状態・確認担当・version等は通常の確定処理に従って更新する。この復元DBでは新形式の年調の新規作成は重複実施せず、恒久DB試験とブラウザーの年調導線で検査した。

移行は完了したが、私的検証スクリプトが直後に誤ったcheckpoint名を読んだため一度停止した。正しいファイルから移行後の照合を再開し、復元先の消去やmigrationの再適用は行わなかった。

## 出典と限界

[国内給与資料](../domain/japan-payroll-automation.md) に2026-09-13の照合範囲を記録した。移行互換性のため既存payloadの確認日2026-09-12は保持した。hashは内容の識別であり、法令監修・公式署名の証明ではない。

収録済み制度は2026年の国内JPY・月額甲欄と通常年調の既存範囲である。任意の制度ファイル実行、自動収集、賞与・乙欄等の拡張、翌年度の税率を前年で代用する処理は含めない。申告準備CSVの対応年度・形式は別契約として保持する。
