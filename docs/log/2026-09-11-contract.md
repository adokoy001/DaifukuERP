## 決めたこと（と理由）
- **period は「対象月（役務の月）」**。`generate_invoices { period: '2026-06' }` は 6 月分を請求する。billingTiming は請求書の**日付だけ**を決める（advance = 6 月の billingDay、arrears = 7 月の billingDay）。spec の「date = billing date of the period (… for arrears the following month)」と contract_billing の unique (contractId, period) をそのまま読んだ。月次バッチで「今月走らせると後払い契約は先月分」という運用にしたい場合は呼び出し側が period を 1 か月戻す（判断待ち）。
- **日割りは「単価を先に丸める」**（AC-3 の後段の選択）。明細の `quantity` は契約のまま、`unitPrice = round(月額単価 × 係数, roundingMode, 通貨桁)`。通貨桁は kernel `currencyScale(company.currency)`（JPY = 0）。係数は**分数のまま**持つ（`{num, den}`、月の日数 28〜31 なので分母は lcm = 377,580 の約数、安全な整数）。計算は `unitPrice × num ÷ den` を 1 回だけ割って丸める。先に 10/31 を 40 桁の小数にすると 31,000 × 10/31 が 10000.000…0001 になり `up` で 10,001 に化けるため（unit テストで固定）。
  - daily: 月の係数 = その月に契約が掛かる日数（開始日〜終了日、両端含む）÷ その月の実日数。none: 1 日でも掛かる月は 1。
  - 例 1（開始月）: 開始 2026-05-22、月額 100,000、切捨て → 10/31 → 32,258.064516… → **32,258**（half_up 32,258 / up 32,259）。
  - 例 2（終了月）: 終了 2026-08-15、月額 100,000 → 15/31 → 48,387.09… → **48,387**、標準 10% の税 4,838 → 合計 53,225（DB テストで実測）。
  - 例 3（2 月・四捨五入境界）: 開始 2026-02-10 → 19/28 → 67,857.142857… → down **67,857** / up 67,858。月額 15,501 × 15/30 = 7,750.5 → half_up 7,751 / down 7,750。
  - 丸めて 0 円になった明細は請求書に載せない。全明細が 0 円なら請求書を作らず `skipped: zero_amount`。
- **intervalMonths は「月額 × k か月分を 1 枚で請求」**。請求対象月は開始月 + k × n（n ≥ 0）だけで、それ以外は `not_aligned`。1 請求の係数は含まれる k か月の係数の和（例: 開始 2026-04-16、k = 3、月額 10,000 → 15/30 + 1 + 1 = 5/2 → 25,000。実測）。spec は interval の金額の意味を書いていないので、単価 = 月額で一貫させた（判断待ち）。
- **nextPeriod = 「請求書をまだ作っていない、最も早い請求対象月」を台帳（contract_billing）から導出**。順番どおり生成すれば spec どおり intervalMonths ずつ進む。8 月を 7 月より先に作ると nextPeriod は 7 月のまま（飛ばした月を失わない）。この定義だと「nextPeriod ≤ period」は「対象月が開始月以降・整列・未生成」から自動的に成り立つので、期日判定は台帳の有無で行う（periods.ts `dueReason` のコメントと property テストで確認）。
- **status と nextPeriod はシステム所有で、更新のたびに導出し直す**（`hooks/recalc.ts` before_update。sales の「改ざんは上書き」と同じ方式）: draft は `draft`/null、submitted は status = 「endDate が今日の月初より前なら ended、それ以外 active」、nextPeriod = 台帳から。submit と cancel は kernel の rawUpdate で update フックが走らないので、それぞれ before_submit / before_cancel で設定。`contract.end` は endDate を update するだけで status はこの規則に従う（将来日付に動かせば active に戻る）。
  - submit 時も同じ規則で status を決める。**spec は「submit → active」だが、終了日が既に先月以前の契約を submit した場合だけ ended になる**（後から台帳登録する場合。判断待ち）。
  - 「今日」が月をまたいでも、何かが契約を更新するまで保存値の status は変わらない（生成・end・汎用 update で再導出）。
- **spec からの逸脱（要判断）: ended の契約も endDate を含む月までは請求対象にした**。AC-3 は「every active contract」だが、そのままだと「退去日の登録が翌月以降になる」普通のケース（例: 9/10 に endDate=8/15 を登録 → ended）で、8 月の日割り請求書が二度と作れない。期日判定の「endDate ≥ period start」で終了月の翌月以降は必ず `ended` で弾かれるので、増えるのは「終了月までの未生成分」だけ。一覧（generate の対象・schedule の行）は `docstatus=1 ∧ (status=active ∨ (status=ended ∧ endDate ≥ 対象月初))`。
- **contract_billing は generate_invoices だけが書く**: unique (contractId, period) が冪等性の本体（同時実行でも片方は 23505 → CONFLICT で請求書ごとロールバック）。汎用 `contract_billing.create/update/delete` が REST/MCP に出るので、module 内の per-Context マーカー（`withBillingWrite`、kernel の isSavingLines と同じ形）の外からの書き込みは admin でも INVALID_STATE（`hooks/billing.ts`）。権限は sales = read/create（生成に必要）、accounting / viewer = read。**AC-6 の「sales all ops」は contract と contract_line に適用し、台帳には update/delete を付けていない**。
- **生成の順序**: 請求書 draft（sales repository + kernel `saveLines`。期日・税・合計は sales が導出）→ 台帳行（ここで同時実行が衝突し、転記前に止まる）→ `runAction('sales_invoice.submit')`（submit 指定時。省略時は設定 `contract.auto_submit`）→ 契約を touch（nextPeriod 再導出）→ イベント `contract.invoice_generated`。1 回の実行は**全部成功か全部失敗**（kernel に savepoint のポートが無い。失敗した契約は ctx.log.warn に出してから再 throw）。
- **請求書は常に `priceIncludesTax: false`**（契約単価は税抜。会社設定 tax.price_includes_tax が true でも。DB テストで実測）。note は spec どおり `契約 CTR-2026-000001 2026-06 分`。明細の摘要は契約明細のまま（期間・日割りの注記は付けていない）。
- **取消（AC-2）は生成済みの請求書が生きている間は拒否**（draft または submitted。hint: 請求書を取消／下書きなら削除、将来の請求停止は contract.end）。取消後に amend した新しい契約は台帳が空なので、元の請求書が取消済みでないと同じ月を二重請求するため。台帳の `invoiceId` は `onDelete: cascade`: **生成した draft 請求書を削除するとその月は再び due になる**（実測）。submitted を取消した請求書の月は「生成済み」のまま（再請求は sales の amend で行う。判断待ち）。
- **出力の形**: `created: [{ contractId, invoiceId, number, total }]` は spec どおり。`skipped: [{ contractId, reason }]` に、既存請求書がある場合だけ `invoiceId` と `number` を足した（AC-4「existing invoice ids を返す」を満たすため）。reason: `not_active | already_generated | not_started | ended | not_aligned | zero_amount`。
- **schedule（AC-5）** は generate と同じ純粋関数 `planPeriod` を使う（予定額 = 生成される請求書の税抜合計。DB テストで「schedule の due 行 = 実際の生成結果（件数・税抜額・日付）」を突き合わせた）。列: contractNumber / partnerName / title / billingDate / expectedAmount / factor / status / reason / invoiceNumber / contractId(ref) / partnerId(ref) / invoiceId(ref)。not_due 行は billingDate null・予定額 0。並びは請求日昇順（null は最後）→ 契約番号。totals.expectedAmount、meta: period / counts / truncated。generated 行の予定額は**現在の契約条件で再計算**した値（後から endDate を変えると発行済み請求書と一致しないことがある）。
- 明細フックは sales と同じ規則: 品目から description / unitPrice / taxCategory を補完、`amount = quantity × unitPrice`（月額、丸めなし）、submit 後は直接書き込みも凍結。
- 設定: `contract.default_proration`（daily/none、既定 daily。create で prorationRule 省略時に使う）、`contract.auto_submit`（bool、既定 false）。メニュー: 契約一覧（order 45）、請求予定（`/r/contract.schedule`、order 46）。

- contract.end で終了日より後の生成済み請求書を知らせる／調整する（赤伝はスコープ外）。
- 請求書明細の摘要に対象期間・日割り（例「(5/22〜5/31 日割)」）を載せるか。
- spec のスコープ外: 値上げ改定履歴、自動更新（更新料）、請求書 PDF、前受金の期間按分仕訳、複数通貨。

## 判断待ち（利用者）
- **ended の契約も終了月までは生成対象にした**（AC-3 は active のみ）。spec どおりに戻すか。
- 終了日が既に先月以前の契約を submit すると ended になる（spec は「submit → active」）。
- intervalMonths の単価の意味（月額 × k か月、今回）か、1 請求あたりの額か。
- period の意味（対象月、今回）。後払い契約を「請求月」で走らせたい運用にするか。
- 台帳（contract_billing）の権限を sales = read/create に絞った（AC-6 の「all ops」との差）。
- generated 行の schedule 予定額を現在の契約条件で再計算している（発行済み請求書の金額を出すべきか）。

## 次のセッションへ
- API / MCP からは `contract.create { partnerId, title, startDate, endDate?, billingDay?, billingTiming?, intervalMonths?, prorationRule?, roundingMode?, note?, lines: { contract_line: [{ productId?, description?, quantity?, unitPrice?, taxCategory? }] } }` → `contract.submit { id }` → 毎月 `contract.generate_invoices { period: 'YYYY-MM', contractId?, submit? }` → `{ created: [{ contractId, invoiceId, number, total }], skipped: [{ contractId, reason, invoiceId?, number? }] }`。予定は `contract.schedule { period }`（TableResult）、終了は `contract.end { id, endDate }`（契約の JSON を返す）。
- 不動産パック: 居住用家賃は `non_taxable`、事務所・駐車場は `standard` の明細を同じ契約に並べればよい（税は sales が税率ごとに計算。DB テストで混在を実測）。敷金（預り金）・礼金は契約明細ではなく別伝票の想定。
