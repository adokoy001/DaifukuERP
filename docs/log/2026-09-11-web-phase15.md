## 決めたこと（と理由）
- **消込パネルは meta の規約で推論する**（/meta に宣言的ヒントが無い）。条件は全部: document に `partnerId`（ref）と `direction`（enum）、`lines` に名前が `_allocation` で終わる明細があり `invoiceId`（uuid/text/ref）・`invoiceEntity`（enum）・`amount`（decimal）を持つ、`<module>.outstanding`（無ければ `<entity>.outstanding`）が `resultKind: 'table'` で、inputSchema があれば `partnerId`・`direction` を受ける。アクション名まで条件に入れたのは、「呼ぶ先」を推測で決めないため（無ければパネル自体を出さない）。規約は docs/conventions/ui.md に既存の推論（レポート、明細グリッド列、印刷、エラーパス）と並べて書いた。
- **パネルは行を足すだけで保存しない**。フォームの現在値（保存前でも可）で `POST /actions/payment.outstanding { partnerId, direction }` を呼び、確定で明細グリッドに `invoiceEntity / invoiceId / amount` の行を追加する。保存は既存の「ヘッダ＋明細を 1 リクエスト」のまま（サーバの検証経路を 1 本に保つ）。区分・取引先が未入力のあいだはボタンを無効化してヒントを出す。
- **既定額 = min(残高, 未配分)、0 未満にしない、金額未入力なら残高**。未配分 = 金額 − グリッドの配分合計 − パネルで先にチェックした行の額（複数選択で合計が金額を超えないように）。額は「0 より大きく残高以下」でないと追加ボタンが押せない（サーバ AC-2 と同じ条件）。グリッドに既にある請求書はチェック不可（サーバは submit 時に同一請求書の重複を拒む）。パネルの結果は gcTime 0 のクエリで、開き直すたびに残高を読み直す。
- **AC-2「submit を拒む」は 保存 と 確定 の両方に掛けた**。フォームで 配分合計 > 金額 なら保存を送信前に止める（フォーム上部とサマリに alert、トースト）。保存済みの下書きで Σ明細 > 金額（API で作られた場合など）なら ヘッダの「確定」を無効化して理由を表示。サーバは draft 保存では Σ を検査しない（payment ログ: replace-all の途中状態のため）ので、クライアントの方が厳しいが、spec の文言どおり。
- **小数の表示規則（AC-8）を置き換えた**: 最小桁を必ず出し、有効な小数は 6 桁まで出す（切り捨て表示をやめた）。最小桁は money（`FieldMeta.money`）なら meta の `scale`（kernel が会社通貨で解決、JPY=0）、scale が無いか 6 以上なら `/auth/me` の `company.currency` の最小単位。money でない decimal（数量・率）は 0。TableResult の decimal 列は money の区別が無いので通貨の桁。kernel は通貨を知らないとき money に scale 6 を付ける（MCP resources・会社なし）ので、money の scale ≥ 6 は「通貨不明」とみなす。旧規則（web-polish）の「scale を超える桁は出さない」は、kernel-phase15 で money の scale が 0 になった結果 `1234.5 → 1,234` を生んだ（kernel-phase15 ログの判断待ち (a) を採用）。
- **ハードコードの会社通貨を削除（AC-4）**。`DEFAULT_CURRENCY = 'JPY'` をやめ、`/auth/me` 読込前・会社なしは最小 0 桁（詰めない）。未知の通貨コードは ISO 4217 の多数派 2 桁（kernel の `currencyScale` と同じ）。KWD/BHD=3、VND=0 は web の表のまま（kernel は 2。下の「API 側の差」）。
- **入力欄も同じ規則**。フォーカス中は生の文字列、非フォーカス時は表示形。6 桁を超えて打った値は表示形にすると隠れるので生のまま見せる（`formatDecimalInput`）。
- **ext フィールド（AC-3）はフォーム値のキーを `ext.<key>` のまま持つ**（エンティティ項目名は camelCase でドットを含まないので衝突しない）。同じ FieldWidget・同じ変換（`toPayload`）を通し、`lib/ext.ts extPayload` が `ext` オブジェクトにまとめる。kernel は update で `ext` を丸ごと置換するので、フォームに無いキー（ADR-0003 の自由形式、ページ表示後の登録）は記録の値を残し、空欄はキーを消す。update は登録キーの値が変わったときだけ `patch.ext` を送る（decimal は正規形で比較、触っていない ext を送り直さない）。必須 ext は create 時と、update で ext を送るときに要求（ADR-0014 のサーバ規則に合わせた）。確定後は `allowOnSubmit` に `ext`（全部）か `ext.<key>` があるときだけ編集可。VALIDATION の `ext.<key>` / `patch.ext.<key>` はその ext フィールドに紐付ける。
- **一覧の ext 列**: `views.list` の `ext.<key>` を extFields から解決し、値は `row.ext[key]`、並べ替え不可（API が ext の orderBy をしない）。現在の kernel は `views.list` に ext を書けない（ADR-0014 帰結）ので、将来のビュー定義向け。
- **AC-7**: totals を「列 key に一致するもの」と「しないもの」に分け、前者は従来の合計行、後者は表の下の「合計」キー・値リスト（キーはそのまま、値は小数の表示規則）。**一致する totals が 1 つも無いときは空の合計行を出さない**（従来は tax_period_summary で「合計」だけの空行が出ていた）。CSV は合計行の後に `key,value` 行をサーバの順で追加（一致する totals が無ければ合計行は出さない）。
- **明細セルの多相参照リンク（spec 外の小追加）**: `<x>Id`（uuid/text）と同じ行の `<x>Entity`（enum、値が /meta のエンティティ名）があれば、id 入力の下に参照先の番号をリンク表示。消込明細が uuid だけで「どの請求書か」読めなかったため（payment ログの gap「invoiceId は uuid なので汎用 UI はリンクにできない」への回答）。行ごとに `GET /api/<entity>/<id>`（react-query でキャッシュ）。規約として ui.md に記載。
- **`apps/web/package.json` に `test` スクリプトを追加**（`vitest run --config ../../vitest.config.mts --project unit`）。**それまで `pnpm --filter @daifuku/web test` はスクリプトが無く、何も実行せずに exit 0 だった**（実測）。オーケストレータの指示するゲートが空振りしていた。
- **NumberField のフォーカス時の差し替えを focus イベント内で DOM に反映**（下の「見つけた問題」）。

## API 側の差・ギャップ（apps/api・kernel・modules は編集していないので報告のみ）
- **`payment.accountId` は /meta で `required: true, hasDefault: false` だが、hooks/validate.ts が `payment.accounts` から既定を入れる**。汎用フォームは必須とみなし、利用者に科目の選択を求める（e2e でも「普通預金」を選んでいる）。「フックが既定を入れる」を meta に出す手段（例: DSL の `defaultedByHook` → `hasDefault: true`）が要る。
- **消込の宣言的ヒントが meta に無い**（規約で推論）。`lines[]` に `picker: { action, fill: { invoiceId, invoiceEntity, amount } }` のような宣言があれば、名前規約に依存しなくて済む。
- **TableColumn に money の区別が無い**ので、レポートの decimal 列（率 `taxRate` を含む）は通貨の最小桁で表示される。JPY では影響なし、USD では `0.1 → 0.10`。
- **通貨の最小桁の表が kernel と web で違う**: kernel `currencyScale` は JPY/KRW=0、他は 2。web は VND=0、KWD/BHD=3 を持つ。money 項目は meta の scale（kernel）が勝つので、KWD の会社では項目（2 桁）とレポート列（3 桁）で最小桁がずれる。
- **通貨が渡らないと money の scale が 6**（`apps/mcp` の resources、会社なしのリクエスト）。web は money の scale ≥ 6 を「不明」とみなして回避したが、kernel が通貨不明時は scale を省く方が明確。
- `views.list` に `ext.<key>` を書けない（ADR-0014 の既知の帰結）ため、一覧の ext 列は e2e で /meta を加工して確認した。
- dev ビルドで ext を登録しているモジュール／パックが無い（`extFields` は全エンティティで `[]`）。

- レポートの decimal 列の最小桁（通貨桁で良いか、TableColumn に money を足すか）。
- 通貨の最小桁表を kernel と web のどちらに寄せるか（ISO 4217 どおりなら kernel 側を直す）。
