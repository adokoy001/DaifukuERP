## 決めたこと（と理由）

- **出力の型は kernel の `todoResult` に 1 つだけ置いた。** `tableResult`（帳票の出力）と同じ種類の共有 schema で、6 提供元が同じ Zod 定義を複製しないため。`todoItems()` が件数 0 の項目を落とす。DSL や port（ADR-0013）を増やしていないので ADR は作らない。`href` は schema でもアプリ内パス（`/` 始まり、先頭の `//`・`\`・空白なし）に制限し、画面側で画面カタログに対して再検査する二重の防御にした。
- **件数は各 module の既存の読取経路（`Repository.count` / `list`）を利用者の `Context` のまま使う。** 会社・拠点・店舗・本人の境界とロールを新たに書かないため。`systemContext()` や集計専用の経路は作っていない。`edge.todo` は `edge.board` と違い期限切れの実行中ジョブを `uncertain` に変えず、条件（実行中かつリース/期限切れ）で数える。
- **「処理できる人に、処理できるものだけ」を数える。** 各項目を処理 action の `canRunAction` や `can(ctx, entity, op)` で絞り、本人の申請（勤怠・訂正・有給・経費・給与）と自分が作った申告準備資料は数えない（各 action が自己承認を拒否するため、数えると押せない項目が並ぶ）。payment の閲覧専用ロール（viewer）は提供元を実行できない。
- **計画の provider 一覧からの変更**（spec の「実装時に計画から変えたこと」に記録）: sales の期限超過は `payment.todo` に含め仕入側を追加、workforce に勤怠の確認待ち・経費の精算待ち・本人の差戻しを追加、restaurant の「未提出」は直近 7 日（昨日まで）の営業予定日に限定（当日は営業中）し差戻し中の日は別項目で数える。
- **href に問い合わせ文字列を許した。** 従業員・勤怠管理は月単位の表示なので、`/workforce?period=<最古の申請の月>` で該当の月を開く。運営画面は `/operations?from=&to=`（最長 31 日、店舗×日の上限を超えないため）。検査はパス部分を `findNavigationEntry` に通し、hash と外部・未知のパスは表示しない。`/workforce` の route に `period`（YYYY-MM）と `tab` の search を足した（不正値は捨てる）。
- **画面は 1 つの query に `Promise.allSettled` の結果を入れる。** 1 提供元の失敗は `{ ok: false }` としてその提供元のグループだけに出る。再試行はその提供元だけを呼び、query のデータの該当要素だけを差し替える。`staleTime: 0` / `gcTime: 0` で画面表示ごとに取得し、定期取得・フォーカス時・再接続時の再取得は止めた（AC-7）。手動の更新中は前回の件数を残す（UI 規約の状態表示）。
- **受信箱の画面の分野は「その他」。** 業務横断の分野が無いため。サイドバーへの専用の常設リンクは足さなかった。ナビゲーションの既存ブラウザ試験（AC-1、smoke）が「サイドバーのリンクはホーム・自分の勤怠・画面を探す・分野だけ、11 個以下」を検査しており、その契約を変えないため。入口はホームのカード、画面検索と分野「その他」。（2026-10-30 訂正: 初版の記録では「サイドバーは変わらない」としていたが、それまで「その他」の分野が無かったロール（例 workforce_employee）には、受信箱によりサイドバーと分野一覧に「その他」が 1 つ増える。分野は最大 8 のままで 11 個以下の契約内。レビューの指摘で判明。）
- **新しい画面と部品は UI キットとトークンで作り、`token-usage.test.ts` の `CONVERTED` に `pages/inbox-page.tsx`・`components/inbox-card.tsx`・`inbox.css` を足した。** 分岐点は 480 / 768 のみ。失敗表示は `role="alert"` にしない（複数の提供元が同時に失敗すると alert が並ぶため。再試行ボタンは「<業務名>を再試行」という名前を持つ）。

### 決めたこと

- **`my_returned` は `/me?tab=<attendance|expenses>&period=<最古の月>`。** 従業員ポータルは月単位の表示で、前月の差戻しが開いた画面に出なかった（レビューの再現: NOW=2026-09-12、8 月の経費の差戻しで `/me` は 9 月を開き経費が空）。勤怠と経費それぞれ最古の 1 行を読み、古い方の種類のタブと月を開く。`/me` の route に `parseEmployeeSearch`（月は `parseWorkforceSearch` と同じ検査、タブはポータルのタブ id のみ）を足し、`employee-page.tsx` は `workforce-page.tsx` と同じく search から初期化・同期する。指摘は月だけだったが、経費は「今日」タブに出ないためタブも付けた。
- **`edge.todo` は edge_manager 限定。** 結果不明のジョブを解決できるのは `edge.resolve`（manager）だけで、operator は処理できない項目を見ていた（AC-1 と ui.md「誰に出すか」に反する）。operator を例外として残す案より、規約どおり処理できる人に絞る方を選んだ。operator は従来どおり `edge.board` でジョブを見られる。
- **`restaurant_chain.todo` の未提出は店舗×日の集約 2 回で数える。** 営業日ボードは全店舗・14 日分の締め（比較期間を含む）・7 日分の予定を全行読み、`MAX_REPORT_ROWS` を超えると `ValidationError` で提供元全体（差戻し・確認待ち・確定待ちを含む）が失敗していた。`RestaurantDayPlan`（確定済み・営業予定）と `RestaurantClosing`（確定済み、または提出・承認・差戻し中の下書き）を同じ 7 日で `aggregate` し、差を数える。どちらも利用者の `Context` の report port なので店舗の境界は変わらない。先に `count` で上限（既定 10,000 店舗×日）を確かめ、超えたら未提出の項目だけを返さない（運営画面も同じ上限で 7 日のボードを開けないため）。数え方の規則はボードと同じだが、同じ店舗×日に新しい未提出の下書きと古い差戻しが並ぶ場合、ボードは未提出、新方式は差戻し（`returned_reports`）として数える。spec の「差戻し中の日を除く」に合うのは新方式。
- **画面の失敗表示は ui-kit AC-8 の形にした。** 説明文の後にサーバーのメッセージ、エラーコード・HTTP・ヒントは閉じた `<details>`。`MetaError` の詳細部分と同じ形を `components/error-details.tsx` に置いた（`MetaError` 自体は並行する a11y 作業との衝突を避けて変えていない）。`role="alert"` にしない方針は維持。
- **再試行中も失敗表示を残す。** 以前は再試行すると失敗表示（とフォーカス中のボタン）が骨組み表示に置き換わり、フォーカスが `<body>` に落ちていた。再試行中の失敗グループは `status: 'error'` + `retrying` とし、ボタンは `aria-disabled`・「再試行中…」。取得できたら見出し（`tabIndex={-1}`）へフォーカスを移し、結果を既存の `aria-live` 領域で知らせる。再び失敗したら同じボタンにフォーカスが残る。合計の行も消えない（指摘の「更新中も前回の件数を残す」に合う）。
- **急ぎ（`warn`）は文字でも示す。** 件数バッジの中に「急ぎ／Urgent」を出す。アイコンは共通の `icon.tsx` に警告アイコンが無く、共通部品の変更を避けて文字だけにした。項目リンクの読み上げ名は `sr-only` の括弧で項目名・業務名・件数を区切る。
- **表示できない項目（`dropped`）を伝える。** 項目が返ったのに 1 件も表示できない場合は「処理待ちはありません」ではなく「開ける画面がない項目が N 件あります（権限を管理者に確認してください）」を出す（ホームのカードと `/inbox`）。
- **AC-6 の `//` は文言を実装に合わせた。** 拒否するのは先頭の `//`（プロトコル相対）。問い合わせ文字列の値の `//` は値で、パスはカタログで検査され、移動先の `validateSearch` が未知のキーを捨てる。この場合を単体試験に加えた。
- **payment の開く画面は絞り込みを足さず、文書で案内した。** 帳票ページは URL から入力を受け取らず、一覧の search は q・sort・page のみ。帳票の入力の受け渡しは汎用画面の機能追加になり C3 の範囲を超えるため、付録N と spec の表に「方向を選んで実行し、支払期日の列で確認」「一覧は下書き・取消済みも含む」を書いた（指摘 2 件の短期案）。

## 見つけた問題と修正（発見経路つき）

- `restaurant_chain.todo` で `operationsData` に `{}` を渡して型エラー — 発見: typecheck、修正: 範囲と同じ入力を渡す。
- `InboxItemLink` の任意 prop に `undefined` を渡して型エラー（`exactOptionalPropertyTypes`）— 発見: web typecheck、修正: prop の型を `Label | undefined` にした。

- 旧版の e2e が注入していた失敗の本文 `{ code, message, hint }` は API の形（`{ error: { ... } }`）ではなく、画面は「HTTP 500」と汎用のヒントを出していた — 発見: レビューの指摘（メッセージが画面に出ない）を受けて追加した表示の検査、修正: 本文を API の形にした。
- AC-7 のブラウザ検査が `document` に `visibilitychange` を出しており、フォーカス時の再取得を有効にしても成功していた — 発見: 設定を一時的に変える確認、修正: window に出す。
