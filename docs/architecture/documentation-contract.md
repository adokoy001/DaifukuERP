# 文書の管理方法

AIと人が同じMarkdownの正本を読み、ソースの変更と合わせて更新します。

## 役割と優先関係

| 文書 | 答えること | 更新する契機 |
| --- | --- | --- |
| [AI_INDEX](../../AI_INDEX.md) | 何から読み、どのソースを変えるか | 入口や責任範囲が変わるとき |
| [AGENTS](../../AGENTS.md) / CLAUDE | 実装で必ず守る規約 | 基盤の開発規約が変わるとき |
| [architecture](README.md) | 今の構造と主要経路 | package、権限、処理経路が変わるとき |
| [ADR](../adr/) | なぜその設計にしたか | 既存設計の契約を変えるとき |
| [specs](../specs/) | 何を満たすべきか | 実装前と利用者の範囲変更時 |
| [domain](../domain/) | 業務用語・公的根拠・確認日 | 制度や業務の意味が変わるとき |
| [manual](../manual/00-index.md) | 利用者が何を操作するか | 画面や手順が変わるとき |
| [STATUS](../STATUS.md) | 実装済み/未検証/次の課題 | 統合と検証が終わるとき |
| [log](../log/) | 何を変え、どう確かめたか | 実作業の区切り |

実装の事実は現行ソースと実行した試験に基づきます。specと不一致なら、利用者の意図に照らしてコードかspecを修正し、その理由を残します。過去logを現行設計の代用にしません。ADRを置き換えるときは旧判断との関係を記します。

## 内容の書き方

相対リンクを使って移動可能にし、主要な説明から実装の入口へリンクします。構成や流れは小さなMermaid図で補い、巨大な自動生成schemaを本文へ貼りません。宣言から生成できる項目/エンドポイントはmetaとソースを参照し、二重管理しません。

「対応」「完了」「安全」とだけ書かず、対象業務、制約、どの試験を実行したかを示します。将来機能は「計画」「未実装」、ローカルだけの測定は「ローカル」、公開後CI未実行はそのまま明記します。日付・金額・資格情報の例は合成データに限定します。

## 変更の完了時

入口リンク、package登録、主要entity/action名、操作手順、移行番号、実測件数を現行コードと照合します。内部の履歴URLや個人の環境パスを追加しません。相対リンクが切れている場合は直し、読者が参照不能な非公開ファイルを前提にしません。
