# 不変条件と独立した検証

[仕様](../specs/practical-verification.md) / [検証台帳](../verification/invariants.md) / [実測記録](../log/2026-09-13-practical-verification.md)

既存の固定例・実DB・ブラウザ検査を保ち、生成操作列、独立参照計算、有限モデル、mutationを追加する。これらは検査範囲が違い、単一の「安全スコア」にまとめない。

## 責任範囲

| 層 | 仕組み | 実行 |
| --- | --- | --- |
| 文書 | 仕様・実装・試験への索引、前提と失効契機、参照切れ検査 | `pnpm verify:assurance` |
| 変更の確認 | 基点commitからの差分と未追跡ファイルに直接リンクする台帳ID | `pnpm verify:assurance --changed main` |
| 純粋計算 | DecimalのBigInt参照、全銀の独立bytes読取、シフトの有限全探索 | 通常`pnpm test` |
| 業務の連続 | 商流・銀行・申告の生成操作列、会社/拠点の非干渉比較 | 専用DBで`pnpm test:db` |
| 検査自身 | Decimalと貸借検査を変異させ、実テストが検出するか確認 | `pnpm verify:mutation` |
| エッジ設計 | 通信/永続化を分けた有限TLA+モデル、到達性とガード破壊 | `pnpm verify:edge:model` |

## 生成検査と独立性

商流では、有効な受注Q・履行F・請求Bと要求IDを小さな参照状態に置く。銀行は既存入出金への関連付けと新しい入出金の作成を分ける。申告は原資料のhashと確認状態を扱う。成功・拒否・再送を必ず通すprefixに生成tailを加え、各操作の直後に数量・残高・保存状態を検査する。

seed/pathを保存して最小反例を再現する。今回の業務試験は生成配列を使うため、fc.commands専用のreplayPathは使わない。固定prefixだけの成功を生成探索の成果として数えず、生成したtailも実行する。失敗時の縮小がやり直せるよう、試行ごとに独立したfixtureを作る。比較対象から時刻/採番等を除く場合は理由を明記し、金額や権限まで正規化で消さない。

商流・銀行・申告の生成試験は`PBT_SEED`・`PBT_PATH`・`PBT_RUNS`を受け取る。再現時はVitestの`-t`で失敗した1試験を選ぶ。例: `PBT_SEED=730202 PBT_PATH='<出力されたpath>' pnpm exec vitest run --project db modules/trade/test/workflow-model.db.test.ts -t 'sales compares'`。通常の生成回数はDB44例、全銀210例。回数の拡張は任意探索として別に記録し、固定例の合格と混同しない。

シフトoracleは通常制度・最大3人4枠だけを全探索する。本体の制約関数を参照解として呼ばず、型だけを共有する。推薦の品質は最小欠員との差で観測し、すべての問題に最適性を要求しない。制度・権限・実DBの確認を代替しない。

## Mutationの運用

StrykerJSを固定した開発依存として使い、金額・数量の基礎演算と貸借検査のソース全体を対象にする。行番号による対象指定は通常構成では使わず、ソース移動で条件が無検査になるのを避ける。生成されたコピーは`.stryker-tmp`へ隔離し、通常のVitest/lintが重複検査しないよう除外する。元の製品ソースをin-placeで変更しない。

Vitest 5との初回組合せでは、戻り値を空にしても生存する誤判定を観測した。現行はStrykerのcommand runnerから毎回新しいVitestプロセスを起動し、検出できることを確認する。workspaceのkernel参照もsandbox側へ明示解決する。遅くなるため通常gateとは別に実行する。詳細な結果とレビューは[mutation運用](../../verification/mutation/README.md)へ記録する。

## 形式モデルと実装の接続

[エッジのモデルと前提](../../verification/edge/README.md)を参照する。開始受理・応答到着・journal保存・機器送信を一操作にまとめない。遅着する不確実報告も実装の遷移として残す。

モデルの反例と代表トレースを実DB/端末試験へ戻す。有限モデルに反例がないことは、任意長の実行・全OS・機器の副作用の全面的証明ではない。ネットワーク分断時の人による確認待ちは失敗ではなく設計された状態として扱う。

## 読み替えてはいけない主張

別請求書への分割で税額が変わらない、入出庫を任意順に並べ替えても移動平均が一致する、取消すると全DBが元に戻る、schemaが同じなら実行時の認可も同じ、といった性質を無条件に置かない。前提と観測対象を定め、既知の旧版不具合まで参照解として固定しない。
