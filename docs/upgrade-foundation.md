# 共通基盤補強版への移行（2026-09-12）

既存DBには `pnpm db:migrate` を使う。`db:reset` は内容を消去する初期化コマンドであり、移行手順には使用しない。実行前にDBと添付ストレージを同じ時点で保存する。ソース配布用の `bundle-all.sh` は環境設定・業務DB・添付実体を含まない。

## スキーマ

`0007_foundation_integrity.sql` は tenant/company を含む参照制約、消込履歴、発行時スナップショット、取引通貨・単位、在庫評価の締め履歴を追加する。元のテーブルや金額を削除しない。Drizzleの生成順では参照先の一意制約より外部キーが先になるため、この migration は一意制約を先に並べてある。

既存の不正な会社間参照があると外部キー追加は失敗する。migration 全体がロールバックされ、旧データと旧適用履歴が残る。元伝票を確認して正しい参照へ修正し、再実行する。移行を通す目的で参照制約を外したり、別会社のデータへ付け替えたりしない。

`DAIFUKU_PACKS=none` でも DB CLI はインストール済み全パックの物理スキーマを保持する。会社に適用する機能の選択と、保存済みテーブルの存続を分ける。

## 旧伝票の履歴

既存の売上・仕入請求書、入出金がある会社の通貨が JPY 以外なら、移行全体を開始前に拒否する。外貨の金額を円へ読み替えない。元の通貨を保全した明示的な移行設計が必要になる。

- 統制勘定は元の確定仕訳にある、同じ取引先・請求総額に一致する統制側の行が一意な場合だけ復元する。
- 消込履歴は確定・取消済み入出金とその消込明細から復元する。従来の取消の有効日は元取引日だったため、取消分は同日に負数を追記する。
- 元伝票を復元でき、復元額と請求書の入金済額が一致したものに履歴利用可能の印を付ける。元伝票がない消込は推測で補完しない。履歴が不明な請求は現在の入金済額がゼロでも、履歴の修復まで過去残高集計・追加消込・取消を拒否する。
- 旧発行時スナップショットは NULL を維持する。現在の取引先住所や会社名で過去の帳票を再生成しない。再発行が必要なら、保存済み発行ファイルや監査記録から個別に復元する。
- 旧仕訳の勘定分類、旧明細の単位など、過去の値を確定できない情報は原資料の確認が必要。分類が欠けた仕訳の税集計は現在の科目分類で補わず拒否する。新規の確定伝票では記録時点の値を保持する。
- 旧小売月締めは在庫評価締め履歴へ移す。締め日以前の在庫評価を後から変える入力を拒否する。

## 操作・連携の変更

- システムが計算する残高・状態・転記先などへの通常CRUD入力を拒否する。UIはこれらを入力対象から外し、業務アクション経由で更新する。
- 確定・取消・訂正・削除は `expectedVersion` を渡せる。古い画面からの操作は競合として扱う。
- 取消は任意の `correctionDate`（YYYY-MM-DD）を受け付ける。省略すると元取引日を使い、締まっている期間なら開いた期間の日付を指定する。空文字は送信しない。
- 同じメールアドレスが複数テナントにある場合、ログインに `tenantId` を指定する。MCPでは `DAIFUKU_TENANT_ID` を使う。接続後の権限変更・アカウント無効化も次の要求から反映する。
- `pack.apply` は保存済み設定値を維持する。明示的な上書きが必要な新規導入の台本では `force:true` を指定する。会社に未適用のパックの拡張・処理は有効にならない。

## 検証

`apps/api/test/upgrade.db.test.ts` は旧 migration 7本で実データを作成し、追加 migration の適用と再適用、金額・明細の保持、消込前後の基準日残高、不明履歴の拒否、不正参照時の原子的失敗を検証する。新規DBだけでの試験と区別して維持する。
