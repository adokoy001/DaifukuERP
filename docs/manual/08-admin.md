# 08 管理者向け

## 利用者・会社・店舗の権限

操作手順は [運営・権限・BIガイド](appendix-e-operations-control.md#2-利用者と会社店舗を設定する) を参照してください。

- テナント管理者は「利用者と権限」で利用者の作成、有効状態、パスワード、会社所属と担当店舗を管理します。
- 会社の業務ロールとテナント管理権限は別です。会社の `admin` だけでは、テナント全体の利用者管理はできません。
- 店舗限定の所属は、担当店舗に対応を明示した操作だけ利用できます。店舗スタッフが本部の財務・在庫確定を代行することはできません。
- 通常の読取・書込・アクション・CSVは現在の利用者と所属で再認可します。パスワード、有効状態、管理者属性の変更は既存セッションを失効させ、会社所属の変更は次の要求へ反映します。
- 最後の有効なテナント管理者を失う変更、自己の管理権限・有効状態・所属の変更は拒否します。同時編集は版番号で検出します。
- 利用者を無効にする、またはテナント管理者の属性を外すと、その利用者が発行した有効な API キーも同時に失効します（確認の文に件数が出ます。再び有効にしても鍵は戻りません）。下の「API キーの発行と失効」を参照してください。

旧版の `users.roles` を直接編集して権限を変更する運用は使いません。管理UI/APIで所属を変更します。ログアウトは現在のブラウザーからトークンを消します。OIDC SSOの本人紐付け、TOTP MFA、招待メール、メールによるパスワード再設定は [付録H](appendix-h-enterprise-operations.md) の設定後に利用できます。本人パスワード変更や認証設定変更では全端末のsessionを失効させます。

## 会社の追加と編集

テナント管理者は「設定・管理」→「会社の管理」（`/admin/companies`）で、テナントの会社を一覧し、会社を追加し、会社名と国を変更します。テナント管理者でない利用者には画面が表示されず、アドレスを直接開いても「テナント管理者だけ」と表示されます（API も拒否します）。

1. 「会社を追加」を押し、会社コード（英大文字・数字・`_`・`-` で 1〜20 文字。テナント内で重複不可）、会社名、国（ISO の 2 文字、既定 `JP`）を入れて「会社を作成」を押します。通貨は `JPY` に固定です（売上・仕入・入出金の伝票の確定が JPY の会社だけに対応しているため、ほかの通貨の会社は作れません）。入力に誤りがあるとその欄に理由が出て、カーソルが移ります（使用済みのコードもここで分かります）。
2. 作成すると、初期設定（`pnpm run setup install`）と同じ初期データ（勘定科目、税率、当年の会計年度と会計期間、倉庫 `MAIN`、単位、見本の取引先・品目など）が新しい会社に入り、作成した人が会社の管理者として所属します。途中で失敗したときは会社も初期データも残らず、「会社を作成できませんでした。何も保存されていません。」と、失敗した業務（module）の名前が表示されます。原因の詳細（SQL など）は画面に出さないので、技術情報の欄の内容と時刻を添えて運用者に連絡してください。
3. 完了の枠の「切り替えてセットアップを始める」で新しい会社に切り替わり、セットアップウィザード（`/setup`）が開きます。会社情報・会計年度・勘定科目・税・発行者・在庫・業界テンプレート・利用者・勤怠給与を順に整えてください（「[03 初期設定](03-setup.md#セットアップウィザード)」）。画面上部の会社名と「会社を切り替え」の一覧にも新しい会社が出ます。
4. 一覧の「編集」で会社名と国を変えられます。会社コードと通貨は作成後に変更できません。会社の削除・無効化、会社間のデータ移動はできません。

会社の作成・変更は監査に残ります（作成者、日時、変更前後）。通貨は会社に保存しますが、複数通貨の業務はまだ無いため、作成できるのは JPY の会社だけです。業界テンプレートは作成後に「業界テンプレート」画面で会社ごとに適用します。

## API キーの発行と失効

外部連携（会計・EC・BI などのサーバーから REST API を呼ぶ）や AI エージェント（MCP、[09 AI から使う](09-ai.md)）には、人のメールアドレスとパスワードを渡さず、用途ごとの API キーを発行します。テナント管理者は「設定・管理」→「API キー」（`/admin/tokens`）で鍵を発行・失効し、履歴を確認します。テナント管理者でない利用者には画面が表示されず、アドレスを直接開いても「テナント管理者だけ」と表示されます。

- 鍵は 1 つの会社とロールに固定され、人と同じ権限検査を通ります。鍵で作成・変更した記録の監査には操作者が鍵の ID（`actor_type = machine`。各記録の監査ログでは `machine:` に続く ID の先頭 8 文字）として残ります。鍵は承認・確認・本人の申請・給与と勤怠の判断・申告準備など人の判断を要する操作には使えず、利用者・会社・API キーの管理、本人の認証設定、店舗機器の pairing も行えません。
- 発行には本人確認（現在のパスワード。MFA を登録していれば認証コードも）が要ります。本人確認の設定状況を読み込めなかったときは、その旨と「再試行」が表示され、読み込めるまで「発行」は無効です。本人確認は API に `IDENTITY_ENCRYPTION_KEY` を設定した環境だけで使えるため、未設定のときは「発行」が無効になり、設定を促す表示が出ます（一覧・失効・履歴は使えます。設定は [付録H](appendix-h-enterprise-operations.md) と [運用手順](../operations/enterprise-identity.md)）。

1. 「API キーを発行」を押し、名前（何に使う鍵か）、用途（「連携（REST API）」または「AI エージェント（MCP）」）、会社、ロール、有効期間（30・90・180・365 日。既定 90 日）、現在のパスワードを入れて「発行」を押します。用途は入口を限定します: 連携用の鍵は REST API だけ、MCP 用の鍵は MCP サーバーだけで使えます。ロールに「会社管理者」を選ぶと、会社のすべての業務を操作できる鍵になる旨の注意が出ます。必要なロールだけを選んでください。
2. 発行すると鍵（`dfk_` で始まる文字列）が一度だけ表示されます。「コピー」で写し、安全な場所（連携先の秘密情報の保管場所など）に保存してください。画面を閉じると二度と表示できず、サーバーにも鍵そのものは残りません（照合用の hash だけを保存します）。紛失したら新しい鍵を発行し、古い鍵を失効させます。通信の失敗で結果がわからなかったとき、または発行の処理中に画面を閉じたときは、一覧に「未使用」の心当たりのない鍵が無いか確かめ、あれば失効させてください（もう一度発行するときは本人確認を入れ直します）。
3. 連携では `Authorization: Bearer <鍵>` を付けて REST API を呼びます（例: `curl -H "authorization: Bearer $DAIFUKU_API_KEY" http://<API>/api/partner`）。`x-company-id` は不要です（付けるなら鍵の会社と同じ値。別の会社を指定すると 403）。URL の query に鍵を入れたり、ブラウザーから鍵を使ったりはできません（ブラウザーの要求に付く `Origin` / `Sec-Fetch-Site` があると 401）。MCP では `DAIFUKU_API_KEY=<鍵>` を設定します（[09 AI から使う](09-ai.md#mcp-サーバを起動して接続する)）。
4. 一覧には名前（下に鍵の ID の先頭 8 文字）・用途・会社・ロール・発行者・発行日時・期限・最終使用・状態（有効・期限切れ・失効・停止中）が出ます。30 日以内に期限が来る鍵には「期限まで N 日」、一度も使われていない鍵には「未使用」と出ます。「停止中」は発行者がテナント管理者でなくなった鍵で、使えません。
5. 行の「失効」を押し、任意の理由を入れて「失効する」を押すと、その鍵を使う連携・エージェントは次の要求から拒否（401）されます。失効は取り消せません。発行者以外のテナント管理者も失効できます。
6. 行の「履歴」で、発行・失効と、拒否された利用（失効済み・期限切れ・用途違い・発行者が無効・別会社の指定。同じ理由は 1 時間に 1 件）を確認できます。鍵で行った業務の記録は各記録の監査ログで確認します。

- 有効な鍵はテナントで 100 件まで、期限は最長 365 日です。発行後に名前・ロール・期限・会社は変えられず、延長もできません。変えるときは新しく発行し、古い鍵を失効させます。鍵は削除せず、失効済みの記録として残ります。
- 期限が切れた鍵・失効した鍵・用途が違う鍵・発行者が無効な鍵は、理由を区別せず同じ 401（`API key is invalid, expired or revoked.`）になります。理由は履歴で確認してください。未知の鍵を同じ接続元から 5 分間に 100 回送ると、その接続元からの照合は一時的に 429 になります。拒否された既知の鍵は、その鍵だけが 5 分間に 100 回で 429 になります。
- 事故対応: 鍵が漏れた疑いがあるときは、直ちにその鍵を失効させ、新しい鍵を発行して連携先を更新します。利用者のセッションが盗まれた疑いがあるときは、パスワードの再設定と全端末ログアウトに加えて、一覧でその利用者が発行した鍵（発行者と発行日時）を確認し、心当たりのないものを失効させてください。発行の監査には発行に使ったセッションの世代（`issuedSessionVersion`）も残ります。発行には本人確認が要るため、盗まれたセッションのトークンだけでは鍵を作れません。
- MCP 用の鍵を使っても、MCP サーバーはデータベースの接続情報で動きます。MCP を動かす端末は信頼できるものに限り、信頼できない環境からの連携には REST の連携用の鍵を使ってください。

## 導入チェック

「設定・管理」→「導入チェック」（`/admin/health`。管理者か settings ロールの利用者のみ、店舗・拠点に限定された所属では開けません）で、選択中の会社の設定漏れと運用状態を点検します。運用を始める前と、月初などの節目に開いてください。

- 項目は「要対応」（赤）・「注意」（黄）・「OK」（緑）の順に並びます。色だけでなく文字でも状態を示します。
- 各項目の「直す」（OK の項目は「確認する」）で、直す画面へ移動します。直したら導入チェックに戻り、「再点検」を押すと取り直します。再点検に失敗したとき（サーバーに届かないなど）は「再点検できませんでした。前回の結果を表示しています。」と表示し、前回の結果を残します。
- 点検する項目:

| 項目 | 要対応・注意になるとき | 直す画面 |
| --- | --- | --- |
| 今日を含む会計期間 | 今日を含む期間が無い・締め済み（要対応）、30 日以内に期間が尽きる（注意） | 会計年度の作成（`accounting.open_fiscal_year`）、月次締め |
| 標準税率の有効期間 | 今日に有効な標準税率が無い（要対応） | 税率の一覧 |
| 会社プロフィール | 正式名称が未入力・保存値が定義に合わない（注意） | 設定の「会社」タブ |
| 請求書の発行者 | 会社名しか印字できない、登録番号が無い（免税事業者を除く）、保存値が定義に合わない（注意） | 設定の「会社」または「販売」タブ |
| 在庫の設定 | 自動入出庫が有効なのに倉庫が決まらない（要対応）、既定に指定した倉庫で代わる・物品の品目が無い（注意） | 倉庫の一覧、設定の「在庫」タブ |
| メール配送（SMTP） | 未設定（注意。招待・パスワード再設定メールが使えない） | 運用者が設定 |
| シングルサインオン（OIDC） | 常に OK（設定済みか未設定かを表示） | — |
| データベースの更新 | 未適用の更新がある・版に無い適用記録がある（要対応） | 運用者が `pnpm run setup upgrade` |
| 添付の保存先 | 書き込めない（要対応）、保存先が未設定（注意） | 運用者が権限を確認 |
| 業務イベントの配送 | 配送に失敗したイベント（8 回の試行の後に止まった社内の処理・Webhook・メール）がある（注意）。再試行を待っているだけなら OK で、未配送と送信待ちの件数を表示 | 管理者は「イベント配送」の失敗タブ |

- 点検は利用者自身の権限で行います。settings ロールだけの利用者は会計期間や倉庫を読めないため、その項目は「点検する権限がありません」（注意）と表示されます。
- 画面と API（`GET /meta/health`）は、接続先・パスワード・鍵・ファイルの場所を表示しません（設定の有無と件数だけ）。
- バックアップの最終時刻は点検しません。下の「添付とバックアップ」の手順で運用者が確認してください。
- 会社の管理者は、同じ点検（運用の項目を除く）を使って初期設定を順に進める「セットアップ」（`/setup`）も使えます。導入チェックが一覧で点検するのに対し、セットアップは段階ごとに直す操作と確認・スキップの記録を持ちます（「[03 初期設定](03-setup.md#セットアップウィザード)」）。

## イベント配送と Webhook

伝票の確定・取消、入金の消込、契約請求の生成などの業務イベントを、外部のシステム（会計連携・通知の中継・自社の業務システム）へ署名付きの HTTP POST（Webhook）で送れます。受信箱の件数が増えたときに本人へメールで知らせることもできます。配送は運用者が有効にした API サーバーの worker（`EVENT_WORKER_ENABLED=true`、または `events:deliver` の定期実行。[配備手順](../operations/deployment.md)）が行います。worker が動いていないと、イベントは送信待ちのまま溜まります。

### 送信先を登録する

1. 「設定」の「外部連携」タブで「外部連携（Webhook・通知）」を開き、送信先を JSON で入力します（最大 10 件）。1 件の形: `{"id":"accounting","label":"会計連携","url":"https://hooks.example.com/daifuku","topics":["sales_invoice.submitted","sales_invoice.*"],"enabled":true}`。
   - `id` は英小文字・数字・`_`・`-`（40 文字まで、会社内で重複しない）。`topics` は「エンティティ名.submitted」のような名前か「エンティティ名.*」です。主な topic: `<伝票>.submitted`・`<伝票>.cancelled`（確定・取消）、`sales_invoice.payment_applied`・`purchase_invoice.payment_applied`（消込）、`contract.invoice_generated`、`journal_entry.reversed`。`inbox.` で始まる topic は送れません。
   - URL は https で、公開されたホスト名（IP アドレスや社内名は不可）です。開発では `http://127.0.0.1:ポート/...` も保存できますが、送れるのは運用者が開発・試験用に許可したサーバーだけです。
   - **URL は秘密ではありません。** settings ロールの利用者に見え、設定の履歴に残ります。受信側は URL の中の token ではなく、下の署名で送信元を確かめてください。
   - 秘密の値（`secret` など未知の項目）を入れると保存できません。
2. 「設定・管理」→「イベント配送」（`/admin/event-deliveries`。会社の管理者で、店舗・拠点に限定されない所属の利用者だけ）を開き、送信先のカードの「署名鍵を発行」を押して確認します。発行すると、その送信先へイベントの送信を始めます。**発行より前に起きたイベントは送りません。**
3. 表示された署名鍵（`whsec_` で始まる文字列）を「コピー」して受信側に設定します。ダイアログを閉じると再表示できません（画面・URL・ブラウザに保存しません）。分からなくなったら「署名鍵を再発行」してください。再発行すると古い鍵では検証できなくなります。同じ URL のまま再発行しても、それまでに起きた未配送のイベントは引き続き送ります。
4. 送信先の URL を変えると、その送信先の署名鍵は「URL が変わったため再発行が必要」になり、管理者が再発行するまで送りません（settings ロールだけでは署名付きの送信先を差し替えられません）。

署名鍵の発行には、サーバーに認証設定の暗号鍵（`IDENTITY_ENCRYPTION_KEY`）が必要です。無いサーバーでは「署名鍵を発行」を押せず、理由を表示します。

### 受信側で確かめること

各リクエストは `POST`、本文は JSON `{"deliveryId","eventId","topic","occurredAt","companyId","data"}`（`data` はイベントの内容: 伝票の id・番号・金額・日付・状態など）で、次のヘッダーが付きます。

| ヘッダー | 内容 |
| --- | --- |
| `Daifuku-Delivery-Id` | 配送 ID。再試行・再送でも同じです。**受け取った ID を記録し、同じ ID は 1 回だけ処理してください**（同じイベントが 2 回以上届くことがあります） |
| `Daifuku-Event-Id` / `Daifuku-Topic` | イベントの ID と種類 |
| `Daifuku-Timestamp` | この送信の UNIX 時刻（秒） |
| `Daifuku-Signature` | `v1=` と、HMAC-SHA256 の小文字 16 進 |

署名は、鍵に署名鍵の文字列（UTF-8）、対象に `<配送 ID>.<Daifuku-Timestamp>.<受け取った本文のバイト列>` を使った HMAC-SHA256 です。Node.js での検証の例:

```js
import { createHmac, timingSafeEqual } from 'node:crypto';
function verify(secret, headers, rawBody /* Buffer: 受け取ったままの本文 */) {
  const id = headers['daifuku-delivery-id'];
  const ts = headers['daifuku-timestamp'];
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false; // 古い再送を拒む
  const mac = createHmac('sha256', secret).update(`${id}.${ts}.`).update(rawBody).digest('hex');
  const expected = Buffer.from(`v1=${mac}`);
  const actual = Buffer.from(headers['daifuku-signature'] ?? '');
  return actual.length === expected.length && timingSafeEqual(actual, expected);
}
```

本文を JSON として読み直してから文字列に戻すと署名が合わなくなるので、受け取ったままのバイト列で検証してください。10 秒以内に 2xx を返すと「送信済み」になります。転送（3xx）は追いません。

### 失敗と再送

送れなかったとき（10 秒以内に応答が無い、接続できない、TLS の検証に失敗、3xx・2xx 以外の応答）は、1・2・4・8・16・32・60 分の間隔で再試行し、8 回目（約 2 時間）で「失敗」に止めます。送信先のアドレスが内部・予約済みの範囲に解決された、署名鍵を復号できない、本文が 256 KiB を超える、といった直らない失敗はすぐ「失敗」にします。社内の処理（購読者）が失敗し続けたイベントも同じ間隔で 8 回試して止めます。

「イベント配送」の「失敗」タブで、状態・種別・送信先または宛先・topic・作成日時・試行回数・最終エラーの説明を確認し、受信側を直してから「再送」を押します。再送した行は同じ配送 ID のまま「送信待ち」タブへ移ります。導入チェックの「業務イベントの配送」も、失敗があると「注意」になり、管理者には失敗タブへのリンクを表示します。送信先が消えた・無効になった・URL が変わった・その topic を購読しなくなった配送や、通知を止めた利用者宛てのメールは「取消」になります。「送信済み」と「取消」は 30 日後に削除します（「失敗」は削除しません）。

一覧には本文・URL・メールアドレス・署名鍵・受信側の応答の内容は表示しません。

### 受信箱のメール通知

1. 管理者が「外部連携（Webhook・通知）」の「受信箱のメール通知を許可する」をオンにします（サーバーにメール送信の設定が必要です）。
2. 各利用者が「やること（受信箱）」の「件数が増えたらメールで知らせる」をオンにします（[付録 N](appendix-n-navigation.md#やること受信箱で処理待ちを確認する)）。

約 15 分ごとに本人の権限と担当範囲で件数を数え、増えたときだけ、会社名・前回と今回の合計・項目ごとの件数・受信箱へのリンクを日本語と英語で 1 通にまとめて送ります。オンにした直後の最初の点検は基準にするだけで、メールは送りません。メールの件数には、受信箱の画面で開けない項目（表示されない項目）が含まれることがあるため、画面の合計より多いことがあります。利用者が無効になった、または会社の所属を外れたときは通知の登録を消します。受信箱の件数は Webhook には送りません。

### 注意

送信先へ業務データを送ることが個人情報の第三者提供などに当たるかは、送信先を登録する管理者が判断してください（現在のイベントは取引先名・氏名・住所を含みませんが、法的な評価はしていません）。外部の慣行（Standard Webhooks など）との互換は確認していません。

## 監査と確認

伝票には作成・更新・確定・取消・改訂の記録が付き、画面の監査ログから実行者と変更前後を確認できます。「利用者と権限」にはアクセス変更の監査を表示します。パスワードの値や認証ハッシュは監査画面へ出しません。会計・在庫の確定記録は内容を直接編集せず、取消・改訂で訂正します。

代理AIからの要求も利用者の権限を引き継ぎ、代理元を記録します。AIを使うだけで操作権限が増える仕組みにはしません。API キーによる操作は、監査に鍵の ID（`actor_type = machine`）として残り、人の操作とも代理AIとも区別できます。各記録の監査ログには操作者が `machine:<鍵の ID の先頭 8 文字>…` と出ます。その 8 文字を「API キー」画面の一覧（名前の下の ID）と照らし合わせると、鍵の名前・発行者・履歴がわかります（監査ログに鍵の名前を直接出すことは今後の課題です）。

ロールごとに何ができるかは下の「権限マトリクス」、だれがいつ何を変更・CSV 出力したかを会社全体で探すときは「監査ログの検索」を使います。

## 権限マトリクス

「設定・管理」→「権限マトリクス」（`/admin/permissions`）で、どのロールがどのデータに何をできるかを確かめます。会社の管理者（admin ロール）とテナント管理者が使えます。admin でない利用者には「設定・管理」に表示されず、アドレスを直接開いても「管理者だけ」と表示されます。店舗・拠点に限定された所属の admin には項目が表示されますが、開くと「管理者だけ」と表示されます（どちらも API が拒否します）。表はシステムの権限定義から毎回作るので、業務（module）や業界テンプレートを追加すると自動で反映されます。権限そのものは変更できません。所属のロールは「利用者と権限」で変えます。

- 「データ」タブは、業務ごとにまとめたデータの行 × ロールの列の表です。セルの略号は 閲（閲覧）・作（作成）・更（更新）・削（削除）・確（確定）・取（取消）・改（改訂）・出（CSV 出力）で、表の下に凡例があります。`admin` はすべての操作ができます。
- 行の札の意味: 「自分の行のみ」（自分が担当・作成した行だけ）、「条件付き」（区分などの条件に合う行だけ）、「項目の制限」（一部の項目は特定のロールだけが読める）、「店舗限定」「拠点限定」（店舗・拠点に限定された所属でも使える）、「店舗端末」（店舗の機器から操作できる）、「変更の監査なし（CSV 出力は記録）」、「未適用のパック」、「テナント共通」（全会社で共有するデータ）。
- 行の「詳細」を開くと、行ルールの説明（例: 入出金で販売ロールは「区分 = 入金」の行だけ）、その行ルールが絞る操作、読めるロールが限られた項目、店舗・拠点に限定された所属でロールごとにできること、店舗端末の操作、名前付きの承認（遷移）とそれを実行できるロールが出ます。行ルールは既存の行の閲覧・更新・確定などを絞るもので、作成する値は各業務の検証で確かめます。
- 承認の遷移が 1 つだけある伝票では、「確定」は承認ロールで行う「（遷移名）経由のみ」と表示されます。ロールの列を並べた表では、その「確」に「*」が付きます。
- 「業務」「ロール」「名前で探す」で絞り込めます。ロールを 1 つ選ぶと、データ × 操作の表に切り替わります。スマートフォンなど幅の狭い画面では最初からロールを 1 つ選んだ表示になります。未適用のパックのデータは「未適用のパックも表示」で表示します。条件は URL に残るので、同じ会社を選んでいれば URL を共有して同じ表を開けます。
- 「アクション」タブは、締めや取込などの操作をロールごとに実行できるかと、その入口の権限（ログインした利用者、特定のロール、あるデータへの操作）を示します。操作によっては中でさらに確認（テナント管理者だけ、など）を行います。
- 凡例の「kernel の機能」は、データの表に現れない権限です。会社設定の変更と履歴・導入チェックは admin と settings ロール、権限マトリクスと監査ログの検索は admin、利用者と権限・会社の管理はテナント管理者が使えます。
- 複数のロールを持つ人は許可の和になります。行ルールは、許可を与えるロールがすべて制限されているときだけ当たります。

## 監査ログの検索

「設定・管理」→「監査ログの検索」（`/admin/audit`）で、選択中の会社の監査記録を探します。権限マトリクスと同じく、会社全体に所属する admin とテナント管理者が使えます（admin でない利用者には表示されず、店舗・拠点に限定された所属の admin が開くと「管理者だけ」と表示されます）。開くと直近 7 日（今日を含む、日本時間）の記録が新しい順に 50 件ずつ出ます。

1. 期間（開始日・終了日。日本時間の 2000-01-01 以降の日付で、両端を含めて 366 日まで）、利用者、対象（データの種類や会社設定・所属など）、操作（作成・更新・削除・確定・取消・CSV 出力など）を選んで「検索」を押します。対象を選ぶと記録 ID でも絞れます。
2. 利用者の一覧には、今の所属者、テナント管理者、所属を外した人（「（所属解除済み）」）が出ます。退職者が辞める前に何を変えたか・出力したかも探せます。システム・店舗端末・AI の操作は「ID を直接入力」で実行者の ID を入れて探します。AI が利用者の代わりに行った操作は、その利用者で絞ると出ます（「名前（AI 代理: agent id）」と表示）。
3. 結果の各行に日時（日本時間）、利用者、対象、操作と内容（作成は書いた値、更新は変わった項目の前後、CSV 出力は「n 行（全 m 件）・列・条件」）が出ます。「記録を開く」で記録の画面へ移り、「変更前後をすべて見る」で全項目を確かめます。admin は項目の制限を受けないので、読めるロールが限られた項目の値も表示されます。表示しない設定の項目（保存先の鍵など）はだれにも出ません。この会社で使えないデータ（未適用のパックや、停止したパックのデータなど）の記録は出ず、対象に選ぶと「この会社ではこの対象の監査を読めません」と表示されます。
4. 「次へ」「前へ」「最初へ」でページを移ります。条件とページは URL に残るので、再読込・戻る・URL の共有（同じ会社を選んでいる場合）で同じ結果が出ます。この画面でたどっていないページを URL から開いたときは、ページ番号の代わりに「続きのページ」と表示します。条件を変えて「検索」を押すと、いつも 1 ページ目から表示します（同じ条件でもう一度押すと、最新の記録を読み直します）。日付の誤り（実在しない日付、2000-01-01 より前、開始日が終了日より後、366 日超）はその欄に理由が出て、検索しません。URL の読めない条件（壊れたページの指定など）は使わず、その旨を表示します。
5. テナント管理者は「範囲」で「テナントの管理操作」を選ぶと、利用者の作成・変更、パスワード変更、セッション失効、招待・本人確認の記録を探せます。範囲を切り替えると、利用者・対象の選択肢もその範囲のものに変わります。

- 一覧の CSV 出力（「一覧」画面の CSV）は「CSV 出力」の操作として記録され、だれがいつ何件・どの列・どの条件で出力したかが分かります。条件のうち制限項目の値は「[masked]」のまま表示します。
- 検索は記録を読むだけで、記録の変更・削除や、検索したことの記録はしません。監査記録は追記専用で、アプリから更新・削除できません。
- 別の会社の記録を見るときは画面上部で会社を切り替えます（全会社の一括検索はしません）。会社の管理者は所属していない会社を選べないので、その会社の記録も見られません。
- この画面は電子帳簿保存法の検索要件（取引年月日・金額・取引先での検索）を満たすものではありません。証憑の検索は別の画面で行います。

## 添付とバックアップ

添付本体は `DAIFUKU_STORAGE_DIR` で指定した保存先に置きます。相対パスはAPIの作業ディレクトリ基準です。DBの添付情報だけではファイル本体を復元できません。

[導入・更新手順](../operations/setup.md) には、DBバックアップの別DB実復元と失敗後の再開手順があります。DB dumpだけで添付本体・設定秘密・DB roleまで保全したことにはなりません。停止時点を合わせたバックアップ、復元後の伝票・残高・添付照合を運用手順へ含めてください。

添付の訂正は新しいファイルを追加して差替え理由を記録します。ウイルス検査、外部オブジェクトストレージ、電子帳簿保存法上の制度適合認定は実装・保証していません。

## 運用設定

設定画面は、選択した会社に対する権限で操作します。業界テンプレートは同じ会社の業務設定へ影響するので、異なる業種の試験は会社を分けて行ってください。初回管理者、JWT、DB接続秘密は開発用の固定値を流用しません。

外部接続、TLS、CORS、ログイン試行の制限、監視の方針は [SECURITY.md](../../SECURITY.md) と導入先の運用設計で確認してください。アプリを動かすOS/DB全体の安全性を、UIの権限設定だけで代替できるものではありません。
