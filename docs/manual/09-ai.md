# 09 AI から使う（技術者向け）

## 考え方: すべての操作は「アクション」

大福帳の業務操作は、すべて名前の付いた **アクション**（例 `sales_invoice.create`、`sales_invoice.submit`、`accounting.trial_balance`、`real_estate.move_in`）として定義されています。一つのアクション定義から、次の三つが自動で作られます。

- REST API: `POST /actions/<アクション名>`
- MCP ツール: 名前の `.` を `_` に置き換えたもの（例 `accounting_trial_balance`）
- 画面: 一覧・フォーム・レポート（v0.1 の画面が呼ぶのは台帳の基本操作とレポート、請求書の表示だけ）

入力の検査・権限・監査ログは、どこから呼んでも同じです。2026-09-11 のデモ環境では 229 のアクションがあり、MCP ツールも 229 個でした（内部専用のアクションは公開されません）。**画面にボタンの無い操作**（逆仕訳、年度の開設、入居・退去、家賃請求の作成、小売の月次締め、テンプレートの適用など）は、ここで説明する方法で実行します。

## MCP サーバを起動して接続する

MCP サーバ（`apps/mcp`）は標準入出力（stdio）で動きます。API サーバとは別のプロセスで、DB に直接接続します。

| 環境変数 | 必須 | 意味 |
|---|---|---|
| `DATABASE_URL_OWNER` / `DATABASE_URL` | ○ | `.env` から自動で読まれる（作業ディレクトリとその 3 階層上まで探す） |
| `DAIFUKU_EMAIL` / `DAIFUKU_PASSWORD` | ○ | エージェントが代理する利用者。その利用者のロールで動く |
| `DAIFUKU_AGENT_ID` | | 監査ログに残るエージェント名（既定 `mcp-agent`） |
| `DAIFUKU_COMPANY_ID` | | 会社（既定はその利用者の既定の会社） |
| `DAIFUKU_STORAGE_DIR` | | 添付の保存先（既定 `.data/storage`） |

起動コマンド（リポジトリの外からでも動くよう `-C` でディレクトリを指定）:

```sh
DAIFUKU_EMAIL=admin@example.com DAIFUKU_PASSWORD=password \
  pnpm -s -C /path/to/erp-experiment --filter @daifuku/mcp start
```

**`-s`（silent）を必ず付けてください。** 付けないと pnpm が `> @daifuku/mcp start` という行を標準出力に書き、MCP の通信路に JSON でない行が混ざります（2026-09-11 に SDK のクライアントで確認: エラーを報告しつつ接続は続いたが、厳密なクライアントでは失敗しうる）。

Claude Code に登録する例（**未検証**。コマンドの形は上と同じ）:

```sh
claude mcp add daifuku -e DAIFUKU_EMAIL=admin@example.com -e DAIFUKU_PASSWORD=password \
  -- pnpm -s -C /path/to/erp-experiment --filter @daifuku/mcp start
```

設定ファイル（`mcpServers` 形式）で書く例（**未検証**）:

```json
{
  "mcpServers": {
    "daifuku": {
      "command": "pnpm",
      "args": ["-s", "-C", "/path/to/erp-experiment", "--filter", "@daifuku/mcp", "start"],
      "env": { "DAIFUKU_EMAIL": "admin@example.com", "DAIFUKU_PASSWORD": "password", "DAIFUKU_AGENT_ID": "claude" }
    }
  }
}
```

接続すると、ツール一覧（説明は英語と日本語、`mutates: yes/no`、読み取り専用のツールには `readOnlyHint`）と、リソース `daifuku://meta`（全体のメタデータ）・`daifuku://entities/<台帳名>` が見えます。エラーは `isError: true` と `{code, message, hint, details}` で返るので、エージェントは `hint` を読んで入力を直せます。MCPもAPIと共通の実行環境設定を使い、`DAIFUKU_PACKS` の選択に従ってテンプレートを読み込みます。

## REST API の呼び方

```sh
# 1. ログインしてトークンを得る（12 時間有効）
TOKEN=$(curl -s -X POST http://localhost:3000/auth/login -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"password"}' | jq -r .token)

# 2. アクションを呼ぶ: POST /actions/<名前>、本文は入力の JSON
curl -s -X POST http://localhost:3000/actions/accounting.trial_balance \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -H 'x-agent-id: my-agent' \
  -d '{"from":"2026-10-01","to":"2026-10-31"}'
```

- `x-agent-id` を付けると監査ログに `agent` として残ります（エージェントから呼ぶときは付けてください）。
- 会社を切り替えるときは `x-company-id: <会社ID>` を付けます。
- 台帳の基本操作には短い形もあります: `GET /api/<台帳>?search=&limit=&offset=&orderBy=field:asc&where=<JSON>`、`GET /api/<台帳>/<id>`、`POST /api/<台帳>`（明細は `{"lines": {"<明細台帳>": [...]}}`）、`PATCH /api/<台帳>/<id>`（`{"patch": {...}, "expectedVersion": n}`）、`DELETE /api/<台帳>/<id>`、`POST /api/<台帳>/<id>/submit|cancel|amend`、`GET /api/<台帳>/<id>/audit`。
- エラーは HTTP ステータスと `{"error": {code, message, hint, details}}`。主なコード: `VALIDATION`（400、`details.issues[].path` に項目）、`NOT_FOUND`（404）、`CONFLICT`（409、同時更新・重複）、`INVALID_STATE`（409、状態として許されない操作）。
- 全エンドポイントの一覧は `GET /openapi.json`、ブラウザで見るなら `/docs`（Swagger UI）。

## `/meta` の見方

`GET /meta`（MCP では `daifuku://meta`）は、ログインした利用者から見えるシステムの全体像です。エージェントには最初にこれを読ませてください。

| キー | 中身 |
|---|---|
| `entities[]` | 台帳。`name`、`label`（ja/en）、`kind`（`entity` / `document`＝状態を持つ伝票）、`fields[]`（型、必須、既定値の有無、選択肢）、`ops`（この利用者に許された操作）、`lines`（明細台帳）、`extFields`（テンプレートが足した項目）、`views` |
| `actions[]` | アクション。`name`、`description`（ja/en）、`mutates`（データを変えるか）、`inputSchema`（入力の JSON Schema）、`resultKind`（`table` はレポート） |
| `modules[]` | モジュールとメニュー |
| `roles` | この利用者のロール |
| `packs[]` | 読み込まれたテンプレートと、この会社に適用済みか（`applied`） |

1 つの台帳だけなら `GET /meta/entities/<名前>`、設定は `GET /meta/settings`。

## エージェントに伝えておくこと

- **確定した伝票は消せません。** `DELETE` や `*_delete` は下書きにしか効かず、確定済みには `INVALID_STATE`（「Cancel the document instead」）が返ります。誤りは `cancel` → `amend`（訂正版の下書き）→ 修正 → `submit` で直します。
- **仕訳は取消もできません。** 手入力の仕訳は `accounting.reverse_entry { id, date? }` で逆仕訳を作ってから正しい仕訳を入れます。請求書・入出金などから自動生成された仕訳は、起票元の文書を取消します。単独の逆仕訳は拒否されます。
- 入金済みの請求書は取消できません。先に入出金を取消します。
- `submit` は帳簿（仕訳・在庫・請求書の残高）を動かします。人間の確認を取ってから実行させてください（v0.1 に承認の仕組みはありません）。
- `serverOwned` / `readOnly` の項目（請求書の `balance` / `status` / `paidAmount` など）は公開入力へ含めません。直接の書換えは拒否されます。入金は `payment` の作成と `submit` で反映させます。
- 画面と同様、保存・削除・確定・取消・訂正では取得時の `expectedVersion` を送って競合を検知してください。取消の `correctionDate` は任意で、空欄ならキーを省略します（元の取引日）。指定した場合はその訂正日を使います。
- 締めた会計期間の日付では確定できません（`INVALID_STATE`、`hint` に再開の方法）。
- 監査ログに残るので、試行錯誤は本番の会社でさせず、デモ用の会社か DB で行ってください。
- 必須の文字列項目に空文字 `""` を送ると受け付けてしまう場合があります（例: `partner.create {"name": ""}` が成功した）。入力は送る前に確かめさせてください。
